# Iteration 3 of the sTGC alignment: the first refit after the 17.55 mm strip-frame
# fix (825d1fe21e, reco + slow sim together).
#
# WHY. StFttClusterMaker used to build the cluster position from the strip's
# row-band coordinate instead of the strip centre, dropping a constant 17.55 mm
# (26.74 mm on the diagonal rows) from every FTT hit. Reco now asks
# StFttRawHit::stripCenter() for it. Measured point by point on this very run
# (script/fttPointDump.C, 14826 points, identical cluster identity): the hit moves
# 17.5500 mm in its own measured local coordinate -- y for H clusters, x for V --
# and 18.9080 mm in both x and y for the diagonals (26.74/sqrt2). In the global
# frame that is +-1.7550 cm with the per-quadrant sign of
# StFttDb::getGloablOffset_ClusterPoint: A (+,+), B (+,-), C (-,-), D (-,+).
#
# Every fitted pentOnStation therefore LAGS the code by that amount. This run
# measures the lag against FST-only tracks rather than assuming it.
#
# WHAT TO EXPECT. Each quadrant's blind residual should sit at ~+1.755 cm
# OUTWARD from that quadrant's own origin, i.e. +dx,+dy for A, +dx,-dy for B,
# -dx,-dy for C, -dx,+dy for D, in the PRECISE coordinate of each orientation
# (dx for V strips, dy for H). The correction is -(residual), so .000004 should
# come out ~1.755 cm SMALLER in magnitude than .000003 per quadrant. If it does
# not, the 17.55 mm story is incomplete and the table should not be regenerated.
#
# Note the quadrant split in FwdTracker.h assigns qidx from the hit's x,y against
# the StFttDb quadrant origins, which do NOT move. Every hit moves away from its
# own origin, so the assignment gets strictly more inclusive -- no hits are lost
# to the shift, and some previously-unassigned band hits join. The cross-condition
# cuts gate the OTHER coordinate, which is unchanged, so the same candidates are
# histogrammed. Histogram range is +-15 cm and script/stgcQuadOffsets.C searches
# the peak over +-2.9 cm, both comfortable for a 1.755 cm shift.
#
# CONTROL. pico_iter2_20260930 is the same 90 files, same 13000 events, same
# config with the pre-fix code; its blinddiag/ is already on disk, so no extra
# jobs are needed for the before/after. It is NOT a pure A/B -- StFttDb gained the
# real per-quadrant transform (9830929fb2) and scMapXY correction (8bdfb264bd)
# in between -- but the per-quadrant outward 1.755 cm is a distinctive signature.
#
# GEOMETRY. fGeom is passed EXPLICITLY (argument 11) rather than through the
# fGeom.root symlink, so the campaign cannot drift if the link is repointed:
#     fGeom.dev2022sm.misalign1.sdt20211112.000003.root
# pentOnStation is read only by StFttDb (via StFttDbMaker) and by AgPosition when
# the geometry is built with "misalign", so the cache and the table are a matched
# pair -- this one was built at sdt 20211112.000003, the same entry StFttDb
# resolves at this run's 2022-03-04 stamp. Once .000004 exists, BOTH have to be
# remade before any job runs, or the result is silently 17.55 mm wrong.
#
# TIME WINDOW. The per-run anchors moved into the DB on 2026-10-16, so
# fttDataWindow/ no longer holds the .txt files that iter2 staged (they are in
# fttDataWindow_keep/). Checked for run 23063028: 382 of 384 per-VMM anchors are
# identical between the DB and that file; vmm 54 differs by 5 ticks and vmm 260
# has no DB calibration (-1, on-the-fly anchor) where the file had 3694. In mode 2
# the stored min/max are not used at all -- the -1,3 window on the command line is
# -- so only the anchors matter, and 2 of 384 VMMs is nothing for a per-quadrant
# mean over 90 files.
#
# RESULT, 2026-10-24. All 90 jobs clean. blinddiag_iter3.root, read with
# script/stgcQuadOffsets.C("blinddiag_iter3.root",0,2,5.9) -- note the 4th
# argument: with the default 2.9 cm peak-search half-width the macro flagged
# quadrant C's dx at stations 3 and 4 as sitting on the window boundary.
#
# The per-quadrant residual moved by exactly the predicted 1.755*(sx,sy):
#
#       dy    n=15   mean +0.008 mm   rms 0.41 mm   max |dev| 1.26 mm
#       dx    n=10   mean +0.088 mm   rms 0.49 mm   max |dev| 1.02 mm
#       both  n=25   mean +0.040 mm   rms 0.44 mm
#
# over 25 independently fitted coordinates at 4.8-175 sigma. Excluded: disk1
# quad A (zero V-strip hits, anomalous in iteration 2 as well) and the 5 dx
# cells below the 5-sigma floor, quadrant C stations 3 and 4 among them -- and
# those were weak in iteration 2 too (2.9 and 2.6 sigma), so it is not new.
#
# Because the delta is a universal constant to better than half a millimetre,
# StarDb/Geometry/stgc/pentOnStation.20211112.000004.C applies the ANALYTIC
# -1.755*(sx,sy) to all 16 cells instead of the fitted per-cell deltas, which
# would have left those 5 dx cells held at a value known to be 17.55 mm wrong.
#
# RETRACTED. An earlier version of this header claimed the fitted sTGC
# "alignment" collapsed 11x in dy once the constant was removed. That was read
# out of the geo(..)+align(..) text in .000003's comments, which is STALE:
# stgcTableAddDelta.py updates t0/t1 and leaves the comments alone, so by
# .000003 they still described iteration 1 (row 1's comment implies t1 = 5.428,
# the actual value is 4.605). Using the real numbers the claim does not survive.
# The confirmation above needs no decomposition of the table and stands on its
# own. .000004's comments are rewritten.
#
# ALSO FOUND, and now understood. The Sep-30 cache this campaign ran on is not
# reproducible: rebuilding sdt20211112.000003 today moves 9 FST sensor nodes --
# wedge 6 on all three discs -- by (0.155,-0.032) cm, twice the FST survey
# (-0.0775,+0.016).
#
# The mechanism: dev2022sm puts the 12 wedges of each FST disc into TWO groups at
# two xy values 2x the survey apart, which is the half-support-structure split
# (hssOnFst). The Sep-30 cache splits them 5/7 -- wedges 1-5 in one group, 6-12 in
# the other -- while a fresh build splits them 6/6, which is the physically
# sensible half. The one wedge that changes groups is wedge 6, hence the 9 sensors.
# Dmitry's 10-16 deactivation of the 11 old 2021-10-25 FST entries included exactly
# one hssOnFst row, which fits. Two FRESH builds at .000003 and .000004 agree with
# each other exactly, so none of this comes from the campaign.
#
# iter2 and iter3 used the same cache, so the measurement above is a clean
# difference and is unaffected. Iteration 4 inherits the 6/6 boundary.
#
# Noted on the way: the y2024 tag applies NO FST survey at all -- all 108 sensors
# sit at exactly (0,0) in both Run-24 caches -- so Run-24 tracking runs on ideal
# FST geometry. That is why the Run-24 cache pair shows zero FST movement.
#

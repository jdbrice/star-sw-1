FST outer-sensor gap offset: a sign error in StFstHitMaker

The two outer sensors of every FST wedge are reconstructed 1.000 deg away from where the silicon is — one full kFstStripGapPhi, about 0.39 cm at r=22 cm. Correcting it improves the track fit for exactly those hits by 3.2% in χ²/ndf, and lets 8.5% more of them survive the quality cuts. Original email

The bug

StFstHitMaker.cxx lines 159 and 163 add the ±0.5·kFstStripGapPhi term to the two outer sensors with the signs the wrong way round:

L159  sensor == 1:  ... - kFstzFilp[disk-1]*kFstzDirct[moduleIdx-1]*0.5*kFstStripGapPhi;   -> +
L163  sensor == 2:  ... + kFstzFilp[disk-1]*kFstzDirct[moduleIdx-1]*0.5*kFstStripGapPhi;   -> -

Nothing else changes. Swapping the two signs puts every strip exactly on the AGML silicon.

Same ±1.000 deg on all 36 wedges. The inner sensor is exact everywhere, so only the outer pair is affected.

Which sensor owns which strips is not derivable from the code — getSensor() comes from mChannelId (electronics) and getPhiStrip() from mGeoId (geometry), and only Calibrations/fst/fstMapping links them. Read out over all 36864 channels:

sensor 0 (inner):  phiStrip   0-127,  rStrip 0-3
sensor 1 (outer):  phiStrip   0-63,   rStrip 4-7
sensor 2 (outer):  phiStrip  64-127,  rStrip 4-7

The reconstruction is also wrong on its own terms, without reference to AGML: those two spans overlap by 0.77 deg across the wedge centreline, at identical radii (both rStrip 4-7), where kFstStripGapPhi says there is a 1 deg gap. Silicon cannot overlap.

Reconstructed outer-hit azimuth relative to its own wedge centreline, with the correction off and on. No track fit is involved, so nothing can absorb the effect. 152 files of runs 23081008/23081015, ~58M rows.

With the fix off the two outer sensors pile up on top of each other at the centreline — 1.67× the surrounding density, approaching the 2× expected where two sensors overlap — and the outer edges are empty. With it on the centreline empties completely and the edges populate. The inner sensor is untouched, which is the control.

The narrow spikes are real, not a plotting artefact: they sit at the same local phi in the inner control with and without the fix, so they are fixed features of the detector (a few strips with elevated occupancy, recurring at the same strip number across wedges). They are worth a second look in the outer panel: a single spike near |δφ| = 5° with the fix off becomes two, bracketing it at about 3.8 and 6.3°, with it on. That is a 1 deg shift of the two outer halves in opposite directions acting on a fixed feature — the same signature as the centreline and the edges, seen a third way.

Binning note: one FST strip per bin (30/128 = 0.234375°), rebinned by 4. Bin widths that are not an exact multiple of the strip pitch beat against it and paint periodic spikes that look like structure.

What this does not fix

  • Not the 12-fold wedge structure. The RMS of the 12 per-wedge means is unchanged to ≤0.002 cm. That remains open — see the FTT geometry page and residual page.
  • Not the absolute fit. χ²/ndf is ~7.8, nowhere near 1, and FST pull widths are 0.161 (U) and 0.555 (V) with 73.8% of rows outside a 1 cm residual core. The FST covariance model dominates the χ²; a 3.2% geometric improvement is real but small against it. Fixing the covariance is plausibly a prerequisite for judging any FST alignment work.
  • Not MC. StFstFastSimMaker never applies a gap term at all, so MC has no displacement to remove — applying the correction there would introduce one. MC has a different problem: it bins phi on a flat 1536-fold grid that ignores the 1 deg gap and the outer sensors' ±15.5 deg extent. See StFstSlowSimMaker, which has since been written and closes against GEANT truth.

Applying it

The afterburner reads finished hits from MuDst (setFstHitSource(MUDST)) and never runs StFstHitMaker, so fixing that file alone does not change afterburner output. MuDst does keep mMeanRStrip, mMeanPhiStrip and mHardwarePosition, and the correction is a constant shift in phi, so it can be applied at load time on existing files — no DAQ reprocessing:

StFwdHitLoader.cxx, after the FstWedgeAligner block:

    if ( mApplyFstGapFix && sensorIndex > 0 ) {
        const double sgnAsIs = ( sensorIndex == 1 ) ? -1.0 : +1.0;
        vPhi -= sgnAsIs * kFstzFilp[diskIndex] * kFstzDirct[wedgeIndex] * kFstStripGapPhi;
    }

Opt-in via setApplyFstGapFix() on StFwdHitLoader/StFwdTrackMaker, and a trailing applyFstGapFix argument on fwd_afterburner_db.C.

Open question: this flag is a trap

Now...I haven't yet thought about automating this flag. I'm sure we will make mistakes setting/not setting mApplyFstGapFix for current mudst vs fixed Mudst if we ever fix StFstHitMaker. This is exactly why I did not make this a commit and PR, but rather putting this in an email. Please think through what we should do. Not fixing StFstHitMaker may be an option...

Whether the correction should be applied depends on which production wrote the MuDst, and that is invisible in the file. Set it wrong and you get a 1 deg error either way — uncorrected, or corrected twice.

But it only matters in one of the two tracking modes. That halves the problem and is worth stating first:

space-point mode (default)planar mode (xihe-align)
what the hit position comes from StMuFstHit::localPosition, read as (r, phi, z) — see the warning below meanRStrip/meanPhiStrip + StFstConsts.h + the plane from fGeom.root
carries the gap sign from StFstHitMaker? yes no — strip indices are unchanged by the gap sign
needs setApplyFstGapFix? yes, and getting it wrong is the trap never — the flag is irrelevant here
has its own copy of the gap convention? no yes, in TrackFitter.h — independent of StFstHitMaker, must be right on its own terms

So the flag is a space-point-mode problem only. Planar mode never reads the affected quantity, which is also why Xihe's alignment work was unaffected by either of the StFstHitMaker bugs.

Separate defect found in space-point mode, still open. StFwdHitLoader does

  float vR   = localPosition(0);
  float vPhi = localPosition(1);
  float x0 = vR*cos(vPhi);   float y0 = vR*sin(vPhi);

in both loadFstHitsFromMuDst and loadFstHitsFromStEvent. But commit 9e70bfd0a9 changed setLocalPosition() to store sensor-local cartesian coordinates, so cos/sin of it is meaningless — the same error PR25 fixed inside StFstHitMaker, in a different consumer that PR25 did not touch. Existing 2022 productions predate 9e70bfd0a9 and are still polar, so they read correctly today; this bites any MuDst or StEvent written with current code, including the new slow-sim chain. It is independent of the gap question and needs its own decision: either the loader converts, or localPosition goes back to polar and Xihe's planar code takes the cartesian from elsewhere.

Do not decide it by hand — three options

1. Make the flag unnecessary. Fix the convention once (below), reprocess, and delete the flag. Nothing to set, nothing to detect. The cost is reprocessing and a window in which old and new MuDst coexist — during which one of the next two is still needed.

2. Stamp the convention into the file. StMuFstHit::mHardwarePosition is a UInt_t holding 1-108: 7 bits used, 25 spare. Set a high bit to mark the new convention, bit-clear meaning the old one, so every existing file still reads correctly. No schema change, no new member — but getDisk()/getWedge()/getSensor() compute straight from it and would need masking, in both StMuFstHit and StFstHit. Explicit and free at runtime; only helps files written after it lands.

3. Detect it from the data. The signature is not statistical, it is a geometric impossibility, and it is binary:

                 outer hits with          outer hits with
                 |dphi_local| < 0.383     14.4 < |dphi_local| < 15.4
  displaced           83,135                        0
  correct                  0                  167,426

With the displacement the two outer sensors overlap across the wedge centreline; corrected, that band is empty because it is the physical gap. Rule: apply the correction iff the centreline band is populated. Old data gets corrected, fixed data does not, and MC is empty too (AGML knows the gap), so the dangerous MC case is safe by construction rather than by remembering. Cost: 2.03 band hits/event on run 23081008, so ~50 events settles it — and it can be a one-time pre-pass over the file's FstHit branch, measured per file, so no events are spent and run conditions do not matter.

These are not exclusive: 1 is the destination, 3 covers the transition and every already-written file, 2 is worth doing if we expect this class of change again.

Underneath all of it: one source of truth for the gap

The 1 deg gap is currently written out by hand in five places. They agree today, so nothing is broken — but they all encode the same physical claim (which side of the wedge centre-line each outer sensor sits on), and that claim can only be changed correctly if all five move together. One function should state it:

/// Which side of the wedge centre-line an outer sensor sits on:
///   +1 sensor 1, -1 sensor 2, 0 inner sensor (no gap).
/// THIS IS THE SINGLE STATEMENT OF THE OUTER-SENSOR GAP CONVENTION.
inline int fstOuterSensorSide(int sensor)
{
   if (sensor == 1) return +1;
   if (sensor == 2) return -1;
   return 0;
}

/// Signed phi offset of an outer sensor's strips from their no-gap position.
inline double fstOuterGapPhiOffset(int sensor)
{
   return -0.5 * kFstStripGapPhi * fstOuterSensorSide(sensor);
}

in StRoot/StEvent/StFstConsts.h, which all five already reach. Every site then collapses onto it, reproducing today's behaviour exactly:

sitenowwith the helper
StFstHitMaker:159,163 two branches, ∓S·0.5·gap + S*fstOuterGapPhiOffset(sensor) — one line, branches gone
TrackFitter.h dphi if(sensor==1)…else if(sensor==2)… + fstOuterGapPhiOffset(sensor)
TrackFitter.h centerDphi +S·o / −S·o fstOuterSensorSide(sensor) * S * outerCenterDphi
StFstSlowSimMaker gapTerm = (sensor==1)? −sgn·0.5g : +sgn·0.5g sgn * fstOuterGapPhiOffset(sensor)
StFstFastSimMaker separate kA/kB expressions one expression via the helper
StFwdHitLoader (legacy flag) sgnAsIs = (sensor==1)? −1 : +1 fstOuterSensorSide(sensor) * S * kFstStripGapPhi

The loader entry is worth a second look: its sgnAsIs is exactly −fstOuterSensorSide(), and it applies a full gap rather than a half — correct, since undoing a sign flip is twice the offset. Routing both through one function makes that relationship visible instead of something to re-derive.

Two steps, deliberately separate:

  • Step 1, centralise. Pure refactor, provable line by line, no behaviour change. Reviewable without agreeing about the physics.
  • Step 2, flip. If the measurement below is accepted, the entire change is two return values in fstOuterSensorSide(), and all five sites follow.

Both written out as diffs, assuming PR23-25 have landed: proposed_change.txt.

On whether to fix StFstHitMaker at all: leaving it unfixed does avoid the vintage ambiguity, but only for as long as nobody fixes it. It is an obvious two-sign error once written down, so someone eventually will, and at that point every analysis carrying a hard-coded ON silently acquires the error it was correcting. Auto-detection removes the reason to leave it broken, so the recommendation is: fix StFstHitMaker.cxx:159,163 for future productions, and make the load-time correction self-configuring rather than a flag anyone has to remember. A version marker on the hit would be cleaner still, but needs a schema change, and detection works on every file that already exists.

Three workable options then — detect per file, mark a bit, or leave StFstHitMaker alone and always correct — with different trade-offs between robustness, code churn and how badly it fails if someone forgets. Worth agreeing on before this becomes an interface anyone depends on, rather than deciding it here.

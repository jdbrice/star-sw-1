METHOD

Rather than read the plan and ask "is it complete?", invert it: enumerate every
code file changed against the real STAR main and ask which PR claims it.
Anything unclaimed is either a gap or a deliberate keep-local, and BOTH need a
decision written down -- otherwise someone later "fixes" the omission by
pushing a diagnostic we proved wrong.

  baseline   starbnl/main = 1ef9aaefdf (2026-09-22), i.e. star-bnl/star-sw
  scope      StRoot, StarVMC, StarDb, StDb; .cxx .h .C .xml .idl
  result     133 changed code files in 25 packages
             113 matched a PR in the plan by file stem or package
              20 matched nothing  <- the list below

THREE BUCKETS, not one. The decision for each file is:

  (A) PUSH AS-IS          a real fix STAR needs
  (B) PUSH, STRIP THE FLAG a fix that exists behind a compensation switch.
                          The FST outer 1 deg gap is the case in point:
                          applyFstGapFix only exists because MuDst written
                          before the fix needs compensating. Upstream wants the
                          fix in StFstHitMaker with no switch.
  (C) KEEP LOCAL          diagnostics and compensations that were PROVEN WRONG
                          or are ours alone: applyFstMirror (FST wedge mirror),
                          applyFttXYMirror (FTT V/H), the blind-diagnostic
                          machinery (fttNoAdd, mix), our analysis makers.

#18 / mVtxIndex -- the full detail, trimmed out of the plan   (2026-10-07)
================================================================================

The plan keeps only the constraint. The mechanics, for when we actually write
the PR:

  StEvent/StFwdTrack.h            defines pack5and3 and hands the raw byte out
                                  through vertexIndexRaw()
  StPicoDstMaker.cxx  (~L2574)    copies it verbatim:
                                    picoFwdTrack.setVtxIndexRaw(
                                        evTrack->vertexIndexRaw() )
  StPicoEvent/StPicoFwdTrack.h    unpacks with >>3 & 0x1F and & 0x07
  StFwdTrackMaker.cxx             sets it

  Old layout  pack6and2:  6 bits vtxIndex (0-63) + 2 bits trackType (0-3)
  New layout  pack5and3:  5 bits vtxIndex (0-31) + 3 bits trackType (0-7)

  Also in the same change: StEnumerations.h gains kBLCVtxId; StVertex.h gains
  setBLCVertex() / isBLCVertex().

  StMuDSTMaker/COMMON/StMuFwdTrack.h is a DIFFERENT kind of change -- it does not
  pack. It adds "UChar_t mTrackType = 0" beside the existing mVtxIndex, so ROOT
  schema evolution covers reading old MuDst with the new class.

  Minor, worth fixing while we are in there: that member's comment enumerates the
  types as 0=Global,1=BLC,2=Primary,3=FwdVtx,4=BLCVtx and stops -- it predates
  kFCSConstrained=5. Comment only, the UChar_t holds 5 fine.

  Also noticed and worth a line in some PR: StFwdTrackMaker.h:231
  setFittingMaterialEffects() writes the config key "TrackFitter:materialEffects"
  with a lowercase m, while TrackFitter.h:118 reads "TrackFitter:MaterialEffects"
  with an uppercase M. FwdTrackerConfig::canonize() only strips whitespace and
  "[0]", so it does not fold case and the setter cannot work. Nothing calls it
  today, so nothing is broken -- it would bite the first person who tries to turn
  material effects on.

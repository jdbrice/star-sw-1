BUG 1 — FTT projection plane index mismatch  [FIXED]
-----------------------------------------------------
Location: addFttHits(), line ~1549

Symptom:
  Every AAA "FTT proj" line shows z=312.25 regardless of which "disk" (0,1,2,3)
  is being searched.  FTT physically has 4 disks at z≈281, 304, 327, 349 cm.

Root cause:
  addFttHits(gtr, disk) called projectToFtt(disk, track) which uses
  mFttPlanes[disk] for disk=0..3.  createAllFttPlanes() builds 32 planes
  indexed 0..31 by globalPlaneIndex.  The first 4 planes (indices 0..3) all
  belong to quadrants of the same physical disk and share z=312.25.  So
  every refit search projected to the same z, while the hitmap[disk] held
  hits from physically different disks.

Impact:
  Wrong projection (x,y) for disks 1,2,3 → acceptance criteria computed
  against the wrong position.  dPhi and dx/dy comparisons are biased for
  three of four disks.

Fix applied (FwdTracker.h, addFttHits):
  When hitmap[disk] is non-empty, compute the mean z of the actual hits in
  that disk and project to a flat plane (normal=(0,0,1)) at that z.
  Falls back to the old projectToFtt() only if the hitmap is empty.
  Old line commented out with //AAA, new code labelled //AAA fix.

---------------------------------------------------------
Location: addFttHits(), addFstHits()

BUG 3 — H-strip accepted by wrong coordinate (dPhi instead of dy)  [FIXED]
---------------------------------------------------------------------------
Location: findFttStripsNearProjectedState(), acceptance for horizontal strips

Symptom (from fwdtrack.1.log, good electron tid=1, pT≈1.5 GeV):
  H strips are rejected on 3 of 4 FTT disks at dPhi=0.143–0.185 (threshold=0.12)
  even though the hit belongs to the correct MC track (tid=1) and
  dy=0.0–2.8 cm (well within thresholdY=7.5 cm):

    AAA FTT hit H pos=(-23.570+/-4.33, 23.469+/-0.01) dy=2.806 dPhi=0.185 → REJECT
    AAA FTT hit H pos=(-23.570+/-4.33, 23.469+/-0.01) dy=0.042 dPhi=0.174 → REJECT
    AAA FTT hit H pos=(-24.065+/-4.33, 26.028+/-0.01) dy=0.248 dPhi=0.143 → REJECT

Root cause:
  An H strip measures y precisely (sigma_y~0.01 cm) but has large x uncertainty
  (sigma_x~4.33 cm ≈ half strip pitch).  The strip center in (x,y) space is
  therefore displaced in phi from the track by:
    δφ ≈ sigma_x * |y| / r²  ≈  4.33 * 23.5 / 32²  ≈  0.10 rad
  adding up to 0.18 rad depending on quadrant.  Using dPhi as the primary gate
  for H strips is fundamentally wrong because the strip phi-center is not where
  the track crosses the strip.

Fix applied (FwdTracker.h, findFttStripsNearProjectedState):
  H-strip acceptance changed to: dy < thresholdY && dR < thresholdR
  Old dPhi-based line kept and commented out with //AAA.
  (dy is the precision measurement for H strips.)

BUG 4 — V-strip accepted by wrong coordinate (dPhi instead of dx)  [FIXED]
---------------------------------------------------------------------------
Location: findFttStripsNearProjectedState(), acceptance for vertical strips

Symptom:
  Same analysis as Bug 3.  V strips measure x precisely (sigma_x~0.01 cm),
  large y uncertainty (sigma_y~4.33 cm).  A V strip with dx=0.08 cm and
  dPhi=0.024 easily passes — this particular case is fine.  But dPhi for a
  V strip would fail for the same geometric reason if the strip center's phi
  were displaced.

Fix applied (FwdTracker.h, findFttStripsNearProjectedState):
  V-strip acceptance changed to: dx < thresholdX && dR < thresholdR
  Old dPhi-based line kept and commented out with //AAA.
  (dx is the precision measurement for V strips.)

BUG 5 — OR logic in XY gate accepts hits 16 cm off in one coordinate  [FIXED]
(part of Bugs 3 & 4 — fixed by the same edit)
------------------------------------------------------------------------------
Location: findFttStripsNearProjectedState(), original acceptance conditions

Symptom:
  Original condition used || between dx and dy thresholds:
    dx < 7.5 || dy < 7.5
  With a blown-up projection at x=-1.2, y=-6.4, one hit at
  (pos=-3.8, -19.9) had dx=2.6 (passes) and dy=13.5 (fails) → ACCEPT.
  Hit is 13.5 cm off in y purely because the || let it through.

  the || issue is automatically resolved:

  V strip: only dx is checked  → no OR ambiguity

REMAINING ISSUES NOT YET FIXED
================================================================================

1. findFstHitsNearProjectedState: FST dphi threshold (0.082 rad) uses the same
   phi-center displacement problem as FTT.  For FST, the rasterized strip pitch
   (~3 cm) gives δφ ≈ 3/(2*r) ≈ 0.03–0.05 rad added uncertainty.  The threshold
   may need to be widened or replaced with dr/dphi separately per strip orientation.

2. makeFstCovMat: dr and dphi used directly as sigma without dividing by sqrt(12)
   (strip uniform distribution → sigma = pitch/sqrt(12) ≈ pitch/3.46).
   This over-estimates FST hit uncertainty by 3.46×, degrading fit quality.
   (Documented in forwardTrackingSummary.txt issue #5.)

3. LOG_DEBUG/LOG_INFO redefined in StFwdHitLoader.cxx as `if(false) std::cerr`.
   Compile-time suppression of all hit loader diagnostics; makes debugging
   hit-loading problems very difficult.
   (Documented in forwardTrackingSummary.txt issue #4.)

BUG 6 — FST covariance matrix inflated by sqrt(12)  [FIXED — StFwdHitLoader.cxx]
-----------------------------------------------------------------------------------
  rSize=3 cm and phiSize=0.00409 rad used directly as σ in covariance matrix.
  For a uniform strip distribution, σ = pitch/sqrt(12).  `sqrt12 = sqrt(12.)` was
  already computed in the function but never applied — a silent pre-existing TODO.
  Fix: const float dr = rSize/sqrt12;  const float dphi = phiSize/sqrt12;

  Impact: Kalman trusted FST 12× less than correct → sigU at FTT 5.63 → 1.75 cm.
  Misalignment budget at FTT: ~2 cm → ~5.75 cm.

BUG 7 — FTT strip selected by minimum dPhi instead of precision coordinate  [FIXED]
-------------------------------------------------------------------------------------

  After Bug 6 fix, sharp projection exposed 4 cases where min-dPhi V strip had
  dx=10-13 cm while a strip with dx<1 cm existed but was skipped.
  Fix: H strips select by min |dy|; V strips select by min |dx|.

  Result: "2 hits added" cases: 28 → 56 (+28 recovered V-strip matches, fwdtrack.4.log).
  4 remaining V-REJECT are genuine quadrant-boundary cases (no V strip within 7.5 cm,
  dR=8-13 cm for the closest strip — not a search algorithm issue).

BUG 13 — Beamline fit always re-seeds, never uses global momentum  [FIXED — FwdTracker.h]
-------------------------------------------------------------------------------------------
Location: doBeamlineTrackFitting(), line ~850

  if ( true || gtr.mIsFitConvergedFully == false ){
      gtrPV = fitTrack(seedWithPV);        // always: re-seed from scratch
  } else {
      gtrPV = fitTrack(seedWithPV, &gtr.mMomentum);  // NEVER reached
  }

  `true ||` short-circuits the condition permanently.  The beamline fit discards
  the global track's fitted momentum (sigU≈1.75 cm after all hit-finding fixes)
  and re-derives it from raw hit positions using GenericFitSeeder, which can get
  the wrong charge for nearly-collinear FST hits (common for very forward tracks).
  By contrast, doPrimaryTrackFitting always uses &gtr.mMomentum.

Fix: removed `true || ` so the condition evaluates correctly:
  if ( !gtr.mIsFitConvergedFully )  → re-seed (global fit failed)
  else                              → use &gtr.mMomentum (global fit good)

ISSUES FOUND IN THIS RUN
  1. Wrong charge on final track (events 5, 8 = 20%):
     GenericFitSeeder::averageCurvature() computes signed curvature from
     3-point combinations using the beamline hit (0,0,0), an FST hit, and
     the last FTT hit.  For near-straight forward tracks (curvature ≈ 0),
     the signed curvature is near zero and the cross-product sign is
     numerically unstable — small rounding can flip q.
     The correct charge SHOULD propagate from the global fit, but currently
     gfs.makeSeed() recomputes charge even when an external momentum is given.
     Fix needed: pass the global track charge directly to setupTrack instead
     of re-deriving it from the hit geometry in the beamline/primary fitters.

  2. Event 4: electron not seeded (only 1 soft secondary seed found):
     Likely the electron left fewer than 3 FST hits in this event
     (e.g. traversed a dead zone or the phi rasterization failed).
     Not a bug — can happen in simulation.

  3. Event 3 produces 14 fits (3 seeds):
     Secondary particles from the EM shower left enough FST hits to form
     3 separate seeds.  All are correctly identified via QaTruth.

INVESTIGATION PLAN

Rank of suspicion (most to least likely root cause):

A. FST covariance fix (Bug 6 — StFwdHitLoader.cxx, divide by sqrt(12))
   LARGEST numerical change: FST hit weight increased 12× in Kalman.
   If real FST hits have systematic offsets (alignment, calibration) that the
   old inflated uncertainty was absorbing, the now-tighter constraint would
   pull tracks AWAY from the true direction.  This directly explains:
   — wider FCS residuals (track extrapolated to wrong angle)
   — lower match rate (projection misses cluster)
   — possible fit failures (tight FST constraint clashes with FTT)
   TEST: revert to  const float dr = rSize;  const float dphi = phiSize;
   in makeFstCovMat() and re-run pico analysis.

B. Beamline seed fix (Bug 13 — FwdTracker.h, removed true||)
   Beamline fit now starts from global momentum which is near-zero pT (≈0,0,1).
   The old code (true|| always re-seeded) had the GenericFitSeeder use the full
   0→360 cm lever arm to estimate pT and z-slope — often better for z constraint.
   This directly explains:
   — DCA_Z peak less sharp at z=0 (beamline fit starts from bad z-slope)
   TEST: temporarily restore   if ( true || ... )  in doBeamlineTrackFitting.

C. FTT H/V strip selection fix (Bug 7 — FwdTracker.h, min-dx/dy not min-dPhi)
   Now selects the strip with the SMALLEST precision-coordinate distance.
   For Pythia tracks at different phi angles, the min-dPhi strip may actually
   be the correct one (same strip lit by the track), while min-dy or min-dx
   selects a neighboring strip that happens to be geometrically closer but is
   from a different track.
   TEST: revert to   if ( sp < horizontalMin_dp )  and  if ( sp < verticalMin_dp )

D. FTT/FST projection plane fixes (Bugs 1, 8 — addFttHits/addFstHits)
   New projections use mean-z from hitmap hits; old always used mFttPlanes[0..3].
   If the mean-z of real data hits differs from the plane geometry due to
   alignment offsets, the new projection might be less accurate than using
   the single consistent plane.
   TEST: revert addFttHits/addFstHits projection to mTrackFitter->projectToFtt/Fst.

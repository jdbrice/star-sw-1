The macro used to report success after a refused write
------------------------------------------------------
StDbManager::storeDbTable returns bool and fstGeometry_db.C ignored it, so the
first attempt printed

    stored fstOnTpc at 2021-10-10 00:00:00
    Done with database upload.

directly under the "INSERT command denied" error. With "all" that would have
been eight tags of false confirmation over a database that never changed.
Fixed 2026-10-15 (21db9ace6d): it checks the return value, prints
"*** WRITE FAILED ... NOTHING WAS STORED ***" and stops the tag loop.

ANY PUSH LOG OLDER THAN 2026-10-15 SAYING "stored ..." IS NOT EVIDENCE THAT
ANYTHING LANDED.


First push, once permission is granted
--------------------------------------
Test on the smallest possible change first: ideal22 / fstOnTpc. One row,
identity content, beginTime 2021-10-10, which is below every entry that exists
today, so even a fully successful push cannot change what any job reads. It is
also the floor St_db_Maker needs, so it is the first thing we want stored
anyway.

  1.  root4star -b -q 'fstGeometry_db.C("ideal22","writedb","fstOnTpc")'

  2.  confirm independently of the macro -- do not trust the log:

      mysql -h star-db01.sdcc.bnl.gov -P 3316 -u loader -N -e \
        "select beginTime, entryTime, dataID, flavor, deactive, Id, t0, t1, t2
           from Geometry_fst.fstOnTpc where beginTime='2021-10-10 00:00:00';"

      expect ONE row, entryTime = now, ofl, deactive 0, t=(0,0,0).

  3.  the other three tables of ideal22, one at a time:
        ...("ideal22","writedb","hssOnFst")          ->   2 rows
        ...("ideal22","writedb","fstWedgeOnHss")     ->  36 rows
        ...("ideal22","writedb","fstSensorOnWedge")  -> 108 rows

  4.  then the remaining seven tags in full -- NOT "all", which would redo

      for t in fstOnTpc hssOnFst fstWedgeOnHss fstSensorOnWedge ; do

Deactivating the old entries
----------------------------
Geometry_fst holds 11 entries, all dated 2021-10-25, loaded in 2022, 438 rows,
flavor ofl. THEY CARRY NO GEOMETRY -- t=(0,0,0) on every one of the 438 rows,
and the rotation is identity on every row but one: fstSensorOnWedge at
00:00:03, dataID 217, elementID 37 (Id 1036), has a +10 mrad rotation about z,
evidently a test. That entry is superseded by 00:00:04, which is identity, so
nothing resolves to it. So the FST survey has never been in the database for
real data; Run 22 real-data jobs have all used ideal FST geometry.

(Caught only when the full push was verified -- the first check sampled one
beginTime per table for rotations and happened to miss 00:00:03. Check every
entry, not a representative one.)

2021-10-25 falls inside Gene's "real data: any time after that" window, i.e.
after the 2021-10-10 ideal and 2021-10-15 survey slots, so those rows win over
anything we write at 2021-10-15 and our entries would be reachable only by MC
timestamps.

Why deactivate rather than write a second copy after 2021-10-25: the second
copy would make TWO entries the standing requirement for every future alignment
update, one in the MC survey window and one for real data. The next iteration
-- Xihe's or ours -- has to remember both, and forgetting either puts MC and
real data on different geometry with no error and no log line. Deactivating
keeps it at one entry per update:

    2021-10-14  ->  ideal22   (2021-10-10)    MC, misalignment off
    2021-10-19  ->  survey22  (2021-10-15)    MC, survey
    any later   ->  survey22  (2021-10-15)    real data

Nothing is lost. The content is identity, which is exactly what ideal22 at
2021-10-10 provides, so a Run 22 production reconstructed without the survey is
reproduced by asking for a timestamp in [2021-10-10, 2021-10-15).

ORDER: push everything first, ask for the deactivation second. Between the two
nothing changes for anybody -- real data keeps resolving to the identity rows
exactly as today. Reversed, there would be a window with no Geometry/fst entry
at all below a real-data timestamp.

deactivate.txt in StRoot/StFstDbMaker/macro is the request to send to Dmitry
(drafted, not sent -- it opens with "we have just pushed", so it goes after the
push). Tell Gene and Daniel first: deactivation is the moment the survey
becomes the default for everyone's new Run 22 real-data jobs.


Removing the release copy -- same PR, but mind the merge order
-------------------------------------------------------------
$STAR/StarDb/Geometry/fst holds the release's four files at 20211110.000001.
They are byte-identical to our fst/*.20211015.000000.C, field by field -- git
itself reports them as 100% renames in the branch diff. They have to be
REMOVED, not just superseded: St_db_Maker takes the latest beginTime at or
before the requested time whatever the source, and 20211110 is later than every
database entry, so while they exist production never reads Geometry_fst at all.

They are removed in the PR branch fwd-fstdb-geometry-macro (fcstrk13), second
commit, alongside the README note. Same pattern for sTGC later: the removal of
StarDb/Geometry/stgc/*.C goes in the StFttDbMaker/macro PR, not a separate one.
Those three are identity and dead after the stgc->ftt rename (#20 XML + #23
code), so their removal carries no ordering risk.

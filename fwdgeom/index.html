Forward geometry API: what lives in StFttDb and StFstDb

One place to look before writing geometry code for the forward upgrade — a new maker, an alignment table writer, a check macro. Everything below is a public entry point on the DB class that owns the numbers, so nothing here has to be re-derived or copied out of a reader. If you find yourself copying an index expression out of someone else's loop, the function you want is probably on this page; if it is not, it should be added rather than copied.

Status column: main = already upstream, PR = on a pull-request branch, local = committed on akio202607 only and still needs a branch.

→ Is the simulated geometry actually misaligned? — the ideal-vs-misaligned comparison: all 16 sTGC pentagons move by exactly the table they were given, and the FST 54/54 split confirms the half-id fix in the built geometry.

Conventions you have to know first

  • Units are not uniform. StFttDb's shifts and strip geometry are mm; its z locations, its TGeoHMatrix transforms and every Survey table translation are cm. StFstDb is cm throughout.
  • The two detectors index survey tables differently. This is the one that bites.
    • FTT rows are POSITIONAL: row = 4*station + pent, which is what AGML's <Misalign row="N"/> indexes. The Id column is only checked.
    • FST rows are addressed by the Id COLUMN: Id = 1000 + (wedge-1)*3 + sensor. Row order is irrelevant; a row with the wrong Id lands on the wrong sensor however the table is sorted.
    A writer that assumes one convention for the other produces a shuffled table that still loads and still looks plausible.
  • Quadrants and pentagons are not the same index. AGML orders the four pentagons of a station A,D,C,B by rotation about z; StFttDb numbers quadrants A,B,C,D. The permutation is {0,3,2,1}, measured from the built geometry (script/fttQuadConvention.C). It is its own inverse, which is a property of this particular permutation and not something to rely on — use the named functions.
  • Reflections are not rotations. getGloablOffset_ClusterPoint() returns a translation plus axis sign flips. AGML rotates instead. The two agree in quadrants A and C and differ by 140–200 mm in B and D. The TGeoHMatrix API below carries the rotation properly; the (d,s) API is what the existing reconstruction uses and is unchanged.
  • DB timestamps pick the geometry. Run 22: -10 ideal (all identity), -11 survey, -15 survey + first alignment, -16 the alignment lane. See StRoot/StFttDbMaker/macro/Geometry/ftt/README.

Gotchas worth reading once

  • Check geometryFromDb() before anything frame-related. With the DB off, StFttDb uses a frozen 2021 survey, not an ideal geometry — up to 48 mm and ~15 strips from AGML nominal. "No DB" and "ideal" are different detectors.
  • The simulation's geometry and the reconstruction's may not agree. AGML misalignment does not reach a starsim run today, so MC geometry is nominal while StFttDb applies a survey. StFttSlowSimMaker hides this by inverting the same live StFttDb call it will later be reconstructed with, so positions round-trip and residuals look clean — but the strip indices are displaced by 1–15 strips depending on quadrant and axis. Anything channel-level in simulation (occupancy per VMM, acceptance edges, dead masks) is affected; the residual plot you would check is not.
  • mm against cm is the most common slip in this code. The Survey tables are cm, the shifts are mm, and loadGeometryFromDb() multiplies by 10 for exactly that reason.
  • Returns are -1 or false on a bad index, never an exception and never a silent 0, so check them — a quadrant of -1 used as an array index is the failure this is trying to prevent.

Still to do

  • Most of the list above is marked local: committed on akio202607 and not yet on a PR branch. The DB-geometry block is PR #23 (fwd-fttdb-db-geometry); the strip geometry, the TGeoHMatrix transforms and the index maps still need branches of their own.
  • stripSegment()/stripsCross() are written for the four existing orientations. A UV plane would add orientations rather than change the interface.
  • No equivalent of stripsCross() exists for the FST, where the question is different (strips run along R, and the z constraint does the work instead).

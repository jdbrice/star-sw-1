Is the simulated geometry actually misaligned? (2026-10-23)

Any plan that takes strip numbers, acceptance or residuals from a simulated geometry is worthless if that geometry is nominal while the reconstruction applies a survey. This is the check: build the same tag twice, once with the misalignment switched on and once without, and difference the position of every sTGC pentagon and every FST sensor.

Result: the sTGC moves by exactly the table it was given, to 5 x 10-14 cm, on all 16 pentagons.

What was run

  root4star -l -b -q 'build_geom.C("dev2026","ideal.root",false,"sdt20211016")'
  root4star -l -b -q 'build_geom.C("dev2026","misal.root",true ,"sdt20211016")'
  root4star -l -b -q 'dumpGeomNodes.C("ideal.root","ideal.txt")'   # once per file:
  root4star -l -b -q 'dumpGeomNodes.C("misal.root","misal.txt")'   # gGeoManager is a singleton
  python3 cmpGeomNodes.py ideal.txt misal.txt

dev2026 is y2023 with the FST built from FSTMv1m, the config that carries <Misalign> tags; the sTGC module has them in every config. The third argument adds the BFC misalign option, which is the only thing that makes StBFChain call AgPosition::SetReal() — without it AgMLDbFunctor returns the unit matrix however many tags the XML carries. The fourth picks which tables: the misalignment is read at that timestamp.

sTGC: 16 of 16 exact

At sdt20211016 the sTGC tables resolve to Geometry/stgc/*.20211011, the survey slot — the numbers that used to live hardcoded in StFttDb. Measured shift against the table row AGML was told to apply, in cm:

Worst |measured - table| over all 16: 4.7 x 10-14 cm, which is double precision. The loop is closed end to end for the first time: the hardcoded StFttDb survey, written into a DB table, read by AGML's <Misalign> tags, arriving in the built geometry.

It also confirms the row convention independently. Rows are positional, row = 4*station + pent with pent in the A,D,C,B rotation order. Had that map been wrong the quadrants would have been permuted while every individual value still matched — only the per-row comparison catches it.

FST: 54 / 54, and that is the interesting part

The 108 sensors move in two rigid groups, which is what fstOnTpc + hssOnFst[half] should produce:

  (0.0713, -0.3010, 0.0) cm    54 sensors = 6 wedges x 9
  (0.2263, -0.3330, 0.0) cm    54 sensors = 6 wedges x 9

The shift values match an earlier measurement. The split does not: it was 45/63, five wedges against seven. That asymmetry is what exposed the iwedgem.ge.5 bug in the half-id test, which should be .ge.6 for a 12-wedge half to divide evenly. Seeing 6/6 here means the fix is verified in the built geometry, not merely in the generator output.

What this does not prove

  • Translations only. FST sensors are TUBS segments placed on the beam axis, so their node origin is (0, 0, z) and a pure rotation in a survey row would not show up in this probe. Every row used here is a pure translation, so the test is valid as run, but it is not a general misalignment test.
  • The two detectors came from different places. No local FST table resolves at sdt20211016 (the earliest is 20211110), so that half exercises the Run 22 survey as pushed to MySQL. The sTGC half is served from a local file.
  • Nothing here says a simulation will use it. This is the geometry; the BFC misalign option still has to be passed by whatever chain actually runs.

If you rebuild geometry yourself, verify by content

A clean cons is not evidence that your XML reached the library. With no local copy, cons satisfies its targets from the $STAR repository and never runs the parser: exit 0, clean link, and someone else's geometry in the .so, with no error and no warning. Check the build, not the exit code:

  grep -c agmlParser build.log                 # 0 means the parser never ran
  nm -C $lib/libStarGeometry.so | grep dev2026 # the tag you changed should be there

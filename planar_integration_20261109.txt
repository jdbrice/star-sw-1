2. THE FINDING: upstream's planar measurement is wrong
------------------------------------------------------

This is the important result of the evening and it is a code finding, not a
measurement.

`createTrackPointFromPlanarMeasurement` on main (and therefore on every PR
branch) builds the in-plane coordinate as

    hitOnPlane[0] = fh->getX();
    hitOnPlane[1] = fh->getY();

A genfit PlanarMeasurement's coordinates are (u,v) measured FROM THE PLANE
ORIGIN. Assigning global x,y is correct only for a plane whose origin lies on
the beam axis, which describes none of ours -- the FTT chamber planes are
centred near x = +-11 cm, y = 9 cm. So every FTT hit would be displaced by its
chamber offset, SILENTLY, because a PlanarMeasurement keeps only the in-plane
components and cannot notice the rest.

It has never fired because the planar branch is unreachable while
kUseSpacePoints is true. It would have fired the moment anyone flipped it, and
it would have looked like bad alignment rather than a bug.

fcstrk11 has the correct form and has had it since planar mode was adopted:

    TVector3 diff = global - plane->getO();
    hitOnPlane[0] = diff.Dot( plane->getU() );
    hitOnPlane[1] = diff.Dot( plane->getV() );

Ported to the integration branch, along with three smaller planar-mode fixes:

  - kUseSpacePoints constexpr -> TrackFitter:useSpacePoints config key, so both
    arms come from ONE build. A comparison across two binaries is not one.
  - EPD hits forced to the space-point path: getPlaneFor() knows only FTT and
    FST, so an EPD hit in planar mode gets a null plane and is dropped.
  - two off-by-one bounds checks, "index > size()" where it must be ">=".
    An index exactly equal to size() passed the guard and read one past the end
    of mFttPlanes / mFstSensorPlanes. Only reachable in planar mode.

Commits: be4ad24772 (the merge), d35ffa641b (the planar fixes).


3. What the integration branch still CANNOT do, and why it is design work
-------------------------------------------------------------------------

It has no complete FST planar decode, and porting one is not possible.

fcstrk11 derives the FST hit position from the sensor's own AGML shape phi
limits -- mFstSensorPhi1/Phi2, mFstSensorRmin/Rmax -- and that machinery reads
FwdGeomUtils::getFstSensorOrigin, which #39 deliberately DELETED. The two
designs disagree at the root:

    fcstrk11   strip -> phi from the AGML sensor shape (geometry-driven)
    #39/#41    StFstDb owns the conventions; FST planes from
               sensorPlacementByIndex(), measurement = ProlateSpacepointMeasurement

The #39/#41 direction is the right one, so the FST strip->phi decode has to be
REWRITTEN against StFstDb, not lifted. StFstDb::agmlLocalPhi() is already
sitting on #41 with zero consumers -- added in anticipation -- and that is
where it plugs in.

Consequence: the planar-mode PR is NOT "one line plus some fixes". It needs
that rewrite. Scope it deliberately.

Meanwhile the integration branch's FST planar measurement uses the hit's
stored global position projected onto its plane. Self-consistent and correct,
just less precise than re-deriving the position from the strip.

Note also: the 108-sensor mounting-consistency guard does NOT need porting.
Once FST planes come from StFstDb alone there is one source of truth, so the
flag-vs-cache hazard it guarded is structurally gone -- on #41 the invariant
would compare wedgeOrientation() against a placement derived from
wedgeOrientation(), i.e. a tautology.

The number to beat: Primary chi2 ratio 3.86 (4.332 -> 16.737) on pre-17.55 mm
geometry. If the ratio is now near 1, the planar-default PR has its case. If it
is still ~4, the decision reverts to the open choice from 10-01 -- inflate the
FTT measurement sigma with an alignment term in quadrature (mirroring what FST
already does, sigma_total = sqrt((pitch/sqrt12)^2 + delta_align^2)), or finish
the alignment first. akio's recorded preference: understand before inflating,
because a sigma fudge hides the misalignment it absorbs.

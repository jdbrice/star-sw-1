2. THE FINDING: upstream's planar measurement is wrong
------------------------------------------------------

This is the important result of the evening and it is a code finding, not a
measurement.

`createTrackPointFromPlanarMeasurement` on main (and therefore on every PR
branch) builds the in-plane coordinate as

    hitOnPlane[0] = fh->getX();
    hitOnPlane[1] = fh->getY();

A genfit PlanarMeasurement's coordinates are (u,v) measured FROM THE PLANE
ORIGIN. Assigning global x,y is correct only for a plane whose origin lies on
the beam axis, which describes none of ours -- the FTT chamber planes are
centred near x = +-11 cm, y = 9 cm. So every FTT hit would be displaced by its
chamber offset, SILENTLY, because a PlanarMeasurement keeps only the in-plane
components and cannot notice the rest.

It has never fired because the planar branch is unreachable while
kUseSpacePoints is true. It would have fired the moment anyone flipped it, and
it would have looked like bad alignment rather than a bug.

fcstrk11 has the correct form and has had it since planar mode was adopted:

    TVector3 diff = global - plane->getO();
    hitOnPlane[0] = diff.Dot( plane->getU() );
    hitOnPlane[1] = diff.Dot( plane->getV() );

Ported to the integration branch, along with three smaller planar-mode fixes:

  - kUseSpacePoints constexpr -> TrackFitter:useSpacePoints config key, so both
    arms come from ONE build. A comparison across two binaries is not one.
  - EPD hits forced to the space-point path: getPlaneFor() knows only FTT and
    FST, so an EPD hit in planar mode gets a null plane and is dropped.
  - two off-by-one bounds checks, "index > size()" where it must be ">=".
    An index exactly equal to size() passed the guard and read one past the end
    of mFttPlanes / mFstSensorPlanes. Only reachable in planar mode.

Commits: be4ad24772 (the merge), d35ffa641b (the planar fixes).


3. What the integration branch still CANNOT do, and why it is design work
-------------------------------------------------------------------------

It has no complete FST planar decode, and porting one is not possible.

fcstrk11 derives the FST hit position from the sensor's own AGML shape phi
limits -- mFstSensorPhi1/Phi2, mFstSensorRmin/Rmax -- and that machinery reads
FwdGeomUtils::getFstSensorOrigin, which #39 deliberately DELETED. The two
designs disagree at the root:

    fcstrk11   strip -> phi from the AGML sensor shape (geometry-driven)
    #39/#41    StFstDb owns the conventions; FST planes from
               sensorPlacementByIndex(), measurement = ProlateSpacepointMeasurement

The #39/#41 direction is the right one, so the FST strip->phi decode has to be
REWRITTEN against StFstDb, not lifted. StFstDb::agmlLocalPhi() is already
sitting on #41 with zero consumers -- added in anticipation -- and that is
where it plugs in.

Consequence: the planar-mode PR is NOT "one line plus some fixes". It needs
that rewrite. Scope it deliberately.

Meanwhile the integration branch's FST planar measurement uses the hit's
stored global position projected onto its plane. Self-consistent and correct,
just less precise than re-deriving the position from the strip.

Note also: the 108-sensor mounting-consistency guard does NOT need porting.
Once FST planes come from StFstDb alone there is one source of truth, so the
flag-vs-cache hazard it guarded is structurally gone -- on #41 the invariant
would compare wedgeOrientation() against a placement derived from
wedgeOrientation(), i.e. a tautology.

5b. CORRECTION -- this is NOT the comparison the x3.9 came from
---------------------------------------------------------------

I set this run up against the wrong baseline and nearly reported 5a as "the
planar case is made". It is not the same measurement.

The 2026-10-01 campaign's two arms "differ only in NOADD"
(project note: pico_fttadd_20260930 vs control pico_iter2_20260930). That is
fttNoAdd=1 versus fttNoAdd=0 -- FTT hits FOUND BUT NOT ADDED to the track,
versus added. So chi2 4.332 -> 16.737 is the cost of PUTTING FTT HITS ON THE
TRACK, not the cost of representing them as planar rather than space points.

Both arms of 5a have fttNoAdd at its default (false), so both pay that cost
already, which is exactly why the ratio is ~1.

Two things follow:

  - 5a is still a real and useful result: the planar measurement model is
    chi2-neutral, so flipping kUseSpacePoints does not by itself cost chi2.
  - The x3.9 question is UNANSWERED by 5a and is the one that needs
    re-measuring on current geometry. That is the fttNoAdd 1-vs-0 run, section
    5c.

Also do NOT compare the absolute chi2 above to the 10-01 numbers. Primary here
is ~152 against 10-01's 16.737; StPicoFwdTrack::chi2() is raw chi2 and it is
not established that the 10-01 figures were the same quantity rather than
chi2/ndf. The RATIO within one run is what is comparable.

-------------------------------

So quad A station 2 never received the alignment the other three stations did.
Whether that is a genuine zero or a dropped row is akio's and Daniel's call,
but it displaces that pentagon by ~1 cm = 3 strip pitches. Remember we have

One row cannot explain a 10x global inflation on its own, though: quad B is
~5-10 mm off and quad C ~5-10 mm too, consistently. Either the whole alignment
is being applied with the wrong sign/sense, or it is right and something else
is wrong.

5e. What is still unexplained, and how to find it
-------------------------------------------------

Between 2026-10-01 and today, with the SAME hits-off baseline (4.33 -> 4.44)
and the SAME measurement model (both planar), the cost of adding an FTT hit to
a track went from 7.5 to 83.3 units of chi2. Neither the measurement model
(5a, chi2-neutral) nor the DB geometry (5d, <=12%) explains it.

Candidates, in the order I would test them:

  1. THE FTT MEASUREMENT SIGMA. This is the strongest candidate because chi2
     scales as 1/sigma^2, so a factor ~3 reduction in sigma gives exactly the
     factor ~10 observed. Since 10-01 the cluster sigma has been changed --
     there are branches `ftt-cluster-sigma` ("floor the cluster sigma at the
     single-strip resolution") and `ftt-cluster-maxstrip-held` in fcstrk13, and
     the 10-01 note records cov[0][0] = clu->sigma()^2 with the unmeasured
     direction maxStripLength^2/12 and NO alignment term. If the floor moved
     down, every FTT hit got "more precise" on paper while the real
     track-to-hit scatter did not improve, and chi2 must rise by the square.
     TEST: print the FTT measurement covariance for a few hits today and
     compare against the 0.924 mm floor the 10-01 note quotes.

  2. The 17.55 mm strip-offset fix (10-24). It moved FTT hit positions by
     17.55 mm and was confirmed on data to 0.44 mm over 25 coordinates, so it
     should have IMPROVED things. But it is the largest single change to FTT
     hit positions in the window and deserves an explicit on/off.

  3. The FTT data windows pushed 10-16, which changed production's time cut
     from [-65,100] to one bunch crossing. My runs use fttTimeCutMode=0, i.e.
     the DB windows; the 10-01 campaign predates them. Suspicious detail: the
     number of ADDED hits went UP (1.90 per track against 1.650), which is not
     what a tighter time window should do. Worth understanding on its own.

  4. A bisect of fcstrk11 between the 10-01 campaign commit and today, using
     this 60-event A/B as the probe. It is cheap now -- 4 minutes per arm --
     and it is the method that cannot miss.

Until this is understood, the planar-mode-default PR has no physics case to
quote, and that is the honest position. Note carefully that it is NOT an
argument against planar mode: 5a shows the measurement model is chi2-neutral.
Whatever this is, it afflicts space-point mode equally, which means it is a
pre-existing problem in how FTT hits are weighted, not a planar-mode problem.

Caveat on all of 5a-5e: these runs use the macro defaults, so
applyFstGapFix=false where production uses GEOFIX 1,0,0. Identical in every
arm, so the ratios hold, but the absolute numbers are not production-configured.

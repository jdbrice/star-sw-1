How to check out, compile and run branch akio202607
Last updated 2026-11-09.

Covers two different jobs:

  the AFTERBURNER   real data, MuDst in -> picoDst + residuals out.
                    Setup .. Run Afterburner .. Check the afterburner output.
  SIMULATION        generate a sample and run forward tracking on it.
                    Simulation .. Check the reco log.

They use DIFFERENT geometry lanes and the lanes are not interchangeable:
   afterburner Run-22 is dev2022sm + sdt20211112.000004, 
   Run-24 is y2024 +sdt20240622
   simulation is y2022c + sdt20211112.000004 and ideal. 
Nothing warns you if you cross them except the one wedge-mounting error quoted later.

*** Setup

singularity exec -e -B /direct -B /star -B /gpfs -B /sdcc/lustre02 /cvmfs/star.sdcc.bnl.gov/containers/rhic_sl7.sif csh

No -B /afs. /afs is gone -- inside the container it is an empty directory, and
binding it achieves nothing. Everything that used to live under
/afs/rhic.bnl.gov/star is at /star/nfs4/AFS/star, which $STAR already points
at, so nothing is missing. If a macro fails on a path under /afs, the macro is
stale, not the environment.
stardev
setenv TESTDIR <your dir>
mkdir -p $TESTDIR
cd $TESTDIR

Use a disk with room, NOT your home directory: the checkout is ~700 MB and the
build adds ~1.5 GB. If quota runs out mid-checkout, git leaves no .git/index
and a random subset of directories, while git log still shows the right commit.

*** Checkout

git clone --no-checkout -b akio202607 git@github.com:jdbrice/star-sw-1.git .
git config core.sparseCheckout true
cp /star/u/akio/fcstrk11/star-sw-fwd/sparse-checkout.akio202607 .git/info/sparse-checkout
git checkout akio202607
git log --oneline -1

Do NOT run "git sparse-checkout init"

cat .git/info/sparse-checkout
ls StarDb/Geometry/fst | wc -l

The first must show the /StRoot/StFcs* ... patterns, not "/*" and "!/*/" --
those two mean sparseCheckout was initialised rather than copied, and you have
the whole tree.

The second must be 8 (fstOnTpc, fstSensorOnWedge, fstWedgeOnHss and hssOnFst,
each at 20211110 and 20211112). It said 12 until 2026-11-11, which was wrong
for everyone but me: my tree also holds a 20211111 lane that was never
committed and that nothing references. If you have 12, four of them are your
own untracked files.

StarDb is the one data directory the build genuinely needs: St_db_Maker
searches ./StarDb before $STAR/StarDb, and without it a job falls back to
hardcoded geometry and looks like "the tables do nothing".

WHICH TABLES COME FROM WHERE (updated 2026-11-11 -- this branch now matches
production):

  Geometry/ftt/fttHardwareMap, fttDataWindowsB   MySQL
  Geometry/ftt/stgcOnTpc                         MySQL
  Geometry/ftt/stationOnStgc                     MySQL
  Geometry/ftt/pentOnStation                     MySQL

The branch used to ask for Geometry/stgc, which is NOT a DB namespace, so those
three could only come from ./StarDb/Geometry/stgc. The rename to Geometry/ftt
landed upstream as PR #20 (the StgmGeo1.xml <Misalign> paths) plus #23 (the
code), and was followed here on 2026-11-11.

Content did not change. The ftt tables carry the same 16 rows as the stgc ones,
re-stamped onto Gene's -15 lane (20211015.* in place of 20211112.*), compared
row by row first, and the chain reproduces the same numbers afterwards:
chamber z agreement 9.15527e-08 cm, in-plane worst |dxy| 1.95246 cm. Both
unchanged to every digit.

Verified by moving ./StarDb/Geometry/stgc aside for one event: it still reports
"quadrant offsets built from AGML placeholder + DB survey tables". Before the
rename the same test fell back to the hardcoded offsets.

CONSEQUENCE: ./StarDb/Geometry/stgc is now DEAD on this branch -- nothing reads
Geometry/stgc. Left in place rather than deleted, because those files are also
the record of how the Run 22 constants were derived. Do not edit them expecting
an effect.

REBUILDING fGeom AFTER THIS: the <Misalign> paths live in StgmGeo1.xml, which is
compiled into the geometry library, so rebuild it properly -- cons
+StarVMC/Geometry first (that directory owns the generator), then +StarGeometry
and +xgeometry. A green cons does NOT mean your XML is in the library. Caches
built before 2026-11-11 stay valid, because the table content is identical.

*** Compile

cons +StarVMC |& tee cons.geom.log
cons |& tee cons.log
grep -niE "error|Error 1|undefined reference" cons.log | head -40

StChain MUST be among what you built, and it is worth checking explicitly:

  strings .$STAR_HOST_SYS/lib/libStChain.so | grep -c '^y2022c$'     # want 1

If that is 0, or the file is missing, run "cons +StChain" and check again.
WHY THIS ONE MATTERS. The y2022c geometry tag is registered in
StRoot/StChain/GeometryDbAliases.h, which is compiled into libStChain.so and
read back by StMaker::AliasGeometry(). DEV ships its own libStChain.so, and
DEV's copy of that header does NOT have y2022c. So a tree that does not
rebuild StChain silently loads DEV's table and BFC answers

  QA :INFO  -  Invalid Option y2022c. !! ABORT !!

which reads like a missing geometry file and is not one: Geometry.y2022c.C,
StarGeo.xml and xgeometry.age can all be present and correct, and it still
aborts. The same applies to any tag added on this branch.

*** Build fGeom.root

build_geom_misalign.C(geomtag, sdt, misalign, label)
generates fGeom.<geomtag>.misalign<N>.sdt<sdt>[.<label>].root

An existing output file is never overwritten -- the macro says ALREADY EXISTS
and stops. Run it from the TOP of the checkout, so the local StarDb/Geometry
survey tables are among the ones St_db_Maker can see.

Note what "picks up the local tables" does and does not mean. St_db_Maker pools
the .C files from every search directory and takes the LATEST timestamp at or
before the sdt you ask for -- the directory is irrelevant, and ./StarDb has no
priority (StBFChain puts $PWD/StarDb fourth in the list). A local file only
wins if its timestamp is later than every other entry for that table, the ones
in $STAR included. See StRoot/StFstDbMaker/macro/README.

** run22 -- this is the one fGeom.root points at

root4star -l -b -q 'build_geom_misalign.C("dev2022sm","20211112.000004",1)' |& tee build_geom.run22.log
ls -la fGeom.dev2022sm.misalign1.sdt20211112.000004.root
rm -f fGeom.root
ln -s fGeom.dev2022sm.misalign1.sdt20211112.000004.root fGeom.root

The sdt has to be LATER than the local StarDb tables or they are not read at
all. StarDb/Geometry/fst holds slots at 20211110/11/12, all .000001, so
20211112.000004 takes the 20211112 lane, and anything earlier excludes the
local tables entirely. That is the whole reason for the trailing .000004.

Older notes name sdt20211015.000003 here. That lane sits BEFORE every local
table, so it builds DB-only ideal geometry -- a different cache, not an older
spelling of this one. Use it only if ideal geometry is what you want.

** run24

root4star -l -b -q 'build_geom_misalign.C("y2024","20240622",1,"iter2")' |& tee build_geom.run24.log
ls -la fGeom.y2024.misalign1.sdt20240622.iter2.root

iter2 is the newest Run-24 cache on disk (2026-10-24) and the one to use unless
you are reproducing an older campaign. The earlier ones are still there under
pre-convention names -- fGeom.y2024.iter1.sdt20240622.root and
fGeom.y2024.seeded.sdt20240622.root -- and runab's own header comment still
names fGeom.y2024.sdt20240622.root, older again. The LABEL is the only record
of which iteration a cache holds, so trust the label, never the sdt.

Expect ~380 kB and a "=== build_geom_misalign done ===" block naming geomtag,
sdt, misalign and how many FCS volumes were replaced with air (15).

Always pass a label for run24. sdt does NOT identify the iteration: three run24
caches exist, all at sdt20240622, differing only in which
pentOnStation.20231210.* was latest when each was built. sdt20240622 today
gives iteration 1.

For now, I do not symlink the run24 cache to fGeom.root. Pass it as runab's
11th argument instead, so a run22 run cannot silently pick it up.

** SIMULATION uses a third lane -- y2022c, ideal. Do not reuse either of these two
caches for MC; see the simulation section below.

Note StRoot/StFwdTrackMaker/macro/build_geom.C is a DIFFERENT, much older macro
that reproduces neither cache (sdt20211016, no misalign, no arguments). Do not
confuse the two.

*** Run Afterburner

mkdir -p out
mkdir -p scratch
setenv SCRATCH $TESTDIR/scratch

./script/runab \
      /star/data20/reco/production_pp500_2022/ReversedFullField/DEV_fwd_test2/2022/081/23081001 \
      st_fwd_23081001_raw_0000002.MuDst.root \
      $TESTDIR/out \
      0  1  1,0,0  2  -1,3  2,0,0  200 \
      |& tee runab.log

For run24 use
      0  1  1,0,0  2  -1,3  2,0,0  200  fGeom.y2024.misalign1.sdt20240622.iter2.root
for the last line, to specify the run24 fGeom file.

Arguments, in order:

    INPUTDIR BASE OUTDIR ALIGN MAGFIELD GEOFIX FTTTIMECUT FTTWINDOW DIAG MAXEVT [GEOM]

      ALIGN       0      no StFwdAlignmentMaker
      MAGFIELD    1      take the field from the MuDst's own stamp
      GEOFIX      1,0,0  applyFstGapFix only, correct for all current MuDst
      FTTTIMECUT  2      calibrated time
      FTTWINDOW   -1,3   dbcid ticks relative to the per-VMM anchor
      DIAG        2,0,0  FST-blind diagnostic on Primary tracks, hits still added
      MAXEVT      200
      GEOM        omitted, so the fGeom.root symlink. Specify for run24.

$SCRATCH must exist and should be EMPTY -- runab symlinks .$STAR_HOST_SYS and
StRoot into it and copies the 180 MB MuDst there.

*** Check the afterburner output

ls -la out/ out/residual/ out/blinddiag/

Expect out/<base>.picoDst.root, five out/residual/<base>.FwdDetResidual_*.root
(Global, BLC, Primary, BLCVtx, FCSConstrained) and one
out/blinddiag/<base>.fwd_blind_diag.root. runab prints a WARNING line if any
copy-back got nothing.

cat $SCRATCH/fwd_key.log

Must show StFttDb reading the DB tables and the per-run FTT anchors.
"falling back" there means StarDb was not picked up, or this run has no
fttDataWindowsB entry stamped for it -- only 58 runs are calibrated -- and
StFttDb::getTimeCut went to its built-in [-65,100].

A line reading "LOADING DATA WINDOWS FROM LOCAL FILE" is the opposite problem:
a leftover fttDataWindow/fttDataWindow.<run>.txt in the working directory is
overriding the database. That override exists for calibration work only --
remove or rename the file to use the DB.

*** Simulation: generate a sample and run forward tracking on it

Everything below runs from the TOP of the checkout. That is not cosmetic:
LD_LIBRARY_PATH contains the RELATIVE entry .$STAR_HOST_SYS/lib, so from any
other directory you silently link against $STAR's libraries instead of yours.

Generation and reconstruction must agree on the geometry, and nothing checks
it for you except the one error quoted at the end of this section. Agreement
means all three of:

    the AGML tag          y2022c
    the DB lane (sdt)     sdt20211112.000004
    the fGeom cache       built from that tag and that lane

Use y2022c, not y2024. y2022c is the tag PR28 wired to FSTMv2m, i.e.
fstmconfig=2, the as-installed FST wedge mounting, which is what
StFstDb::fstmConfig() returns. Do NOT use dev2022sm for generation: it is the
SIMPLIFIED geometry and produces no FST g2t hits at all, so the sample has
nothing to track (0 FST hits in every event, and it looks like a tracking bug).

Build the matching cache once. misalign 0, because AGML applies no
misalignment in simulation, so an ideal cache is what matches GEANT:

  root4star -l -b -q 'build_geom_misalign.C("y2022c","20211112.000004",0)'
  ls -la fGeom.y2022c.misalign0.sdt20211112.000004.root

Generate. Lambda into the forward acceptance, GEANT doing the decay:

  root4star -l -b -q 'StRoot/StFwdTrackMaker/macro/sim/lambda.C(10,20261109,"gun","sdt20211112.000004","y2022c")'

  -> fwd_lambda_gun.fzd, and one line per event giving the Lambda pt, eta, p
     and the mean decay length beta*gamma*c*tau it implies. At the default
     pt 0.3-1.5 and eta 2.5-4.0 that is ~96 cm on average, against an FST at
     z = 150-180 cm, so most Lambdas decay BEFORE the first disk. Mode "ps"
     instead of "gun" puts both daughters at the primary vertex with zero
     decay length -- a control, not a Lambda sample. See the header of
     lambda.C.

Or a single-particle gun, same lane (gen.C holds the lane in genGeomTag and
genSdt now, defaulting to the pair above):

  root4star -l -b -q 'StRoot/StFwdTrackMaker/macro/sim/single_particle_gun.C(10,541512,"mu-",1,1.0,1.01,2.5,4.0)'

Reconstruct. The lane and the cache are ARGUMENTS of sim() now (2026-11-12),
so one call does it, in the order (file, n, sdt, geomCache):

  root4star -l -b -q 'StRoot/StFwdTrackMaker/macro/sim/sim.C("fwd_lambda_gun.fzd",10,"sdt20211112.000004","fGeom.y2022c.misalign0.sdt20211112.000004.root")'

Pass both. An omitted argument leaves the file-scope default, and the defaults
are the unaligned lane (sdt20211016) and the fGeom.root symlink -- Run-22 DATA
geometry -- so a y2022c sample then reconstructs against the wrong geometry
without one word of complaint in the log.

sim_lambda.C still works and forwards here, but it is DEPRECATED and takes its
arguments in the other order, (n, file, sdt, geomCache). Nothing in it was ever
Lambda-specific. The other sim.C toggles -- RunFcsChain, UseConstBz, RaveMethod
and the rest -- are still globals and still need LoadMacro, set, then call.

*** Check the reco log, in this order

  grep "disagree about the wedge" reco.log

Must print NOTHING. If it fires, the fGeom cache and StFstDb::fstmConfig()
disagree about the FST wedge mounting phase and the planar decode mirrors a
local phi the geometry did not -- wrong by up to half a wedge. The y2024
caches trip this today; y2022c does not.

  grep "geom cache" reco.log

Must name the cache you meant. Left at the default it is the fGeom.root
symlink, which points at a Run-22 cache.

  grep "Fwd Tracking Found" reco.log

Seeds per event, and the seed efficiency against McTracks with >2 FST hits.
Zero FST hits in every event means the generation geometry, not the tracker.

  grep "FwdVertexFinding" reco.log

One line per event: how many RAVE vertices, from how many global tracks, and
each vertex's id, z and track count. If tracks were dropped before RAVE
(null or unconverged fits) a second line says how many.

*** Forward vertex finding: rare, and single-track (2026-11-09)

Forward vertices come out at about 0.03 per event, which is what they did in
June, so nothing has regressed. But every one seen carries a SINGLE track,
which is not a vertex, and no multi-track vertex has been formed at all.

Measured: ~33 events of st_fwd_23081001_raw_0000002.MuDst.root through the
ordinary afterburner, 304 converged global tracks offered to RAVE across them,
events carrying 8 to 15 each -> 1 vertex, nTrk=1. MC agrees: 10 Lambda events
and a four-muon gun gave none, a single-muon gun gave 1 in 10 events, nTrk=1.

What has been ruled out:

  not the track selection   the tracks reach RAVE intact. The log line says how
                            many were dropped as null or unconverged before the
                            hand-over, and in MC that is zero. (In real data a
                            few per event have a null mTrack -- up to 9 of 23 --
                            which is worth understanding separately, but the
                            remaining 14 converged ones still give no vertex.)
  not the method            "kalman", "avr" and "mvf" all give 0 on the same
                            tracks.
  not the beam constraint   TrackFitter:fwdVertexBeamConstraint changes nothing,
                            except that a 1-track event can then make a
                            meaningless 1-track "vertex".
  not our flags             TrackFitter:fstNoAdd and fttNoAdd are both false by
                            default and announce themselves in the log when on;
                            neither was set. findFwdVertices was called in every
                            event. (Note sim.C's comment on setFttHitSource(1)
                            used to read IGNORE -- the enum is
                            {GEANT=0, STEVENT, MUDST, IGNORE}, so 1 is STEVENT
                            and the FTT hits were always being loaded.)
  not the warm start        TrackFitter:warmFitFstTightSigma off vs on, same 10
                            real-data events: 0 vertices either way.
  not findFwdVertices       that function, the default-constructed factory and
                            useBeamConstraint=false are BYTE-IDENTICAL to
                            star-bnl/main (last upstream touch Daniel's #731,
                            2025-09-11). That does NOT clear our branch: we
                            change the fitter, the field adapter and material
                            effects, all of which change the track STATES RAVE
                            is handed. The identical-code argument was
                            overstated when first written here.

NOT A REGRESSION, AND COUNT YOUR EVENTS BEFORE SAYING OTHERWISE.

The June baseline in debug/index.html is 23 FwdVtx entries in 1000 EVENTS of a
single-electron gun -- 0.023 vertices per EVENT. Forward vertices have always
been rare. Ten events therefore expect 0.2 of them, so a zero in ten events is
not evidence of anything, and an earlier version of this section drew exactly
that unfounded conclusion.

With real statistics the rate matches June:

    real data, ~33 events, 304 global tracks offered  ->  1 vertex
    0.03 per event, against 0.023 per event in June 2026

So nothing has broken since June. The warm-start A/B in todo.txt item 4 has
the same sample-size problem and settles nothing either; rerun it at 1000
events on the same single-particle gun the June number used.

WHAT IS ACTUALLY WRONG is not the rate, it is the vertices themselves:

    every forward vertex seen so far has nTrk = 1

A single-track "vertex" is not a vertex. Across ~33 real-data events, 304
converged global tracks offered to RAVE, and events carrying 8 to 15 of them,
not one MULTI-track vertex was formed. That observation does not depend on the
per-event rate, and it is the thing that blocks a Lambda study: Lambda -> p pi
needs a two-track vertex.

Curiosity worth chasing: the vertex id came back as 2 every single time -- in
MC, in the beam-constraint test, and in real data. An id that never varies is
consistent with getId() not being a per-event index at all (see the vertex
index section below).

With TrackFitter:raveVerbosity raised, RAVE says it itself:

    [rave::VertexFactory] produced 0 vertices from 5 tracks.

Where it fails is INSIDE RAVE, not in what we hand over (2026-11-09):

  - The field is right. genfit::GFRaveMagneticField::inTesla, called directly
    against a known ConstField, returns exactly 0.1 x the kGauss value. The
    units are correct and that suspect is dead.
  - What we hand over is finite. Every track's 6D position, momentum and 6x6
    covariance was screened for non-finite entries before the hand-over: zero
    offenders in 10 real-data events, so the NaN is not ours.
  - RAVE still trips its own guard. With a method that reports, it says
        [rave::VertexFactory] when trying to fit:
        rave/CheckedFloat.h: The assigned floating point number cannot be used.
    CheckedFloat throws on any non-finite number, and ONE bad track aborts the
    whole fit, taking the good tracks with it. At verbosity 0 none of this
    appears -- findVertices just returns an empty list.
  - Driving rave::VertexFactory DIRECTLY, with synthetic tracks and no GenFit
    and no STAR code at all, the "default" and "kalman" methods return 0
    vertices even for an easy CENTRAL two-track pair from the origin; "avr"
    returns one, but places it at z=348 cm for two tracks that start at the
    origin. "mvf-smoothing:1" prints the internals:
        [TwoTrackMinimumDistance] comparing track with itself!
        [TwoTrackMinimumDistance] Computation HelixHelix::CAIR failed.
        [rave::VertexFactory] when trying to fit: BasicSingleVertexState::invalid
    HelixHelix::CAIR is RAVE's helix-helix closest approach, which is exactly
    the step that goes ill-conditioned for near-parallel tracks.

So the next move is one of:

  1. Read the GenFit and RAVE sources. cvmfs ships headers and compiled
     libraries only, but both are public and the commit is pinned --
     genfit-b496504a, rave-2020-08-11. GFRaveConverter and VertexFactory are
     the two files worth reading, since the failure is now known to be in code
     we cannot see here.
  2. Ask Daniel whether forward vertex finding has EVER produced a vertex.
     Given the code is identical to main, the honest prior is no.
  3. Stop using RAVE for this. Forward tracks are near-parallel, which is the
     worst case for a general helix-helix vertexer but an easy case for a
     purpose-built fit: minimise the weighted sum of squared distances to a
     common point along z, seeded from the pairwise DCA. That is a small amount
     of code and avoids the whole conversion layer. For a Lambda study this may
     simply be the right answer rather than a workaround.

One thing seen only in real data and NOT the cause: up to 8 or 9 of 23 global
tracks per event carry a null mTrack and are dropped before RAVE. Worth
understanding separately -- the remaining converged ones are plenty.

Consequence: doSecondaryTrackFitting never runs, no
kForwardVertexConstrained tracks are ever made, and StFwdTrack::vertexIndex()
is always 0. Any Lambda or secondary-vertex study has to fix this first.

The knobs for the next person, all config keys on StFwdTrackMaker:

  TrackFitter:raveVerbosity         int, 0 default. At 0 RAVE says NOTHING,
                                    including nothing about why it rejected
                                    every track. Raise it first.
  TrackFitter:raveMethod            "" default (GenFit's own); "avr",
                                    "kalman", "mvf" are the ones tried.
  TrackFitter:fwdVertexBeamConstraint  false default. Diagnostic only: it
                                    biases a secondary vertex onto the
                                    beamline, which is what you are measuring.

From sim.C these are the globals RaveVerbosity, RaveMethod and
UseFwdVertexBeamConstraint.

Next suspect, not yet checked: the perigee parameters RAVE is handed. A
forward track sits within ~10 degrees of the beam, so its perigee relative to
the beamline is nearly degenerate and its covariance along z is huge; the
"blown-up state pT=0.0022" warnings and the "TDecompChol::Decompose() : matrix
not positive definite" error in the same logs point the same way.

*** The vertex index is 5 bits, and truncates silently

StFwdTrack::setVtxIndexAndTrackType packs 5 bits of vertex index and 3 of
track type into one byte, and pack5and3 does A &= 0x1F. So anything above 31
wraps with no warning. StPicoFwdTrack holds the same packed byte.

What is stored is GenfitTrackResult::mVertexIndex, and for a forward-vertex
track that is vtx->getId() -- the id of the rave::Vertex, NOT an index into
the event's vertex list and NOT guaranteed 0-based. The one vertex this dry
run ever produced came back with id=2 in an event holding a single vertex,
which is already enough to show the two are not the same thing.

So "are 5 bits enough" cannot be answered from the number of vertices per
event. It depends on what getId() counts, and that has to be established on a
sample where vertex finding actually works. Until then, do not widen the
field: if getId() turns out to be a running counter the fix is to store the
INDEX (the position in mFwdVertices, which is bounded by the track count),
not to spend more bits on an id that carries no meaning downstream.

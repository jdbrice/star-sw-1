Forward Lambda MC and GenFit/RAVE vertex finding

akio202607, 2026-11-09. A 10-event dry run of the whole path a Lambda → pπ− vertex study has to take: generate into the forward acceptance, run forward tracking, count the RAVE vertices.

Headline

Forward vertex finding returns zero vertices, for every event. Not a Lambda problem — four muons thrown from a common (0,0,0) give zero vertices too. doSecondaryTrackFitting therefore never runs, no kForwardVertexConstrained track is ever made, and StFwdTrack::vertexIndex() is always 0. This has to be fixed before a Lambda study can begin.

The 10 Lambda events

One Lambda per event, flat in pT 0.3–1.5 GeV/c and η 2.5–4.0, handed to GEANT3 which transports and decays it. Mean Lambda momentum 13.6 GeV/c, so a mean decay length βγcτ = 96 cm against an FST at z = 150–180 cm: most decay before the first disk, which is what a displaced-vertex study wants.

Seed finding itself is fine: where the daughters reach the FST, efficiency against McTracks with >2 FST hits is 1.0, and the three events with the full p–π pair give exactly 2 seeds and 2 global tracks.

Where it fails

Not in the hand-over. The tracks passed to RAVE are all non-null and all have converged fits, and with RAVE's own verbosity raised it says so itself:

StFwdTrackMaker:INFO  - FwdVertexFinding: RAVE method left at GenFit's default, verbosity 3
[rave::VertexFactory] produced 0 vertices from 5 tracks.
StFwdTrackMaker:INFO  - FwdVertexFinding: 0 RAVE vertices from 5 global tracks

What was ruled out, all on the same tracks:

triedresult
Track multiplicity 1, 2, 3, 4, 50 vertices, except rare 1-track "vertices"
Four muons from a common (0,0,0)0 vertices
RAVE method kalman, avr, mvf0 vertices, all three
Beamspot constraint onno change (a 1-track event can then make a 1-track vertex)
Null / unconverged tracks reaching RAVEnone — not the cause

Next suspect, not yet checked: the perigee parameters RAVE is handed. A forward track lies within ~10° of the beam, so its perigee relative to the beamline is nearly degenerate and its covariance along z is enormous. The same logs carry addFttHits: skipping blown-up state pT=0.0022 and TDecompChol::Decompose() : matrix not positive definite, which point the same way.

The vertex index is 5 bits, and the question is not about counting

StFwdTrack::setVtxIndexAndTrackType packs 5 bits of vertex index and 3 of track type into one byte, and pack5and3 does A &= 0x1F — anything above 31 wraps with no warning. StPicoFwdTrack carries the same packed byte.

What gets stored is vtx->getId(), the id of the rave::Vertex. That is not an index into the event's vertex list and not guaranteed 0-based: the single vertex this dry run ever produced came back as id=2 in an event that held exactly one vertex.

So "are 5 bits enough" does not follow from the number of vertices per event. It depends on what getId() counts, and that can only be established on a sample where vertex finding works. If it turns out to be a running counter, the fix is to store the index — the position in mFwdVertices, bounded by the track count — not to spend more bits on an id that carries no meaning downstream.

Three traps on the way in, now fixed

  • gen.C did not run at all. Its macro path was a hardcoded list ending in a dozen /afs/rhic.bnl.gov/... directories, and SetMacroPath replaces the path, so the working $STAR entry went with it. Every gun built on it died at macro bfc.C not found in path. Built from $STAR now.
  • Geometry has to match on three things at once — AGML tag, DB lane (sdt), and the fGeom cache — and only one of them is ever checked. Use y2022c + sdt20211112.000004: y2022c is the tag wired to FSTMv2m, i.e. the as-installed FST wedge mounting that StFstDb::fstmConfig() returns. A y2024 cache trips the consistency check: 
    ERROR - FST geometry and StFstDb disagree about the wedge mounting: 108 of 108
sensors ... The planar decode will mirror local phi that the geometry did not
    and dev2022sm is the simplified geometry, which yields no FST g2t hits at all — 0 hits in every event, looking exactly like a tracking bug.
  • The vertex count was invisible. Every vertex log line sat behind verbose, and the count behind kProfile — both compile-time false, so the number could not be seen without editing and rebuilding, and StFwdFitQAMaker's mNumFwdVertices histogram was always empty. One INFO line per event now, always.

Running it

From the top of the checkout — LD_LIBRARY_PATH holds the relative .$STAR_HOST_SYS/lib, so anywhere else links against $STAR instead of your build.

# once: the cache that matches the generator (misalign 0 -- AGML applies none in sim)
root4star -l -b -q 'build_geom_misalign.C("y2022c","20211112.000004",0)'

# generate 10 Lambda into the forward acceptance, GEANT does the decay
root4star -l -b -q 'StRoot/StFwdTrackMaker/macro/sim/lambda.C(10,20261109,"gun","sdt20211112.000004","y2022c")'

# reconstruct
root4star -l -b -q 'StRoot/StFwdTrackMaker/macro/sim/sim_lambda.C(10,"fwd_lambda_gun.fzd","sdt20211112.000004","fGeom.y2022c.misalign0.sdt20211112.000004.root")'

# then, in this order
grep "disagree about the wedge" reco.log   # must print nothing
grep "geom cache"              reco.log   # must name the cache you meant
grep "Fwd Tracking Found"      reco.log   # seeds and seed efficiency
grep "FwdVertexFinding"        reco.log   # vertices, and what was dropped

lambda.C has a second mode, "ps", which decays the Lambda in the macro and pushes both daughters as primaries — zero decay length, by construction. It is a control for what RAVE does with a pair that really comes from one point, not a Lambda sample.

The full recipe, the log checks and the open RAVE knobs (TrackFitter:raveVerbosity, TrackFitter:raveMethod, TrackFitter:fwdVertexBeamConstraint) are in howto_akio202607.txt.

What we can and cannot recover from a production MuDst
akio, 2026-09-28, for Jerome

Question: if MuDst production starts tomorrow WITHOUT any of our June/July/September
changes, what can we still fix afterwards by reading the MuDst and running the
afterburner, and what is baked in?

SHORT ANSWER
------------
Exactly ONE thing is unrecoverable: FST CLUSTERING. Everything else we did this
summer can be redone on top of a production MuDst.

And it has a one-option fix. FST raw hits are already supported in the MuDst; they
are simply switched off by default:

    StMuDstMaker.cxx:1265    if (IAttr("fstMuRawHit")) { ... }
    BigFullChain.h:1572      {"fstMuRawHit", "", "", "CMuDST,fstEvtRawHit", ...
                              "Store FST Raw Hit in MuDst", kFALSE}

Turning that option ON in the production chain makes FST fully recoverable too, and
it is the single highest-value thing to ask for before tomorrow. FTT already writes
its raw hits unconditionally, so this only brings FST up to what FTT already does.


THE THREE ITEMS, CHECKED IN THE CODE
------------------------------------
1. FTT time offsets and cuts -- RECOVERABLE. Confirmed.
   The MuDst stores FttRawHit, FttCluster and FttPoint (StMuArrays.cxx:33), and the
   raw-hit fill is unconditional (StMuFttUtil::fillMuFttRawHits, called from
   fillMuFtt -- no IAttr guard, unlike FST). StMuFttRawHit keeps bcid, dbcid and tb,
   which is the full timing. So the afterburner can re-run StFttClusterMaker with any
   time cut or per-VMM calibration, which is exactly what our SetTimeCut(mode,min,max)
   already does. Nothing about FTT timing is lost.

2. Not feeding 16-strip-wide FST clusters into tracking -- RECOVERABLE. Confirmed,
   with one caveat.
   StMuFstHit keeps getNRawHits(), getNRawHitsR() and getNRawHitsPhi(), so cluster
   width is visible per hit and we can cut on it in the afterburner.
   CAVEAT: we can DISCARD a wide cluster, we cannot SPLIT it back into good hits,
   because the strips that went into it are gone. So this is a veto, not a repair --
   we lose those hits rather than recovering them.

3. FST r-skipping clustering, and the hit placed at the largest R -- NOT RECOVERABLE.
   Confirmed, both halves, in StFstClusterMaker/StFstScanRadiusClusterAlgo.cxx:
     - line 78 comment and loop: "put all raw hits in one phi strip to rawHitsToMerge"
       -- every hit sharing a phi strip is merged with NO adjacency requirement in R,
       so non-adjacent r-strips are clustered together.
     - lines 129-136:  meanRStrip = 0; maxRStrip = 0;
                       for (...) { if (tempRStrip[i] > maxRStrip) maxRStrip = ...;
                                   meanRStrip = maxRStrip; }
       -- the cluster R is the LARGEST r-strip in the cluster. Not charge-weighted,
       not the seed strip, not the smallest R.
   The MuDst keeps only the RESULT (meanRStrip, meanPhiStrip), not the strips that
   produced it, so neither the merge decision nor the true R can be reconstructed.


WHY EVERYTHING ELSE SURVIVES
----------------------------
The MuDst keeps FST hits as STRIP INDICES, not only as a global xyz:

    StMuFstHit: mMeanRStrip, mMeanPhiStrip, plus disk/wedge/sensor and the raw-hit
    counts (StMuFstUtil.cxx:115 rebuilds StFstHit from exactly these)

That is the reason our whole class of FST POSITION bugs is recoverable. The afterburner
in planar mode rebuilds the global position from (rStrip, phiStrip) on the AGML sensor
plane, so it never uses the production global xyz at all. Specifically recoverable:
  - the wedge front/back flip and the per-wedge mirror
  - the 1 degree outer-sensor gap sign
  - every hit getting the disk-centre z instead of its true per-sensor z
  - the sensor -> FTUS plane mapping
  - the survey being applied and then exactly cancelled in StFstHitMaker
All of these are re-derived downstream from the strip indices plus geometry.

Likewise recoverable on the FTT side, because FttRawHit is always written: the per-VMM
time calibration, the data-window/time cut, maxStripLength, the cluster and point
construction, the X<->Y assignment, and all per-quadrant geometry offsets (those now
come from the DB survey tables, not from the MuDst at all).

Everything else we touched since June is simulation-side (StFstSimMaker,
StFttSimHitMaker, StFttChargeSharingMaker) or MC-gated (StFcsDb beamline DB read), and
does not affect real-data production.


IS THE OPTION ACTUALLY USABLE? PARTLY -- THE WRITE PATH ONLY
------------------------------------------------------------
Checked rather than assumed, because an option existing is not the same as it working.

WORKS (by inspection):
  - both options exist, both default kFALSE:
        BigFullChain.h:1571  fstEvtRawHit  "Store FST Raw Hit in StEvent"
        BigFullChain.h:1572  fstMuRawHit   "Store FST Raw Hit in MuDst"  (needs CMuDST,fstEvtRawHit)
  - StFstRawHitMaker.cxx:409-414 creates/fills StFstEvtCollection, so the StEvent side is real
  - StBFChain.cxx:687 passes the attribute to StMuDstMaker
  - StMuDstMaker.cxx:1264-1269 picks up ev->fstEvtCollection() and
    StMuFstUtil::fillMuFstHits writes every raw hit into the MuDst

DOES NOT WORK -- nothing can read it back:
  - StMuFstUtil::fillFst(), the MuDst -> StEvent restore, calls ONLY fillFstHits().
    Raw hits are never restored; the function does not even take an StFstEvtCollection.
  - nothing in StRoot or in $STAR reads StMuFstRawHit, StMuFstCollection::getRawHit()
    or getRawHitArray(). There is no consumer anywhere.

So switching the option on tomorrow WRITES the data but nothing can use it yet. Two
pieces of code are missing, and both are ours to write:
  (a) read the raw hits back -- either extend fillFst() to rebuild StFstEvtCollection,
      or read StMuFstCollection directly in the afterburner;
  (b) re-run StFstClusterMaker on them in the afterburner.

THE POINT: (a) and (b) can be written next week. The DATA cannot be written next week.
That asymmetry is the whole argument for turning the option on tomorrow.

AND THERE IS AT LEAST ONE REAL BUG IN THE DECODE. akio recalls an FST hit bug that
filled garbage into the raw hits and made them unusable; we did not have time to pin the
exact historical commit, but here is one concrete defect still in the code today.

StMuFstRawHit stores only two location words, mChannelId (electronics) and mGeoId
(geometry), and every other accessor derives from them. The derivations split correctly:

    getRdo/getArm/getApv/getChannel   use mChannelId   (electronics)  -- correct
    getDisk/getWedge/getPhiStrip/getRStrip  use mGeoId (geometry)     -- correct

but StMuFstRawHit.cxx:68

    unsigned char StMuFstRawHit::getSensor() const
    {
        int strip = mChannelId % (inner*stripsInner + outer*stripsOuter);   <-- mChannelId
        ...

uses mChannelId with the GEOMETRY strip layout. Electronics and geometry ordering are
different mappings, so getSensor() does not agree with getRStrip()/getPhiStrip() for the
same hit. Whether that is the whole of the garbage akio remembers or only part of it, it
is wrong as written and has to be fixed before the branch is usable.

Supporting evidence that this was never exercised: FstRawHit is empty in every MuDst we
looked at, and the feature came in as a single commit, f38e654361 "Add FST raw hits in
StEvent and StMuDst (#378)", with no follow-up fix commits. The write side itself does
look structurally sound -- StFstRawHitMaker.cxx:538-539 and :594-596 do set both
channelId and geoId -- so the defects we can see are on the decode/consume side, which is
the side we would be writing anyway.


WHAT IT COSTS IN DISK SPACE -- NOW MEASURED, NOT ESTIMATED
-----------------------------------------------------------
UPDATE 2026-09-29: the option was actually run. A MuDst was written from real DAQ
(run 23063032, 200 events, chain "pp2022a fst CMuDST fstMuRawHit") with the option on,
in ~/fcstrk13/star-sw. Measured compressed bytes per branch:

    FcsHit        32229 B/event   46.9% of the tree
    FstRawHit      1975 B/event    2.87%     <- the cost of this option
    FttRawHit      1798 B/event    2.62%
    FstHit          628 B/event    0.91%

So FST raw hits cost about 2 kB/event, essentially the same as FttRawHit already costs
and about one sixteenth of FcsHit. Against a full production MuDst at 154.6 kB/event
that is roughly 1.3%. (The test MuDst is 68 kB/event because the chain is leaner, which
is why the percentage-of-tree figure above is larger than the production fraction.)

The earlier estimate in this note was 0.8-2.5 kB/event; measured 1.97, so the estimate
stands and the answer does not change: it is cheap.

Multiplicity, also now measured: 103.2 FST raw hits/event, against 25.2 clustered
FstHit/event -- so about 4 raw strips stored per clustered hit. FstHit/event matches the
existing production MuDst (24.5), which is the cross-check that this test chain
reproduces production on the FST side.

Time bins: maxTimeBin is 0, 1 or 2 only in this run too, never 3-8, confirming 3 bins
rather than 9.


DOES THE WRITTEN DATA DECODE CORRECTLY? YES
--------------------------------------------
This mattered because the branch had never been exercised and akio reports a past bug
that filled garbage. Decoding geoId independently of the class accessors
(wedge = 1 + geoId/1024, disk = 1 + geoId/12288, r = (geoId%1024)/128,
phi = (geoId%1024)%128, layout confirmed against StFstRawHitMaker.cxx:369):

    disk    1..3    as expected
    wedge   1..36   as expected
    rStrip  0..7    as expected
    phi     0..127  as expected
    geoId < 0 or > 36863 : none

So the write path produces usable data. Whatever the historical garbage bug was, it is
not present in what this chain writes today.

Note for whoever repeats this: do the index arithmetic with integer division.
TTree::Draw divides in double, so geoId/12288 for the last channel gives 2.9999 and the
disk histogram shows a spurious "4". That artifact cost a false FAIL on the first pass.


WHAT WE ASK FOR
---------------
a. Add "fstMuRawHit" (which pulls in fstEvtRawHit) to the production chain. Cost is
   ~0.8-2.5 kB/event, ~0.5-1.6% of the MuDst, at or below what FttRawHit already costs
   (3 timebins; triple it if a run ever takes 9). It makes the
   single unrecoverable item recoverable. The code to CONSUME it does not exist yet, but
   we can write that afterwards -- the data is the part that cannot be made later.
   Budget for fixing the decode too: getSensor() is wrong today and the branch has
   evidently never been exercised. Worth one short test job on a few files first, reading
   the raw hits back and checking disk/wedge/sensor/rStrip/phiStrip against the FstHit
   in the same event, BEFORE committing a full production to it.

b. If (a) is not possible, then the FST clustering fixes have to go in BEFORE
   production starts, or that data is permanently stuck with non-adjacent r-merging and
   R placed at the largest strip. Partial mitigation from the MuDst alone: with
   nRawHitsR known one can assume adjacency and use maxR - (nRawHitsR-1)/2 as a better
   R estimate -- but adjacency is exactly the assumption the algorithm violates, so this
   is an approximation, not a fix.

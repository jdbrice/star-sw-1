PROPOSAL IN ONE PARAGRAPH

Much of the forward-upgrade development of the last two years is NOT in the STAR repository. 
It lives in Daniel Brandenburg's "dev" branch, plus work of Akio's in "akio202607" branch. 
We propose to land it as a sequence of small, independent pull requests against STAR Gitea, 
in a fixed order, rather than as one large merge. This document lists what exists, 
what it depends on.

2b. HOW TO MAKE THESE PRs -- rules learned doing waves 2-4

  Mechanics that cost time to discover; worth following rather than rediscovering.

  * Branches go to STAR/star-sw, not to a personal fork. Jerome prefers branches he
    can see over work scattered across forks. It is also what makes stacked PRs
    possible at all: a PR base must be a branch in the base repo, so a branch living
    only on a fork cannot be used as a base. Delete the branch after merge. #21 was
    closed and re-opened as #22 for exactly this reason.

  * STAR Gitea merges with real merge commits, NOT squashes -- PR#2's branch commit
    b99dd74d12 is an ancestor of main with its SHA intact. So a stacked PR retargets
    to main cleanly after its parent lands: one base change in the UI, no rebase and
    no force-push. (Daniel squash-merges in his own GitHub fork; that is what the
    earlier "git cherry lies" note was about, and it does not apply here.)

  * NEVER take StRoot/StBFChain/BigFullChain.h wholesale from akio202607. Doing so
    DELETES six production chain definitions -- B2023b, P2023b, B2024b, pp2024b,
    P2024b -- and drags in the broken "fttSim" option naming StFttFastSimulatorMaker,
    which exists nowhere. Insert only the one new option, and check the diff has zero
    deleted lines before committing. #25 and #26 were both built this way.

  * Two options inserted in different parts of BigFullChain.h do NOT conflict. #25
    inserts at line ~1577 and #26 at ~1734; a test merge of both is clean. The
    "whoever rebases second resolves it" warning below is about options landing in the
    same region, not about every pair.

  * Expect to carry Daniel's unsubmitted commits. Every package touched so far --
    StFttDbMaker, StFttHitCalibMaker, StFstSimMaker -- had unmerged work of his
    underneath ours. Keep it as its own commit with his authorship and say so in the
    PR text; do not squash it into ours and do not silently rewrite it. Where our
    later commit undoes part of his (the HitCalibHelper histogram cap in #24), leave
    both commits and give the reason in the message.

  * Do not cite in a PR description anything that is not in main. StFttClusterPointMaker
    is not in main, and main's StFwdHitLoader does not read meanRStrip, so neither can
    be used to motivate a PR against main. Check with "git show origin/main:<path>"
    before writing the justification, not after.

  * akio202607 is NOT a superset of dev. It diverged at the 2026-07-09 snapshot and
    never received Daniel's embedded strip geometry, so our StFttDb work was written
    against the old file-reading version. Rebasing it onto his layer surfaced a real
    bug: the constructor needs BOTH initStripGeometry() and resetGeometryToHardcoded(),
    and ours alone would have left every strip map empty. Assume the same kind of gap
    for any other package where dev moved after July.

  * Reconstructing commits: for a package whose history is a long tail of web edits,
    snapshot the package directory at each milestone commit
    ("git checkout <sha> -- <dir>") and commit that with the original author and date,
    rather than cherry-picking dozens of commits that also touch other packages. Verify
    the end state with "git diff --quiet <ref> -- <dir>".

  * "cons +StRoot/StBFChain" regenerates two TRACKED files under StRoot/StBFChain/doc/.
    Restore them before committing. This is one more reason never to stage broadly.

  * Build every commit of a multi-commit PR, not just the tip, so the PR bisects.

3. THE PLAN

  Ordering principle: schema first, because everything depends on it; then
  self-contained new packages, which nobody depends on; then the tracker core; then
  the wiring that drives all of it. Within a wave the PRs do not touch each other's
  files.

  A note on BFC options, which cut across several waves below. Every new maker needs a
  chain option before anyone can use it, so each maker should land WITH its own option
  rather than waiting for a separate options PR. Current state:
    All of these edit the SAME file, StRoot/StBFChain/BigFullChain.h. It is the one
    shared file across the waves, but note (measured) that two options inserted in
    different regions of it merge cleanly -- see 2b. Conflicts arise only for options
    landing in the same region.
    StFttSimHitMaker        DONE -- "FttSimHit" written from scratch, shipped in #26
    StFstSlowSimMaker       DONE -- "fstSlowSim" shipped in #25
    StFttClusterPointMaker  option still owed; it was to come with #810
    fttSim / FcsTrackMatch / PicoVtxless   are what #759 adds
    Reminder: StFttFastSimMaker has NO option in main either, and the "fttSim" option
    #759 adds names StFttFastSimulatorMaker, which exists nowhere -- fix the name.

    The new StEvent FTT fields are deliberately NOT mirrored into the MuDst.
          StFttCluster gains mMaxADC, mIndexMaxStrip and the four mMaxStrip*;
          StFttPoint gains mD1, mD2, mSigmaX, mSigmaY, mSigmaXY and mCov;

          StFttClusterMaker and StFttClusterPointMaker. mCov in particular is a
          std::vector<std::vector<float>> per point and would cost real MuDst

          read straight from a MuDst have these fields empty, with no warning.

              clu->setMaxStripLength( maxAdcHit->stripLength() );

          Without them a cluster carries no strip length or centre, so the unmeasured

        - floor the cluster sigma at the single-strip value, kSigmaMin =
          pitch/sqrt(12) = 3.2/sqrt(12) = 0.924 mm. A single-strip cluster has all its
          charge in one strip, so the computed variance is exactly 0 and the fit weight
          diverges. Verified against merged code 2026-10-13: #10 (Gene's one-line carve-out
          from #9) left star/main:371 as
                clu->setSigma( sqrt( var < 0 ? 0 : var ) );
          which guards only the NEGATIVE case. A single-strip cluster gives var exactly 0,
          not negative, so sqrt(0)=0 passes straight through and GenFit still gets an
          infinite weight today. The floor is still needed. It already exists as pr2 commit
          ee7ee27b9f (1 file, +9/-1) -- lift it out of pr2 rather than rewriting it.

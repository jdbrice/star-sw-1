PROPOSAL IN ONE PARAGRAPH

Essentially none of the forward-upgrade development of the last two years is in the
STAR repository. It lives in Daniel Brandenburg's `dev` branch, plus work of ours that
has not been proposed yet. We propose to land it as a sequence of small, independent
pull requests against STAR Gitea, in a fixed order, rather than as one large merge.
This document lists what exists, what it depends on, and who should own each piece.



1. THE SITUATION

  Daniel's dev vs the frozen STAR main:  394 commits, 140 code files, +15310 / -818.
  A patch-id comparison finds 392 of those 394 have no equivalent upstream, i.e. almost
  nothing was merged before the GitHub repository was frozen.

  Eight of Daniel's pull requests were still open at the freeze and are now unreachable
  as PRs: #569, #759, #796, #804, #810, #811, #815, #826. Every one of the branches
  still exists in jdbrice/star-sw-1, so nothing is lost; only the PR threads are.

  PR #826 alone is 125 of those 140 files and +12890 of the +15310 lines. It should not
  be re-proposed as one piece.

  Separately we have work that has never been proposed: 16 new and 46 modified code
  files, mostly sTGC/FST alignment, the DB-driven geometry path, and diagnostics.


2. ALREADY IN PROGRESS ON GITEA

  #2  StFstHitMaker: meanPhiStrip must be float, not int        MERGED
      The cluster mean phi strip was truncated to int, discarding the fractional part
      of every FST cluster position. Time-critical for productions, now in.

  #3  StFstRawHitMaker / StMuFstUtil: read FST raw hits from a MuDst       open
      Lets FST be re-clustered from a production MuDst, which is what makes the
      forward afterburner workflow possible. Purely additive: no existing signature
      changes, no existing caller touched. Verified on 200 events: clusters rebuilt
      from the MuDst are identical to the ones production wrote into it -- 5032
      clusters, 100.00% exact match on wedge/sensor/meanRStrip, none missing or extra.

  #10 StFttClusterMaker: clamp the variance before sqrt                   MERGED
      Taken out of #9 on its own for the SL26 freeze. Fixes a NaN cluster sigma that
      is present in 7.49% of Run 22 and 1.94% of Run 24 production clusters. Note the
      divide-by-zero guard in the original #815 would not have caught any of them:
      sumAdc is never <= 0, and the NaN comes from sqrt() of a variance driven slightly
      negative by rounding. Downstream, StFwdHitLoader skips any hit with a NaN
      covariance, so those clusters were being lost to tracking.

  #9  StFttClusterMaker correctness fixes (revives #815)                   open
      The rest of #815: Daniel's commit cherry-picked unchanged, plus the remaining
      review comments. One of them matters for correctness --
      `StFttCollection::clusters()` is an owning StSPtrVec whose clear() deletes the
      clusters, while StFttPoint keeps its parents as raw StFttCluster*, so clearing
      clusters alone leaves surviving points referencing freed memory. #9 clears the
      dependent points first. This bites an StEvent rebuilt from a MuDst that already
      carries production points, i.e. the forward afterburner.


3. THE PLAN

  Ordering principle: schema first, because everything depends on it; then
  self-contained new packages, which nobody depends on; then the tracker core; then
  the wiring that drives all of it. Within a wave the PRs do not touch each other's
  files.

  WAVE 1 -- small, independent, recoverable verbatim from Daniel's branches
    #759  BFC options for FWD productions                      1 file,  +6
    #796  BFC chain options for FTT sim / FCS track match      1 file,  +6/-22
          NOTE: as it stands this branch also DELETES four production chain
          definitions (B2023b, P2023b, B2024b, pp2024b). Cherry-pick the additive
          part only.
    #815  StFttClusterMaker correctness fixes     -> split: sqrt clamp merged as
          Gitea #10 for the freeze; the remainder is Gitea #9
    #804  StMuFwdTrack ClassDef v4                             3 files, +11/-8
          Schema: adds mTrackType and bumps ClassDef 3->4. Best landed inside a tag
          rather than after one. Not urgent for a production that writes no forward

  WAVE 2 -- StEvent / StPicoEvent schema, alone, nothing else in it
    StFwdTrack track types kBLCVertexConstrained=4 and kFCSConstrained=5,
    StFwdTrackCollection ownership, StPicoFwdTrack fields. Waves 4-5 depend on this.

  WAVE 3 -- core, self-contained, fully parallel
    StFttDb: embed strip geometry instead of reading Row*.txt   14 files, +1868
    StarVMC: sTGC zplane int -> float                            1 file,  +11/-2
          11 lines. `zplane` is declared int in StgmGeo1.xml, so the sTGC station z

          StFttFastSimMaker does not exercise the real geometry or the clustering.
    StFstSlowSimMaker                              2 files, +615   (ours)
          Runs MC through the real FST reconstruction chain rather than smearing.
    StFstFastSimMaker: set meanRStrip/meanPhiStrip on simulated hits   (ours)

  WAVE 5 -- the tracker core: decompose #826 along Daniel's own split
    He already separated this work in his fork as PRs #13-#19. Re-propose each as its
    own PR, in this order, each depending only on wave 2:
      #13 FST/FTT hit-finding and track-fitting fixes
      #14 seed-curvature fixes + FST warm-start refit
      #15 FTT diagonal-strip calibration gaps
      #16 DCA target/method in refitTrack

4. QA AND DEBUGGING TOOLS -- PROBABLY NOT FOR THE LIBRARY

  Three of the packages above are diagnostics, not reconstruction. Nothing in BFC
  needs them, and nothing in a production chain calls them:

    StFwdResidualMaker        2 files,  677 lines   FST/FTT alignment residuals
    StFttChargeSharingMaker   2 files,  469 lines   sTGC charge-sharing studies
    StFwdAlignmentMaker       2 files,  340 lines   unbiased hit-removed residuals

  We propose NOT putting these through library review, and instead keeping them where
  QA and analysis makers have historically lived -- the StSpinPool model, i.e. a
  repository that does not gate on BFC review. They change often, they exist to answer
  one question at a time, and review bandwidth is better spent on the reconstruction
  code. We are happy either way, but it should be a conscious choice rather than
  something that happens by default.

  If they do go in the library, they belong after wave 5, not inside it.


5. REVIEW FINDINGS STILL OPEN

  StMuFwdTrack's new StMuFwdTrackType enum stops at kForwardVertexConstrained=3.
  Correct against today's main, but mTrackType is copied straight from
  StFwdTrack::trackType(), so once kBLCVertexConstrained=4 and kFCSConstrained=5 land
  in wave 2, anything reading this enum mislabels them. Extend it in the same PR.

PROPOSAL IN ONE PARAGRAPH

Essentially none of the forward-upgrade development of the last two years is in the
STAR repository. It lives in Daniel Brandenburg's `dev` branch, plus work of ours that
has not been proposed yet. We propose to land it as a sequence of small, independent
pull requests against STAR Gitea, in a fixed order, rather than as one large merge.
This document lists what exists, what it depends on, and who should own each piece.


1. THE SITUATION

  Daniel's dev vs the frozen STAR main:  394 commits, 140 code files, +15310 / -818.
  A patch-id comparison finds 392 of those 394 have no equivalent upstream, i.e. almost
  nothing was merged before the GitHub repository was frozen.

  Eight of Daniel's pull requests were still open at the freeze and are now unreachable
  as PRs: #569, #759, #796, #804, #810, #811, #815, #826. Every one of the branches
  still exists in jdbrice/star-sw-1, so nothing is lost; only the PR threads are.

  PR #826 alone is 125 files and +12890 lines -- about 89% of the whole gap. It should
  not be re-proposed as one piece.

  Separately we have work that has never been proposed: 16 new and 46 modified code
  files, mostly sTGC/FST alignment, the DB-driven geometry path, and diagnostics.

  self-contained new packages, which nobody depends on; then the tracker core; then
  the wiring that drives all of it. Within a wave the PRs do not touch each other's

4. REVIEW FINDINGS

  Reported here because they affect what should be merged, not as criticism.

  a) PR #815 as originally written introduces a use-after-free.
     `StFttCollection::clusters()` is an StSPtrVec, an owning container whose clear()
     deletes the elements (StStrArray::clear, StArray.cxx:241), while StFttPoint keeps
     its parents as raw StFttCluster* (mClusters[4]). Clearing clusters alone leaves
     every surviving point referencing freed memory. This is not hypothetical for an
     StEvent rebuilt from a MuDst that already carries production points, which is what
     the forward afterburner does. Gitea #9 clears the dependent points first.

  b) The NaN this fixes is present in real data.
     7.49% of Run 22 and 1.94% of Run 24 production FTT clusters have NaN sigma.
     `sumAdc` is never <= 0, so the divide-by-zero guard in the original PR would not
     have caught any of them: they come from sqrt() of a variance that goes slightly
     negative through rounding. The clamp is in the second commit of Gitea #9.
     Downstream, StFwdHitLoader skips any hit with a NaN covariance, so those clusters
     are lost to tracking. Recoverable after the fact -- the FTT raw hits are in the
     MuDst and StFttRawHitMaker::readMuDst() is already in the library -- so this is a
     "should have" rather than a blocker.

  c) In BFC there is no cross-event accumulation of FTT clusters or points.
     StEventMaker::Clear() -> StMaker::Clear() -> m_DataSet->Delete() destroys the
     StEvent each event, and ~StFttCollection deletes its StSPtrVec members. Confirmed
     in data: Run 24 cluster multiplicity plateaus at ~150/event, which accumulation
     could not do.

  d) StMuFwdTrack's new StMuFwdTrackType enum stops at kForwardVertexConstrained=3.
     Correct against today's main, but mTrackType is copied straight from
     StFwdTrack::trackType(), so once kBLCVertexConstrained=4 and kFCSConstrained=5
     land (wave 2) anything reading this enum mislabels them. Extend it in the same PR.

  e) StFcsDb::getBeamline has no mDbAccess gate in dev.
     With setDbAccess(0) -- MC and particle-gun analysis -- it picks up a real, undated
     DB beamline record and corrupts getLorentzVector(). We carry a gate and will
     propose it.

  f) FitterUtils logs every collinear seed triple at LOG_DEBUG and the seed pT at
     LOG_INFO; in dense MC that was ~660k lines per run. We carry the removal.

  g) FitterUtils has no reversed-field charge correction. The hits determine only the
     sign of q*Bz, so in a reversed field every seed charge guess is inverted and the
     fit does not fully recover. Measured on reversed-field single-electron MC, pT 0.5:
     68.1% -> 76.1% correct charge. We carry the fix.

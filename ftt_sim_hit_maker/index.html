StFttSlowSimMaker: a real-geometry FTT simulation maker

→ Real FTT charge-sharing measurement — the measured 3-strip profile behind this maker's charge sharing, the hardware threshold efficiency, and the X–U / Y–V charge correlation (found 2026-10-21, once the per-VMM time cut is applied).

Renamed 2026-10-17 (PR #26 review): was StFttSimHitMaker, now StRoot/StFttSimMaker/StFttSlowSimMaker, joining the existing StFttFastSimMaker in that package — the same layout FST uses (StFstFastSimMaker + StFstSlowSimMaker). BFC option fttSlowSim. It does not replace the fast sim: that one writes StFttPoint directly with a 100µm blur and never touches clustering or StFttDb; this one writes StFttRawHit and runs the real chain.

A new maker that lets a GEANT MC event drive the FTT reconstruction code path
G2THIT → StFttSlowSimMaker → StFttClusterMaker → StFttClusterPointMaker which uses StFttDb
instead of the fast-sim shortcuts that bypass them entirely.

Motivation

Directly motivated by the single-electron gun @ 45° page: that page set out to test the FTT geometry transform with a controlled, known-kinematics single track, and found that no MC-compatible code path in this repo actually reaches StFttDb :

  • StFttClusterPointMaker::MakeGeantPoints() (what script/sim.C and therefore all particle-gun/Pythia MC uses) reads GEANT truth directly in global coordinates and never calls StFttDb at all.
  • StFttFastSimMaker (the "fttSim" BFC tag) also reads GEANT truth, but writes into an unrelated StRnDHit collection using its own standalone geometry, independent of StFttDb, and unused by anything downstream.
  • StFttRawHitMaker -- the true entry point to the real cluster-making chain -- never reads GEANT truth at all; it only unpacks real raw DAQ data or an already-existing MuDst.
StFttSlowSimMaker closes this gap. This is also essential for
  • Noise studies
  • Studies for high occupancy
  • Embedding

New StFttSlowSimMaker

  • Reads St_g2t_fts_hit and truth hits
  • Takes the quadrant straight from volume_id, then inverts StFttDb::getGloablOffset_ClusterPoint()'s forward transform for that one quadrant
    • There was a better way (2026-10-17). volume_id = 100·station + 10·pentagon + layer (layer 1 = front foil, 2 = back), because each station in StgmGeo1.xml places its four STFM pentagons in turn. So it does carry the quadrant.
    • The digit is not StFttDb's index though: AGML places the pentagons in rotation order A,D,C,B while StFttDb numbers them A,B,C,D, so they differ by the fixed permutation {0,3,2,1}. Measured on a particle gun: every truth hit landing on strips agrees, none disagree.
    • The old brute-force search over all 4 quadrants was wrong for ~4% of hits (its 560mm local box overlaps between quadrants, and it kept the first match) and silently dropped another ~15%.
  • Covers X, Y and both diagonal (U/V) orientations
  • Injects ADC to strips using StFttDb::reverseHardwareMap()
    • Inital model : a fixed 3-strip cluster of 100,800,100 ADC
    • Real-data analysis of FTT hits/clusters to get a realistic strip charge-sharing profile
    • Per-VMM uuid-vs-time diagnostic
    • New model based on that analysis:
      • Total charge/cluster : draw from exponential with mean=431.5 (measured cluster sumAdc mean=RMS) — superseded, see ADC from GEANT energy loss below
      • Center strip is always kept, floored to threshold (~70 ADC) if the draw came in low, keeping single-hit efficiency at 100% for now
      • Width : Gaussian(σ=2.4mm) charge response, fit to the real nStrips=3 cluster mean 25:48:25 ratio
      • Split is asymmetric, depending on where the hit truly lands within its strip (not a fixed ratio) -- restores real charge-division resolution
  • Sum up ADC for same strips (there can be multuple g2t hits for a strip, from 2nd particles or embedding)
  • Create StFttRawHit for all strips with hit above threshold (>= 70)
  • StFttClusterMaker and StFttClusterPointMaker (with mUseGeantData=false) do the actual clustering and transform.

StFttDb::reverseHardwareMap

  • Bug: only ever returned ONE orientation per (plane,quadrant) -- (row,strip) → H/V collision, rMap had no orientation key, so the 2nd orientation silently overwrote the 1st at load time.
  • Fix: rMap now holds a small vector per key; new signature takes orientation as an extra input/output key to disambiguate: 
bool reverseHardwareMap( int &rob, int &feb, int &vmm, int &ch,
                          int plane, int quad, int row, int strip,
                          UChar_t &orientation ) const;   // orientation: in as hint, out as result
  • Only caller anywhere in the repo is this new maker, so the fix carries no other risk.
  • Also ported the StFttCluster::setMaxStripLength() line.

Schematic, not to scale, plane-0 offsets. Row bands drawn to scale-ish for A/D/B/C (colored dots = each quadrant's own local origin -- they do NOT coincide with each other or with the beampipe); U/V hatching (direction only) and row0/1/2 labels drawn once, in A, for clarity -- the same layout repeats in B, C, D.

Diagonal strips exist to resolve H×V crossing ambiguity (confirmed via a reverted commit's StFwdFttClusterQAMaker.cxx, which cross-checks H/V/D candidates), not to cover a gap X/Y misses. One bug found+fixed along the way: MakeLocalPoints() uses opposite row↔sign conventions for DiagonalV vs DiagonalH -- using the same rule for both silently picks a real-but-wrong hardware channel.

Validation

Ran a 5-event electron-gun sample (pT=1.5GeV, η=2.5-4.0, random φ). For X/Y clusters, the measured axis reproduces GEANT truth to ~1mm end-to-end through the real transform -- well within one strip pitch (3.2mm), checked by hand for several quadrants/orientations. For diagonal clusters, the rotation mixes a precise coordinate (from the strip index) with an approximate half-length placeholder into both output x and y, so neither individually matches truth by itself -- but the invariant local_x+local_y = 2·D_StripGroupEdge[0] + √2·(measured strip coordinate) (the placeholder exactly cancels in the sum) reproduces truth to <0.05mm every time, exactly the same residual metric StFwdFttClusterQAMaker.cxx uses to confirm a diagonal cluster against an H×V crossing point. Checked all 4 (orientation, row-sign) combinations by hand. No crashes across the 5-event sample with per-hit debug tracing on.

Full chain: FST + real FTT + GenFit + StFwdResidualMaker (2026-07-17, later that evening)

Built the full chain electron-gun @ 45° asked for but found not actually possible at the time that page was written: FST fast-sim + this maker's real FTT chain + GenFit StFwdTrackMaker + StFwdResidualMaker (copied unmodified from this repo into ~/fcstrk12, which didn't have it), inserted right before fwdTrack so GenFit sees real StFttPoints built through the actual StFttDb transform. Generator: single e-, pT=1.5GeV, η=2.5-4.0, φ=45°±0.001rad (top-south quadrant A, where sx=sy=+1 so the still-open scale-then-shift bug doesn't bite).

200 events → 163 converged Global tracks, 447 FST + 465 FTT residuals. FST residuals are unbiased (mean <0.01cm on all 3 disks). FTT residuals show a small but very consistent systematic offset on every plane -- dx: -0.29 to -0.34cm, dy: -0.37 to -0.45cm, all 4 planes, both axes, same sign, with 52-62 entries each (nowhere near statistical-fluctuation territory). This is new -- not yet explained. Working hypothesis: each StFttPoint's "other axis" is a coarse row-center placeholder, not a real measurement (see maxStripLength fix above) -- even with a real, bounded value and a large sigma, GenFit's Kalman fit still assigns it nonzero weight, and if that placeholder is consistently offset from the true trajectory in the same direction across several planes of the same track, it could pull the whole fit by a few mm -- which would then show up as a small residual even on the OTHER point's precise axis once the fit is projected back, despite that axis's own hit position being accurate in isolation (as validated above, without any fitting involved). Not confirmed; a plausible next step, not done here.

ADC from GEANT energy loss (2026-10-17)

The charge model above draws the cluster total from an exponential and never looks at how much energy the particle actually deposited. Raised in review of PR #26: "Why is the total adc independent of the energy deposited in the strip?" g2t_fts_hit carries de and ds, so the question is whether a de-driven model does better. It does.

What to compare against

  • The measured all-cluster mean of 431.5 is not the right target: 19% of real clusters are single-strip, mean 112, and are noise and unrelated pileup (busy p+p, wide time window). The spike at exactly 1023 in that population is single saturated strips.
  • A single-particle MC should be compared to the nStrips≥2 clusters: mean 508.3, rms/mean 0.930.

The model

  • Sum de over all GEANT steps of one crossing (one track, one foil) — GEANT reports ~7% of crossings as several steps, up to 9. Mean 0.776 keV, Landau, rms/mean 3.19.
  • totalAdc = gain × Σde × G, with G a gas-amplification fluctuation of relative width r (r=0 means pure scaling, nothing added).
  • Then the maker's existing response, unchanged: sub-strip position, Gaussian(σ=2.4mm) split over centre ±1 strip, 70-ADC zero suppression, 1023/strip saturation.
  • Each curve is scaled so its mean equals the real mean, so the plots compare shape, not normalisation.

Result: does de beat the exponential?

Standalone model study (no chain), each scale tuned so that model's own mean equals the real nStrips≥2 mean, so only shape is being compared:

modelscalerms/meanshape mismatch
real data, nStrips≥2—0.93—

(shape mismatch = 104 × mean per-bin squared difference over 0-3000 ADC, smaller is better)

  • GEANT de alone, with zero added fluctuation, already beats the current exponential (3.2 vs 3.6) and tracks the tail out to 2500 ADC where the exponential falls away badly.
  • Adding gas amplification spread helps, but only a little: r≈0.3 is best (1.7), and r≥0.6 — approaching the single-electron exponential limit, which is effectively what the code assumes now — makes it worse again.
  • So for this detector the Landau dominates and the avalanche is a correction, not the other way round. 0.776 keV in a 3mm gap of the pentane/CO2 mix at W≈25-30eV is ~26-31 primary electrons, each avalanching independently, so the gain spread averages down to √(f/N) ≈ 13-20%. The data preferring ~30% is the same ballpark, a little more, which is what TGC saturated-mode gain plus VMM shaping would give.
  • The model cannot reach rms/mean 0.93 and should not be tuned until it does. It saturates near 0.82-0.84 because the 1023/strip cap truncates the Landau tail. The rest of the width in data is pileup, noise and a wider spread of incidence angles than a pT=1.5 electron gun gives. None of those are in this MC yet (see TODO).
  • The model's shoulder near 600-800 ADC is its own hard 70-ADC strip threshold: it disappears if the threshold is lowered to 20. Real data has noise smearing it out; the MC has none.

What the maker now does

StFttSlowSimMaker now draws the charge this way: totalAdc = mAdcPerKeV × Σde × gainFluctuation(), with mAdcPerKeV = 600 and mGainSpread = 0.3, both settable. Below is its actual output through the real chain (StFttDbMaker → StFttSlowSimMaker → StFttClusterMaker), not a model of it, against the same real data.

  • Anchored on the cluster PEAK-strip ADC, not on sumAdc. The peak strip is the center strip, which this ±1-strip model represents faithfully. One parameter puts both moments on the real values: mean 227 vs 226, rms 199 vs 196.
  • sumAdc comes out ~15% high (583 vs 508) and the 4-7 strip clusters are missing (4% vs 20% of real clusters). Both are the same thing: the model puts charge only on the center strip ±1, so it cannot make the wide clusters a shallow-incidence track leaves in real data. That is a known limit of the ±1 design, not a tuning error, and it is why sumAdc is the wrong quantity to anchor on.
  • Single-strip clusters: 30% in MC vs 19% in real data — but the real single-strip population is largely noise and pileup, which this MC does not have at all, so the two numbers are not measuring the same thing.
  • Geometry is unaffected by any of this: 93.1% of truth hits still match a cluster within 5mm, residual mean 0.014mm.

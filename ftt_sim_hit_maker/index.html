StFttSimHitMaker: a real-geometry FTT simulation maker

A new maker that lets a GEANT MC event drive the FTT reconstruction code path
G2THIT → StFttSimHitMaker → StFttClusterMaker → StFttClusterPointMaker which uses StFttDb
instead of the fast-sim shortcuts that bypass them entirely.

Motivation

Directly motivated by the single-electron gun @ 45° page: that page set out to test the FTT geometry transform with a controlled, known-kinematics single track, and found that no MC-compatible code path in this repo actually reaches StFttDb :

  • StFttClusterPointMaker::MakeGeantPoints() (what script/sim.C and therefore all particle-gun/Pythia MC uses) reads GEANT truth directly in global coordinates and never calls StFttDb at all.
  • StFttFastSimMaker (the "fttSim" BFC tag) also reads GEANT truth, but writes into an unrelated StRnDHit collection using its own standalone geometry, independent of StFttDb, and unused by anything downstream.
  • StFttRawHitMaker -- the true entry point to the real cluster-making chain -- never reads GEANT truth at all; it only unpacks real raw DAQ data or an already-existing MuDst.
StFttSimHitMaker closes this gap. This is also essential for
  • Noise studies
  • Studies for high occupancy
  • Embedding

New StFttSimHitMaker

  • Reads St_g2t_fts_hit and truth hits
  • brute-forces which quadrant a hit belongs to by inverting StFttDb::getGloablOffset_ClusterPoint()'s forward transform for all 4 quadrants and keeping whichever gives a physically valid local (x,y)
    • volume_id's own quadrant digit does not match StFttDb's A/B/C/D convention (True? Is there better way?)
  • Covers X, Y and both diagonal (U/V) orientations
  • Injects ADC to strips using StFttDb::reverseHardwareMap()
    • Inital model : a fixed 3-strip cluster of 100,800,100 ADC
    • Real-data analysis of FTT hits/clusters to get a realistic strip charge-sharing profile
    • Per-VMM uuid-vs-time diagnostic
    • New model based on that analysis:
      • Total charge/cluster : draw from exponential with mean=431.5 (measured cluster sumAdc mean=RMS)
      • Center strip is always kept, floored to threshold (~70 ADC) if the draw came in low, keeping single-hit efficiency at 100% for now
      • Width : Gaussian(σ=2.4mm) charge response, fit to the real nStrips=3 cluster mean 25:48:25 ratio
      • Split is asymmetric, depending on where the hit truly lands within its strip (not a fixed ratio) -- restores real charge-division resolution
  • Sum up ADC for same strips (there can be multuple g2t hits for a strip, from 2nd particles or embedding)
  • Create StFttRawHit for all strips with hit above threshold (>= 70)
  • StFttClusterMaker and StFttClusterPointMaker (with mUseGeantData=false) do the actual clustering and transform.

StFttDb::reverseHardwareMap

  • Bug: only ever returned ONE orientation per (plane,quadrant) -- (row,strip) → H/V collision, rMap had no orientation key, so the 2nd orientation silently overwrote the 1st at load time.
  • Fix: rMap now holds a small vector per key; new signature takes orientation as an extra input/output key to disambiguate: 
bool reverseHardwareMap( int &rob, int &feb, int &vmm, int &ch,
                          int plane, int quad, int row, int strip,
                          UChar_t &orientation ) const;   // orientation: in as hint, out as result
  • Only caller anywhere in the repo is this new maker, so the fix carries no other risk.
  • Also ported the StFttCluster::setMaxStripLength() line.

FTT geometry: disk / quadrant / foil / row / orientation

LevelValuesNotes
disk (plane)0-3 increasing z, ~312/330/347/365cm
quadrant (quad)0=A, 1=B, 2=C, 3=D D | A (top row), C | B (bottom row). A is the sign reference (sx=sy=+1); B flips y; C flips x and y; D flips x.
foil (chamber)front / back front = "vertical chamber" (Vertical + DiagonalV strips); back = "horizontal chamber" (Horizontal + DiagonalH strips). Same quadrant, same footprint, two physical foils.
row 0-2X/Y strips 3 bands along the row axis, start edges 11.49 / 172.29 / 360.09mm (YX_StripGroupEdge), strip pitch 3.2mm.
row 3-4diagonal (U/V) strips NOT a 4th/5th spatial band -- same footprint as rows 0-2, on the same foil. row 3 vs 4 is just the sign of (y-x) in local coordinates (which side of the strip's own long axis).
orientation 0=Horizontal, 1=Vertical, 2=DiagonalH, 3=DiagonalV Horizontal/Vertical ↔ row 0-2; DiagonalH/DiagonalV ↔ row 3-4, on the back/front foil respectively.

Schematic, not to scale, plane-0 offsets. Row bands drawn to scale-ish for A/D/B/C (colored dots = each quadrant's own local origin -- they do NOT coincide with each other or with the beampipe); U/V hatching (direction only) and row0/1/2 labels drawn once, in A, for clarity -- the same layout repeats in B, C, D.

Diagonal strips exist to resolve H×V crossing ambiguity (confirmed via a reverted commit's StFwdFttClusterQAMaker.cxx, which cross-checks H/V/D candidates), not to cover a gap X/Y misses. One bug found+fixed along the way: MakeLocalPoints() uses opposite row↔sign conventions for DiagonalV vs DiagonalH -- using the same rule for both silently picks a real-but-wrong hardware channel.

Validation

Ran a 5-event electron-gun sample (pT=1.5GeV, η=2.5-4.0, random φ). For X/Y clusters, the measured axis reproduces GEANT truth to ~1mm end-to-end through the real transform -- well within one strip pitch (3.2mm), checked by hand for several quadrants/orientations. For diagonal clusters, the rotation mixes a precise coordinate (from the strip index) with an approximate half-length placeholder into both output x and y, so neither individually matches truth by itself -- but the invariant local_x+local_y = 2·D_StripGroupEdge[0] + √2·(measured strip coordinate) (the placeholder exactly cancels in the sum) reproduces truth to <0.05mm every time, exactly the same residual metric StFwdFttClusterQAMaker.cxx uses to confirm a diagonal cluster against an H×V crossing point. Checked all 4 (orientation, row-sign) combinations by hand. No crashes across the 5-event sample with per-hit debug tracing on.

Full chain: FST + real FTT + GenFit + StFwdResidualMaker (2026-07-17, later that evening)

Built the full chain electron-gun @ 45° asked for but found not actually possible at the time that page was written: FST fast-sim + this maker's real FTT chain + GenFit StFwdTrackMaker + StFwdResidualMaker (copied unmodified from this repo into ~/fcstrk12, which didn't have it), inserted right before fwdTrack so GenFit sees real StFttPoints built through the actual StFttDb transform. Generator: single e-, pT=1.5GeV, η=2.5-4.0, φ=45°±0.001rad (top-south quadrant A, where sx=sy=+1 so the still-open scale-then-shift bug doesn't bite).

200 events → 163 converged Global tracks, 447 FST + 465 FTT residuals. FST residuals are unbiased (mean <0.01cm on all 3 disks). FTT residuals show a small but very consistent systematic offset on every plane -- dx: -0.29 to -0.34cm, dy: -0.37 to -0.45cm, all 4 planes, both axes, same sign, with 52-62 entries each (nowhere near statistical-fluctuation territory). This is new -- not yet explained. Working hypothesis: each StFttPoint's "other axis" is a coarse row-center placeholder, not a real measurement (see maxStripLength fix above) -- even with a real, bounded value and a large sigma, GenFit's Kalman fit still assigns it nonzero weight, and if that placeholder is consistently offset from the true trajectory in the same direction across several planes of the same track, it could pull the whole fit by a few mm -- which would then show up as a small residual even on the OTHER point's precise axis once the fit is projected back, despite that axis's own hit position being accurate in isolation (as validated above, without any fitting involved). Not confirmed; a plausible next step, not done here.

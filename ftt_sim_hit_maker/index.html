StFttSimHitMaker: a real-geometry FTT simulation maker (proposal / in progress)

Landing page for a separate, ongoing piece of work: a new maker that would let a GEANT particle-gun or Pythia MC event drive the real FTT reconstruction code path (StFttClusterMaker → StFttClusterPointMaker → StFttDb::getGloablOffset_ClusterPoint()) instead of the fast-sim shortcuts that bypass StFttDb entirely. Full design in proposal_ftt_sim_maker.txt at the repo root. Being worked on in a separate Claude session from the one that found and fixed the maxStripLength bug below -- this page is the shared reference point between the two.

Motivation

Directly motivated by the single-electron gun @ 45° page: that page set out to test the FTT geometry transform with a controlled, known-kinematics single track, and found that no MC-compatible code path in this repo actually reaches StFttDb --

  • StFttClusterPointMaker::MakeGeantPoints() (what script/sim.C and therefore all particle-gun/Pythia MC uses) reads GEANT truth directly in global coordinates and never calls StFttDb at all.
  • StFttFastSimMaker (the "fttSim" BFC tag) also reads GEANT truth, but writes into an unrelated StRnDHit collection using its own standalone geometry, independent of StFttDb, and unused by anything downstream.
  • StFttRawHitMaker -- the true entry point to the real cluster-making chain -- never reads GEANT truth at all; it only unpacks real raw DAQ data or an already-existing MuDst.

So the actual bug that turned out to explain the swapped/bowtie-shaped FTT footprint (StFttCluster::maxStripLength() defaulting to -999, full writeup at fttgeom/index.html) was found and fixed by reading the code and computing the StFttDb transform by hand against real data -- not by a controlled single-track test, because no such test was possible. StFttSimHitMaker is meant to close that gap for the next one.

Status

Proposal only as of 2026-07-17 -- not started, not urgent (the bug it would have helped find is already found and fixed by hand). See proposal_ftt_sim_maker.txt for the full design: two candidate approaches (inject synthetic StFttCluster objects directly, or the preferred option, inject synthetic StFttRawHit objects and let the real StFttClusterMaker do the clustering, reusing StFttDb::reverseHardwareMap()/hardwareMap() to avoid needing any new StFttDb code), rough scope (half a day to a day), and the reasoning for doing this in a separate session rather than folded into the bug-hunting one.

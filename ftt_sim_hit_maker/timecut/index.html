Goal / Method

  • Source: production p+p 500GeV MuDst, run 23081004, 2000 events (st_fwd_23081004_raw_6000003.MuDst.root).
  • Driver: script/checkFttTimeVsUuid.C (chain: StMuDstMaker + St_db_Maker + StMuDst2StEventMaker + StFttDbMaker + StFttHitCalibMaker, no StFttClusterMaker -- every raw hit is inspected, not just ones surviving a time-cut-gated clustering pass).
  • X axis = per-(VMM,FOB) uuid, computed exactly as StFttHitCalibMaker::Make() computes it internally: 
    UShort_t fob  = (UShort_t)mFttDb->fob( rawHit );
UShort_t uuid = rawHit->vmm() + ( StFttDb::nVMMPerFob * fob );
    confirmed identical, line for line, to what's actually used to key the real per-channel calibration (StRoot/StFttHitCalibMaker/StFttHitCalibMaker.cxx:103-104) -- not a separate/approximate indexing scheme.
  • "RAW" = hit->dbcid() as unpacked, before any per-channel anchor subtraction. Plotted over its full measured range [0,4096) (a 12-bit counter), not an arbitrary window.
  • "CORRECTED" = StFttHitCalibMaker's own hit->time() (dbcid - dbcidAnchor[uuid]), only filled once that channel's helper is ready() (>200 samples) so cold-start sentinel (-4097) hits are excluded. Plotted over ±1000 to see the whole pedestal shape, not clip it.
  • Both 2D plots use SetLogz so the sharp per-VMM peak and the much lower-rate surrounding structure are both visible together.

Bug found and fixed (2026-07-22): StFttDb::quadrant() checked its "already mapped" sentinel against the wrong constant, so the fallback to the real quadrant never fired -- the per-VMM time-calibration anchor (computed earlier in the chain than hardware mapping runs) silently merged all 4 quadrants sharing a (plane,feb,vmm) into one shared anchor:

-    if ( hit->quadrant() < nQuad )        // nQuad=16 (total, all 4 planes) -- wrong bound
+    if ( hit->quadrant() < nQuadPerPlane ) // =4, matches StFttDb::plane()'s own check
         return hit->quadrant();
     return hit->rdo() - 1;

Separately found and also fixed: HitCalibHelper::time() did dbcid - dbcidAnchor[uuid] with no handling for dbcid's 12-bit (4096) rollover -- a channel whose true peak sits near the 0/4095 edge got split into two disconnected sub-peaks by the naive subtraction. Now wraps to the shortest signed distance. The 3rd row below shows this fix on top of the quadrant fix.

Mechanism: the merged "anchor" is just whichever quadrant is loudest

HitCalibHelper's self-calibrating anchor is dbcidAnchor[uuid] = mode-of-histogram. Under the bug, that histogram was the SUM of up to 4 real quadrants' distributions sharing a (plane,feb,vmm). Checked directly (script/checkQuadrantMergeEffect.C, feb=0/vmm=0, all 4 planes, bypassing the bug by using hit->sector()/rdo() directly for ground truth):

Not random pickup -- deterministic "highest-occupancy quadrant wins." Quadrant C has the most raw hits of the 4 in all 4 planes for this feb/vmm, and the merged anchor lands exactly on quadC's own peak every time. Quadrants A/B/D silently get corrected against quadC's anchor instead of their own, offset by anywhere from a few hundred to ~2000 dbcid units -- the direct source of the secondary bumps around ±700-800 in the buggy 1D plot above (the aggregate, across all feb/vmm/plane slices, of many individual offsets like these). Caveat: dbcid is a bounded 12-bit counter, so very large naive peak differences near the 0/4095 edge could in principle reflect wraparound rather than a true offset -- doesn't change the qualitative conclusion.

Did this cost us anything in production?

Checked directly: hit->time() (the value this bug corrupts) is read in exactly two places in the whole repo, both inside StFttClusterMaker::PassTimeCut()'s kTimeCutModeDB/kTimeCutModeCalibratedTime branches -- both unreachable when mTimeCutMode == kTimeCutModeAcceptAll, which returns true immediately without ever touching hit->time(). Since production defaulted to AcceptAll until this session's time-cut investigation changed it, this bug was silently dormant in all prior production running -- no real signal was ever lost to it, because nothing was ever cut on the value it corrupts.

Findings

  • 18,380,903 raw hits total; 98.4% had a ready, non-sentinel corrected time by the time this 2000-event sample finished (cold-start warm-up is a negligible effect at this statistics -- occupancy is high enough that every active VMM clears the 200-sample threshold almost immediately).
  • Coverage, post-fix: 372 of 384 possible uuids (VMMs) show real hits. Broken down by (plane,quad), every single one of the 16 combinations is fully populated (24/24 = 6 febs × 4 vmm) EXCEPT disk1/quadA, which is exactly half-populated (12/24, feb 0,2,4 only) -- matching this session's earlier, independent, direct sector()/rdo()-based check of that one region exactly. Before the fix, the buggy quadrant() merged all 4 quadrants into 1 slot per (plane,feb,vmm), making it look like only ~96 uuids (4 disks × 1 merged "quadrant") had any data at all -- the detector is essentially fully instrumented in this file; that was a software artifact, not a hardware coverage problem.
  • CORRECTED time pedestal is narrower than it first appeared: with the quadrant bug merging up to 4 different real per-quadrant timing offsets into one shared anchor, the pre-fix pedestal looked broad and nearly flat out past ±800-1000. Post-fix, each VMM's anchor is computed from its own genuine (single-quadrant) dbcid distribution, and the resulting pedestal is visibly bounded, falling to ~0 by roughly ±300 -- a real calibration-quality improvement, not just a coverage one. The sharp peak at time=0 is still only a few × the local background at its base, so the core finding (current production's AcceptAll time-cut mode lets substantial out-of-time noise into clustering) still stands, just with the noise now more precisely characterized as bounded rather than unbounded.
  • A handful of individual uuids (visible as thin near-vertical lines spanning the entire dbcid/time range in both 2D plots) look like isolated bad/noise channels with flat, structureless dbcid distributions -- plausibly related to the "ffff! FFFF!" corrupted-word warnings seen in every run's stderr this session. Not investigated further yet.

2. Cause: HitCalibHelper::ready() counted distinct values, not hits

A hit gets time = -4097 (always cut) until its VMM is "ready":

-  return ( ... dbcidHist[uuid].size() > MIN_BCID_SAMPLES );   // number of DISTINCT dbcid values
+  return ( ... nSamples[uuid]         > MIN_BCID_SAMPLES );   // number of hits
  • A well-timed VMM puts its hits on a few dbcid values, so it can stay "not ready" forever; a noisy one gets ready fast. On sparse data the cut keeps noise and drops clean channels.
  • Harmless while production used AcceptAll; decisive once the calibrated cut was enabled.

3. Per-run anchors instead of per-file warm-up

VMM anchors are reset at random at every run start, so they must be measured per run. Measuring them once from enough events removes the per-file warm-up entirely.

  • StRoot/StFttDbMaker/macro/FttDataWindows/fttDataWindow.C -- MuDst (or list) for one run → fttDataWindow/fttDataWindow.<run>.txt, png/, root/, plus one line in fttDataWindow.<year>.QA.txt.
  • Raw dbcid per VMM; anchor = most populated dbcid; runs until 95% of active VMMs are calibrated.
  • Accepted if the in-window fraction is ≥ 0.7 × run median; otherwise kept if within 20 ticks of its FOB's median anchor; otherwise anchor = -1 (no calibration).
  • The window is measured per VMM as well: the in-time crossing, against a background taken at the same phase (t + k·4.263, k = ±1..6), grown outward from the peak until it holds 95% of that crossing. It is then widened if needed to contain [-1,3], the one-crossing window of section 5: the fit may only open a VMM's cut further, never tighter, so a thin measurement cannot throw real hits away. Measured median on AuAu runs 24192016/17: [-1,3], with ~3% of VMMs opening to -2 or -3. VMMs with anchor = -1 keep the wide [-65,100].
  • StRoot/StFttDbMaker/macro/FttDataWindows/fttDataWindow_db.C -- reads one run or all files, gets startRunTime from RunLog, stores and reads back. Refuses to store poor calibrations unless forced.

All zero-field runs are now calibrated (2026-09-21, one condor job per run, script/submit_fttcal.pl + script/runfttcal, one MuDst per run read in place):

Each dataset directory holds fttDataWindow.<run>.txt (the calibration), qa/ (one QA line per run, plus 0_header.qa so cat *.qa prints a header first), png/ QA plots, and empty/ for runs with no usable FTT data — those are kept OUT of the calibration directory on purpose: such a file is syntactically valid but full of anchor -1, and a consumer that loaded it would reject every hit of that run. The per-VMM dbcid histograms (root/, 25 MB) and the condor logs are not copied here; they stay in fttcal/ in the working area.

Reading the QA table

Columns: run, date, time, nFiles, events read, raw FTT hits, then VMM counts (nOK, noisy = noisy-FOB but usable, fFob = anchor taken from the FOB median, lowS = too few hits, rej = failed the quality cut, dead), then the fraction of hits inside the window (all, H, V, diagonal H, diagonal V) and the stop reason.

stop = endOfInput does NOT mean "needs more events". It means the file ended before 95% of active VMMs were calibrated, and it covers two different situations:

  • No FTT at all (3 runs, all early 2022): 6-12k events read, ZERO raw hits, all 384 VMMs dead. More events cannot help; these are the empty/ runs.
  • Rejected VMMs, not statistics (19 runs in 2022, all 13 in 2024): millions of raw hits, lowS = 0 or 1, so every VMM had plenty of data. 2024 misses the threshold by about two VMMs — 340 OK + 8 noisy = 348 good of 369 active = 94.3%, against the 95% required. The early-2022 ones miss by more (24-59 rejected). The calibration written is still good for the VMMs that passed; only the "converged" label is missing. Either relax goodFrac to ~0.92, or find out why those VMMs are rejected — 2024 rejects the same 20 in every run, which looks like a fixed set of bad channels rather than a statistical effect.

2024 needs a look before use: its in-window fraction is 0.42 against 0.89 for 2022, worst on the diagonal-H strips (0.32). With per-VMM anchors applied, that says the [-65,100] window sits much less well on the 2024 signal than on 2022.

  • uuid = StFttDb::vmmId(), 0-based 0-383 (idl comment fixed on dev, PR #20).

  • DB entries have a begin time only. A run with no entry of its own gets the previous run's entry -- whose anchors are wrong for it. So _db writes the run number into the spare slot 384 (uuid -1, min = run/10000, max = run%10000), and StFttDbMaker uses the anchors only if it matches the run. Windows are used either way.

5. Corrected time: field ON vs OFF, and does the cut make sense?

Corrected time = dbcid - per-run anchor, all calibrated VMMs (script/plotFttCorrectedTime.C).

field ON 23081049 (2.09M hits)field OFF 23063028 (0.32M hits)unit area, log

Out-of-time hits come in bunch crossings

  • The field-on plateau is periodic with 4.263 ticks (periodogram FWHM 4.23-4.30). RHIC bunch spacing is 106.6 ns (9.383 MHz), and 40 MHz / 9.383 MHz = 4.263.
  • So one tick = 25 ns, and each bump in the plateau is one out-of-time bunch crossing. (Inferred from the period; to be confirmed with the electronics.)
  • The in-time crossing is narrow: at zero field 72% of all hits are in t = [-1,1].
1-tick zoom: data and pileup backgroundperiodogram (red: 40 / 9.383)

Background model and window choice

Pileup at time t is taken from the same phase in the neighbouring crossings: bg(t) = mean of counts at t + k×4.263, k = ±1..±6, interpolated between ticks, excluding neighbours inside the in-time crossing (|t + k×4.263| ≤ 3). A linear slope of the plateau cancels. Signal = hits - bg. signal fraction = signal / hits in window; signal kept = signal relative to the DB window [-65,100]. (script/checkFttTimeComb.C)

  • Field ON, DB window [-65,100]: only ~9.5% of the hits kept are in-time. A flat-plateau estimate gives ~27% because the crossings are densest near t = 0.

  • Field ON "signal kept" for tight windows is ~0.83. At ~1.1M background hits in the wide window a 1% subtraction error is ~11k hits (~10% of signal), so this is either real broadening with field or estimate noise. The field-OFF value (0.99) is the cleaner number.

  • Direct check with field on: time of FTT hits matched to tracks vs unmatched hits.

6. Other changes

  • StFttDb::getTimeCut(): a VMM with no data-window entry returned an uninitialized mode and window. StFttClusterMaker defaults to kTimeCutModeDB, so this reaches every chain that does not call SetTimeCut() (BFC, simulation). Now defaults to mode 0, [-65,100] (the current DB entry), warns once per run, and clears windows before each load so a failed DB fetch cannot keep the previous run's entry.
  • StFttHitCalibMaker reports how many hits were timed from the DB anchor, on the fly, or not at all.
  • fwd_afterburner_db.C calls chain->Finish() again, so that report and all outputs are finalized while the chain is intact.

The tight window measured on production data (2026-09-21)

The [-1,3] window proposed above was tested against the loose [-65,100] window on real production output: four afterburner campaigns, 10 files each, zero field (run 23063028) and reversed full field (run 23081015), all with per-run per-VMM anchors (fttDataWindow/fttDataWindow.<run>.txt, shipped to the jobs), calibrated-time cut mode, and the FST gap fix, FST mirror and FTT X/Y mirror all ON. Only the window differs within each field setting.

The metric is how well tracks fitted without sTGC hits find those hits, measured with the FST-blind diagnostic (the track knows no FTT hit when the search is made). Note the diagnostic is filled once per track TYPE (Global, BLC, Primary, FwdVtx, BLCVtx), so excess and purity mix them; only the usage fraction is Global-only: excess = peak over local sideband at the projection point, purity = background-subtracted peak entries / all matched entries, usage = fraction of Global tracks with a hit used on an FTT plane. One line per campaign from script/fttMatchSummary.C.

What it says

  • Field on: the tight window is a clear win and costs no tracks. Purity 10.5 → 16.2%, excess 1.04 → 1.36, background under the peak 6.6× lower (157.9k → 23.9k per bin, disk 0 V). Track yield is unchanged (61.0 per event both ways) and the fit is better: <χ²> 17.6 → 15.1. 93% of the matches survive.
  • Zero field is insensitive to the window, as expected with no pileup: purity 23.3 vs 23.1%, excess 1.81 vs 1.84. That makes zero field the clean measurement of what the cut costs in real signal: the background-subtracted peak falls 7%, so [-1,3] keeps ~93% of genuine in-time hits — the field-off number from the 2026-09-14 table (0.99) was optimistic, this is the measured one.
  • The number of real matched hits goes UP with the tighter window, 304k → 429k (+41%), while matched track-disk pairs fall only 8% (2.89M → 2.65M). Cutting hits away cannot create real hits, so the first guess was that the window cleans up clusters. It does not — see the peak width below. What actually happens is that the loose-window background subtraction was eating the signal.
  • Zero field is still ~1.5× better than field on after the cut (23% vs 16% purity), so roughly half the remaining field-on deficit is not out-of-time pileup: it is in-time pileup plus tracking quality in the field.
  • V strips keep beating H strips (zero field 1.84 vs 1.51; field on 1.36 vs 1.31). Unexplained.

Why the "extra" real hits appear: the true match is broad

Fitting the background-subtracted peak (Gaussian, |d|<1 cm) shows the genuine FST→sTGC match is not a sharp spike:

sampledisk0 Vdisk0 Hdisk1 Vdisk1 H
field on, looseσ 0.12σ 0.05σ 0.09σ 0.05
field on, tightσ 0.45σ 0.32σ 0.42σ 0.32
zero field, looseσ 0.65σ 0.38σ 0.48σ 0.50
zero field, tightσ 0.63σ 0.33σ 0.48σ 0.50

Zero field gives the same width with either window, σ = 3-6 mm, and field-on with the tight window agrees with it. Field-on with the loose window is the odd one out: an artificially narrow 0.5-1.2 mm core. The reason is the sideband: with 6.6× more pileup the local background window (1-3 cm) contains a large part of the broad signal itself, so subtracting it removes real signal and leaves only the narrow core. The tight window lowers the pileup until the broad component stands clear.

So the +41% is recovered signal, not new hits and not better clusters. The excess ratio (1.04 → 1.36), the 6.6× background drop and <χ²> 17.6 → 15.1 are the definition-independent statements; the purity numbers move partly because the loose-window measurement under-counts its own signal.

The real width is worth its own look. A 3-6 mm match width is much larger than the sTGC strip pitch, so it is dominated by FTT position/alignment plus the FST-only projection. In zero field the fitted peak centres are also offset from zero, per disk and per orientation: disk0 H +4.4 mm, disk1 H +1.7 mm, disk3 H -2.3 mm, disk0 V -1.5 mm, disks 1-2 V consistent with 0. Those are sTGC alignment offsets, measured with straight tracks and no field.

Caveat: the geometry switches were not varied

All four campaigns ran with the FST 1° gap fix, the FST wedge mirror and the FTT X/Y mirror ON together, so these numbers do not separate the window from the geometry corrections, and they do not say what the FST wedge flip or the FTT X/Y flip is worth on its own. A dedicated zero-field A/B of the three switches at fixed [-1,3] window is the next measurement — zero field is the better place for it, since its excess (1.8) and purity (23%) are far above the field-on values, and straight tracks make a geometry error show up directly.

Goal

  • Replace StFttSlowSimMaker's flat 1:8:1 3-strip model with a real, measured profile.
  • Source: production p+p 500GeV MuDst, run 23081015, 2463 events.

Method

  • No existing FTT cluster QA tool found; StMuFttCluster has no row(), and the cluster↔rawhit link (StMuFttUtil::rebuildRelationships()) is an empty stub — so re-clustering from raw hits directly, in a new StRoot/StFttChargeSharingMaker.
  • Time cut: real per-VMM anchor learned online from each VMM's dbcid mode (same algorithm as StFttHitCalibMaker, 200-sample threshold), window [-65,100] (confirmed from DB, constant for every VMM this run).
  • Re-clustering: same algorithm as StFttClusterMaker (max-ADC anchor, expand while adjacent + non-increasing ADC). Note: real threshold is currently unset (GetThresholdFor() stub returns 0) — any nonzero ADC, including noise, can join a cluster.
  • 57.9% of raw hits pass the time cut; 5,634,704 clusters from 2443 analyzed events.

First peak in cluster total ADC (sumAdc≈50-100)

  • That peak is essentially all nStrips==1 clusters (split sumAdc by multiplicity: n=1 peaks at sumAdc≈90 and is nearly gone by 300; n≥2 peaks at sumAdc≈220 and dominates above that).
  • Per-channel raw ADC (before any clustering, straight from MuDst) has a hard floor: zero hits below ADC≈15, sharp rise, broad hump ≈60-90, then smooth decline. This is a real hardware/DAQ zero-suppression threshold already in the data — not from our clustering (whose own threshold is off/0).
  • So the low-sumAdc peak = real single-strip hits whose only one strip (and no neighbor) cleared that hardware threshold. Not an artifact of this analysis.
  • Real hit vs. noise: can't fully separate without a pedestal run, but the shape argues for real hits — the n==1 decline spans ~300 ADC counts, much broader than a narrow noise excess sitting just above threshold would give; looks more like the natural low-charge tail of real hits being clipped by the threshold.
  • Comb/moiré pattern in the ADC plots is a binning artifact (200 bins over 0-1024 vs. integer ADC values), not physical.

Caveat

  • Falloff vs. offset is much heavier-tailed than a clean Gaussian (roughly ×2 drop per strip out to ±4, tail out to 10 strips).
  • Zero threshold means noise and unrelated pileup (busy p+p event, wide time window) can inflate the tails — not separated from genuine single-hit charge spread.
  • Decided: full deconvolution (threshold + pileup jointly) is more than a tracking detector sim needs. Model scope limited to center strip ±1 (below).

Model implemented in StFttSlowSimMaker

  • Gaussian(σ) charge response, split over center strip ±1 only (far tail dropped — small, 2.8% of clusters, likely pileup/noise contaminated here).
  • σ=2.4mm (pitch=3.2mm), fit to the clean nStrips==3 ratio 25:48:25.
  • Split uses the TRUE sub-strip hit position (previously discarded by rounding) — asymmetric per hit, not a fixed ratio; restores the real charge-division resolution benefit.
  • Total charge/hit: exponential draw, mean=431.5 (measured sumAdc mean=RMS), drawn ONCE per truth hit and shared between the intended + diagonal orientation (same foil, same physical charge deposit — see X-U/Y-V correlation check below).
  • ~70 ADC threshold applied once, after summing all contributions per channel, to neighbor strips only. Center strip is always kept (floored to threshold if the draw came in low) — a naive all-3-strips threshold silently dropped ~30% of truth hits entirely, an unintended efficiency loss (this project keeps efficiency at 100% for now, see TODO on main page).

Same-foil charge correlation (X-U, Y-V)

Vertical(X)+DiagonalV(U) share the front foil; Horizontal(Y)+DiagonalH(V) share the back foil — same physical charge deposit, two differently-angled strip layers. Checked whether that shows up as a real correlation.

1st pass: sum of all hits in the event (too easy)

  • Total in-time ADC per plane/quad/event, one layer vs. the other — NOT per-cluster, just aggregate occupancy.
  • Both show a clear diagonal ridge: correlation coefficient 0.60 (X-U), 0.81 (Y-V).
  • Diagonal layer consistently collects less total charge: U/X mean ratio 0.59, V/Y mean ratio 0.60 — same ratio on both foils, looks systematic (diagonal-strip geometry/gain), not noise.
  • But: this correlates almost trivially just from occupancy (more hits ⇒ more charge on both layers together) — doesn't test whether individual CLUSTERS match.

2nd pass: cluster-by-cluster, all combinations

  • Every (X-cluster,U-cluster) combination within the same plane/quad/event (same for Y/V) — true matches should sit on top of the combinatorial background from unrelated pairings.
  • No peak survives: correlation coefficient drops to 0.017 (X-U), 0.028 (Y-V) at full statistics (51M / 55M combinations). The ratio histograms (U/X, V/Y) are smooth and featureless, no bump near 0.6-0.8 — pure combinatorial background swamps any real signal.
  • Why: ~144 clusters per (disk,quad) per event combining all 4 orientations (~36 per single orientation) — a p+p event doesn't have that many real particles per quadrant. Cross-checked against PRODUCTION's own already-reconstructed StMuFttCluster count (not just this re-clustering) for the same 40 real events: production shows the SAME order of magnitude (~1000-2700 clusters/event). Not a bug in this analysis — StFttClusterMaker::GetThresholdFor() is a real, still-unimplemented stub (returns 0) in production too, so real reconstruction is currently just as noise/pileup-dominated as this re-clustering.
  • Tried requiring EXACTLY 1 X-cluster + 1 U-cluster (no combinatorial ambiguity at all) to isolate clean pairs: zero such plane/quad/events exist anywhere in the full 2463-event file. Occupancy is uniformly too high, everywhere, all the time, in this sample — there's no quiet corner to exploit.

Threshold efficiency: is the hardware threshold cutting real hits? (2026-10-17)

This section is a hypothesis with numbers attached, not a measurement of the detector. It is written down so it can be tested and, if wrong, discarded.

Where it comes from

The simulator's charge model is now driven by the GEANT energy deposit (details): totalAdc = mAdcPerKeV × Σde × gainFluctuation(). Once that model reproduces the measured ADC spectrum above threshold, it can be extrapolated below threshold to ask how many real particle crossings never produce a recordable strip at all.

First, how well is the gain actually pinned?

This matters, because the whole estimate rides on it. mAdcPerKeV was tuned so the MC cluster peak-strip ADC matches the real one — but the real distribution only exists above threshold, so that tuning is partly circular. Re-fitting using only peak ADC in 150-1000 (far above the 70-ADC threshold, and free of the simulator's centre-strip floor):

The minimum is broad and flat from 450 to 600, so the gain is known only to about ±20%. That is the dominant uncertainty on everything below, and it cannot be reduced without data below threshold — which by definition does not exist.

Efficiency, with the simulator's artificial floor removed

The simulator currently floors the centre strip up to threshold, which forces 100% efficiency by construction. That was a deliberate placeholder. Removing it, at the real 70-ADC hardware threshold:

The hypothesis

  • The 70-ADC hardware threshold costs 16-29% of real crossings, most likely around 20-24%. Those particles cross the gas, deposit energy, and never produce a recordable strip. This would be a real detector inefficiency present in the data, not a software bug and not recoverable offline.
  • The threshold sits on the steep part of the curve — between 40 and 100 ADC the efficiency falls from 93% to 58% — so it should vary chamber to chamber and run to run with the gas gain.
  • If true, a per-plane efficiency of ~76-84% is a long way from the ~100% implicitly assumed when calling the FTT hit pickup from VTX+FST tracks "low", and would account for a large part of it.

How to test it, and why the obvious test is the weaker one

The obvious test — take tracks with hits on 3 of the 4 FTT planes and ask how often the 4th has a hit — is model-independent, but it has two problems. It selects on FTT itself, so it is biased towards efficient regions; and the 3-hit requirement is combinatorially punishing exactly when efficiency is low, which is the case it is meant to diagnose. At 80% per plane it is fine (82% of tracks have 3 or more), but at 20% only 0.8% of tracks would qualify and random combinations would dominate the sample.

Projecting VTX+FST tracks onto the FTT is the better tool, because the track selection never touches the FTT and so cannot be biased by it. Its weakness is the opposite one: the pickup number mixes detector efficiency with projection accuracy and alignment.

The way to separate those two: measure pickup efficiency as a function of the search window size. If it plateaus, the plateau is the detector efficiency and the approach to it measures the projection resolution. If it keeps climbing with the window, projection accuracy dominates and the detector efficiency cannot yet be read off. The number predicted here, ~76-84%, is what the plateau should sit at if this hypothesis is right.

X–U / Y–V charge correlation: found (2026-10-21)

The 2nd pass above concluded that no cluster-by-cluster correlation survives the combinatorial background. That conclusion was right about the data it had and wrong about the cause: it was not the detector, and not the threshold. It was the time window. Repeating it with a per-VMM time cut — which did not exist then and does now, from Calibrations/ftt/fttDataWindowsB — the correlation appears.

What it says

  • The old null result reproduces exactly in the first row: 1082 combinations per (plane,quad,event), all‑combination correlation +0.016, and zero clean 1+1 pairs in 1034 events — the same "no quiet corner exists" the 2nd pass reported.
  • One change fixes it. Same file, same self‑calibrated anchors, window [-65,100] → [-1,2]: combinations fall 1082 → 17 and 607 clean pairs appear with correlation +0.693 (Y–V: 713 pairs, +0.701). Nothing else was touched — not the threshold, not the clustering.
  • The per‑VMM window from the database gives the same answer as a flat [-1,2], which is the expected result: the measured run‑median window IS [-1,2].
  • Zero field was already clean — about one cluster per orientation even with the wide window, so the cut buys little there. ZF gives clean pairs for free; high luminosity gives them only with the cut. Two independent routes to the same physics.
  • The ratio is ~1.0, not 0.6. On clean pairs: 0.98–0.99 (high lumi), 1.16 (zero field). The 0.59/0.60 from the 1st pass was an event‑sum artifact: the diagonal orientations carry fewer clusters (dH 28.0, dV 25.8 against H 42.7, V 41.9), which drags a summed ratio down even when the per‑cluster charge is equal. So StFttSlowSimMaker injecting the same charge into both layers of a foil looks right, and no sim change is called for on this evidence.
  • The high‑lumi clean pairs are also the tighter distribution — rms 0.48 against zero field's 0.71 — so that is the better sample for characterising the ratio, not the worse.

The zero-field anchors were the problem, and the DB fixed them

When this was first run, the 48 zero-field runs of 2022 were not in the database at all — their calibration existed only as files — so run 23072005 took 0 DB anchors and fell back for all 102553 hits. They were pushed on 2026-10-21 and the run repeated; that is the highlighted zero-field row above, and everything moved the right way:

  • in-time 51.7% → 86.8%, with 161378 hits on a DB anchor and 2823 falling back. A third of the real zero-field hits had been thrown away by a self-calibrated anchor that was simply wrong for this run.
  • event-sum correlation +0.711 → +0.849 (X–U) and +0.579 → +0.750 (Y–V).
  • clean 1+1 pairs 562 → 816 at +0.701 → +0.722; Y–V 441 → 583 at +0.473 → +0.676.
  • the ratio moves toward unity: 1.155 → 1.086 (U/X), 1.127 → 1.097 (V/Y) -- the direction the high-luminosity sample already pointed.

More real hits means more clusters, so the combination count rises, 1.2 → 3.8, even though the measurement got better: the wide window is still letting the out-of-time tail through. That is the one thing still missing for zero field, a fitted per-VMM window. The ZF calibration files predate the window fit and carry the flat [-65,100] for every VMM, so only the anchors were pushed -- pushing them as an "update" would have replaced the fitted windows of the 13 ZF runs already in the database with the flat one. Refitting those runs from their saved histograms is what remains, and should take the ZF combination count back toward one. High luminosity never had this problem: 23081049 is in the Run 22 set and 10.4M of its 10.9M hits took a DB anchor with a fitted window.

If the ratio holds up it is not a number for tuning the simulation — it is a pairing discriminant: tight around 1.0 for true pairs, flat for accidentals, which is exactly the handle sTGC space-point making needs to decide which X cluster belongs with which U cluster.

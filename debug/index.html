23 LOW EPD StFwdHitLoader.cxx : 678

EPD covariance matrix was hardcoded to σ_xy = 4 cm (isotropic), ignoring actual tile geometry.

EPD tiles are trapezoidal with very different radial (σ_r ≈ 1–2 cm) and azimuthal (σ_φ·r ≈ 3–8 cm) extents. A fixed isotropic 4 cm is wrong for every individual tile. Furthermore, for a tile not aligned with the x or y axis, the (x,y) covariance has a non-zero off-diagonal term C_xy = (σ_r² − σ_s²)·cos φ₀·sin φ₀, which was also missing.

The comment in the code already said "make the covariance matrix based on max x and y distance" but the tile corners returned by StEpdGeom::GetCorners — already available in the same scope — were unused.

For a uniform distribution over a convex quadrilateral, the exact covariance matrix is C = (1/3) × (mean of corner outer-products relative to centroid), which simplifies to dividing the summed squared deviations by 12:

cxx/12  cxy/12
cxy/12  cyy/12    where cαβ = Σ_k (α[k]−α0)(β[k]−β0)

This is exact for rectangles and parallelograms, and a good approximation for the mildly trapezoidal EPD tiles.

Replace hardcoded σ_xy = 4 cm with corner-derived covariance:

double cxx=0,cyy=0,cxy=0;
for(int k=0;k<4;k++){
    double dx=x[k]-x0, dy=y[k]-y0;
    cxx+=dx*dx; cyy+=dy*dy; cxy+=dx*dy;
}
hitCov3(0,0) = cxx/12.0;
hitCov3(1,1) = cyy/12.0;
hitCov3(0,1) = hitCov3(1,0) = cxy/12.0;
hitCov3(2,2) = 1.0; // σ_z = 1 cm

σ_z² = 1 cm² retained (tile thickness ≈ 2 cm; conservative).

 Correct per-tile σ_xy (1–5 cm depending on tile) and non-zero C_xy for off-axis tiles. EPD is a soft measurement so numerical impact on pT resolution is small; correctness matters for χ² and pull distributions. Tested 2026-06-23 (sim, 1000 events, ele.pt1.5.vz0, combined with Crit2_DeltaRho seeding fix): numerical impact on pT resolution confirmed negligible (Primary σ(q/pT) = 0.222 GeV−1 at pT=1.5–3 GeV, same as before).

FST Covariance Study

Background

Bug 6 previously fixed makeFstCovMat() to apply σ = pitch/√12. A systematic investigation (2026-06-16) tested five digitization variants to understand why the mathematically correct pitch/√12 underperforms. The study also examined StFstFastSimMaker (STEVENT path) as a reference for correct strip positions.

GEANT path vs STEVENT (StFstFastSimMaker)

setFstHitSource(0) = GEANT direct: reads raw g2t_fts_hit, applies FstRasterizer (3.0 cm r-bins), then makeFstCovMat.
setFstHitSource(1) = STEVENT: reads StFstHitCollection from StFstFastSimMaker, which uses correct 2.875 cm strip centers (RSegment[]) and sets positionError() = pitch/√12 = 0.830 cm.

STEVENT strips are at r = {6.4375, 9.3125, 12.1875, 15.0625, 17.9375, 20.8125, 23.6875, 26.5625} cm (= kFstrStart[] + 0.5·kFstStripPitchR).
GEANT 3.0 cm raster strips are at r = {6.5, 9.5, 12.5, 15.5, 18.5, 21.5, 24.5, 27.5} cm — biased 0.06–0.94 cm outward growing with strip index.
Phi convention: MAXPHI = 128 strips/wedge × 12 wedges = 1536 global strips, pitch = kFstStripPitchPhi = 0.004091 rad.

Conclusions

  • All "correct" digitization variants are worse than the 3.0 cm rasterizer. Even GEANT FIX v3 (correct positions, unchanged full-pitch sigma) degrades FCS matches and DCA_Z — isolating the position change as the culprit, not the sigma.
  • GEANT FIX v2 ≈ STEVENT in all metrics: the STEVENT path is consistent when position and sigma conventions are properly matched (1536-strip phi).
  • sigma effect (v2 vs v3): pitch/√12 reduces convergence by ~200 tracks. Tight search windows after the first FST disk reject valid hits at subsequent disks.
  • Position effect (v3 vs REVERT A): same convergence, but track quality worsens. The seeding algorithm was developed and tuned against 3.0 cm raster positions; switching to correct 2.875 cm centers disrupts seed formation subtly.
  • STEVENT has fewer convergences than GEANT direct (5432 vs 5920) because StFstFastSimMaker merges GEANT deposits in the same strip into one cluster, reducing the number of hits available per track.

Current status

loadFstHitsFromGEANT restored to FstRasterizer (3.0 cm r-bins, full pitch r-sigma) — REVERT A baseline. FST φ-sigma is now tightened (pitch/√12) in a second KalmanFitter pass after the initial fit converges (pT Resolution Study, Issue #24) — this bypasses the seeding-window problem because tight φ is applied only post-convergence. FST r-sigma: full pitch retained; retuning seeding for correct 2.875 cm strip geometry is future work.

21 HIGH FTT StFttClusterMaker.cxx : 368
(real-data path only;
fast-sim uses sigXY=100 μm)

For single-strip clusters the charge 2nd-moment variance is identically zero (all ADC in one strip → m₂/m₀ = mean²). The existing code sets clu→setSigma(sqrt(var)) = 0.

This zero sigma flows into StFttClusterPointMaker::MakeLocalPoints() as covMatrix[precise][precise] = 0, giving GenFit's Kalman fitter infinite weight in the strip-crossing direction: the track is forced to pass exactly through the strip centre, overriding all other measurements and causing numerical instability in the covariance update.

Strip pitch = 3.2 mm (StFttDb::stripPitch). Minimum physical uncertainty = pitch/√12 = 0.924 mm. Position coordinates are in mm (x = strip × 3.2 − 1.6), so sigma units are mm.

 Clamp sigma to max(sigma_2ndmoment, pitch/√12): 
const float kSigmaMin = 3.2f / sqrtf(12.f); // 0.924 mm
clu->setSigma(
  std::max( sqrtf(std::max(var, 0.f)), kSigmaMin ) );

Applies only to the real-data path (mUseGeantData=false). The fast-sim path (MakeGeantPoints) already uses sigXY = 0.01 cm = 100 μm with correct covariance — unaffected.

 Prevents infinite Kalman weight for single-strip FTT clusters in real-data processing. Not yet tested on data (discovered 2026-06-22).

Context: how the sigma reaches GenFit

Chain: StFttClusterMaker::calcClusterProperties() → clu→setSigma() → StFttClusterPointMaker::MakeLocalPoints() → covMatrix[0][0] = clu→sigma() × clu→sigma() → StFttPoint::setCov(covMatrix) → StFwdHitLoader::loadFttHits() → GenFit::PlanarMeasurement rawHitCov.

The filter in StFwdHitLoader (line 177) skips hits where sqrt(hitCov3(0,0)) == sqrt(hitCov3(1,1)) (diagonal strips), but it does not skip hits with sigma=0 in one direction — those pass through to GenFit with a singular measurement covariance.

Issue #24 — FST φ-Sigma Warm-Start (pT Resolution)

Problem

Design target: σ(1/pT) ≈ 0.2 GeV⁻¹. Measured in perfect MC (ele⁻ gun, pT=1.5 GeV, η∈[2.5,4.0]): σ(1/pT) ≈ 0.815 GeV⁻¹ (>4× worse). Root cause: FST φ-covariance uses full strip pitch (0.004091 rad) instead of pitch/√12 (0.001181 rad), so the Kalman fitter underweights the φ measurement by 12×. Setting tight φ globally kills efficiency (Attempt 1 → eff <5%) because it also narrows the hit search window during initial seeding.

Solution (Issue #24): two-pass fitting — initial pass with full φ pitch for stable seeding, then a warm-start second pass (KalmanFitter, blowUp=10⁶) with tight φ after convergence. Applied to all five track types (Global, BLC, Primary, FwdVtx, BLCVtx).

Warm-start addition — where the new code lives

For the original tracking flow before this fix, see code/index.html — Tracking Flaw.

The warm fitter is inserted at the end of refitTrack(), after the normal FST+FTT+EPD refit converges, for all five track types (Global, BLC, Primary, FwdVtx, BLCVtx).

Cold start vs warm start

The initial global fit (mFitter = KalmanFitterRefTrack, blowUp=10⁹) is a cold start: the state covariance seed is blown up by 10⁹, so the fitter ignores the seed momentum entirely and converges from scratch using only the measurements. This is robust but must use a wide FST φ covariance (full pitch) so the χ² surface is smooth enough to converge.

The tight-φ pass (mWarmFitter = KalmanFitter, blowUp=10⁶) is a warm start: the seed is the already-converged state from the RefTrack fit (position + momentum within 10–30% of truth). The 10⁶ blow-up is large enough to let measurements pull the state, but small enough that the good seed prevents pT→∞ divergence. Starting close to the solution, the fitter can handle the tight FST φ (pitch/√12 ≈ 0.00118 rad) without going unstable.

Key design decisions

DecisionRationale
blowUpFactor=10⁶ (warm) vs 10⁹ (RefTrack) Large enough to not be dominated by old RefTrack fitter states; small enough that the warm seed momentum prevents pT→∞ divergence.
Re-seed from RefTrack fitted state (not original track seed) RefTrack fitted pT is already within 10–30% of truth. Starting from the good estimate avoids the pT→∞ blowup that kills cold-start fits with tight φ.
Filter by detId == kFstId (not sortingParameter) FST hits have detId=kFstId; FTT have kFttId; beamline/PV have kTpcId. Only FST PlanarMeasurements get tight φ covariance — beamline and EPD hits are unaffected.
No restore; use refreshFromTrack() Downstream fitTrack() calls (BLC, Primary, FwdVtx, BLCVtx) each create a new make_shared<genfit::Track>, so they never read the tight r+φ mFitTrack state. refreshFromTrack() re-syncs the scalar fields (momentum, charge, chi2, convergence) from the in-place tight r+φ fit without needing an extra RefTrack pass.
No deleteFitterInfo() Tested: BLC improved (0.814→0.781) but Primary regressed badly (0.568→0.684) and BLC efficiency dropped (98.4%→90.4%) because the warm fitter without prior FitterInfo fails to converge for vertex-constrained tracks. Reverted.

Strategy: warm-start KalmanFitter with tight r+φ (2026-06-24 extension)

After the RefTrackFitter converges (wide r+φ pitch, all hits found), inject a second pass using KalmanFitter (blowUp=10⁶) with FST r and φ covariance tightened in-place. All four elements of the 2×2 planar covariance are divided by 12: rawHitCov(0,0) /= 12 (radial), rawHitCov(1,1) /= 12 (azimuthal), rawHitCov(0,1) /= rawHitCov(1,0) /= 12 (cross-terms). On success, mFitTrack is left in the tight r+φ fitted state and refreshFromTrack() propagates momentum, charge, chi2, and convergence flags to the GenfitTrackResult. Applies to all five track types. Implemented in TrackFitter.h::warmFitFstTightSigma() (renamed from warmFitFstTightPhi() to reflect that both coordinates are now tightened).

Why tighten r in warm-start (but not in initial fit)?

The FST radial strip pitch is 2.875 cm. In the initial fit the full pitch is used as σ_r (keeping the Kalman search window wide so hits on subsequent FST disks are found). In the warm-start pass the hits are already associated — the Kalman fitter is not searching for new hits, it is refining the momentum estimate with the associated ones. Tightening σ_r to pitch/√12 ≈ 0.83 cm correctly weights the radial measurement, analogous to what the φ warm-start did for σ_φ.

Seed theta fix (2026-06-22, FitterUtils.h)

Bug: GenericFitSeeder::makeSeed() computed θ from seed[0]→seed[1]. When disks 0 and 1 rasterize to the same strip centre (common at η≈3 where Δr ≈ one pitch), dx=dy=0 → Rxy=0 → θ=0 → pz=pT/tan(0)=∞. Fix: always use seed[0] and seed[2] (outermost pair, 2× longer z-baseline, no degenerate case).

Issue #25 — Seed Curvature Sentinel Bug (B=0 Tracking)

Problem

Found while testing whether forward tracking works on B=0 (magnet-off) data (runSimFlat.C/runPythia.C fieldOff flag + sim.C UseZeroB → StFwdTrackMaker::setZeroB(), GenFit ConstField(0,0,0)). First attempt: 0 tracks of any type survived didFitConverge(), for a 50-event ele.pt1.5.vz0 sample — with the field on or off. Traced to three compounding bugs in GenericFitSeeder::makeSeed() (FitterUtils.h), the routine that estimates a seed pT/charge from the curvature of the outermost FST hit triple before GenFit's own Kalman fit runs. None of these are specific to B=0 — a genuinely straight (B=0) track's hits are collinear by definition, so it hits this code 100% of the time, but curved tracks with an accidentally-collinear or near-along-z hit triple hit it too (see the field-on control run below).

Bug 1 — collinear sentinel doesn't match its own filter

computeSignedCurvature():
    if (area == 0) {
        ...
        return -1e-7;   // "curvature undefined" sentinel

averageCurvature():
    if (curvature != -1) {   // BUG: checks -1, sentinel is -1e-7 — never matches
        totalCurvature += curvature;
        ++validCombinations;
    }

The collinear sentinel (-1e-7) silently passes the exclusion filter (which checked != -1, a different value) and gets averaged in as if it were a real, tiny, near-zero curvature measurement.

Fix: named constant kCollinearCurvature = -1e-7, used on both sides of the comparison so they can't drift apart again.

Bug 2 — "no curvature known" sentinel fed into the pT formula anyway

Once Bug 1 is fixed, a fully-collinear triple correctly returns the other, pre-existing sentinel: averageCurvature() returns -1 for "no valid combinations" (also used for "<3 points"). But makeSeed() still computed pt = fabs(K*5/qc) unconditionally — dividing by -1 gives pt ≈ 0.0015 GeV, a degenerate near-zero-momentum seed.

Fix: detect qc == -1 explicitly and fall back to pt = 10 GeV (matching the existing momSeed.SetXYZ(0,0,10) default already used elsewhere in this same function/class as the generic "assume roughly straight" placeholder — not a new number). Charge sign similarly defaults to +1 instead of sgn(-1), which had been silently biasing every degenerate seed to negative charge.

Bug 3 — completes the 2026-06-22 seed-theta fix (still not fully guarded)

The 2026-06-22 seed theta fix (Issue #24 card above) already found that Rxy=0 → θ=0 → pz=pT/tan(θ)=∞ when disk0/disk1 rasterize to the same strip centre, and mitigated it by switching to the wider disk0/disk2 baseline. That reduces but does not eliminate the risk — this test hit a real event where disk0 and disk2 also landed at identical (x,y) (p1=p2=p3=(3.2154, 5.649), differing only in z), still giving tan(θ)=0 and crashing StarMagField::Search() with a NaN assertion several frames downstream.

Fix: guard the division directly — pz = (fabs(tan(theta)) > 1e-6) ? (pt/tan(theta)) : (dz>=0 ? 10.0 : -10.0), same high-|pz| placeholder philosophy as Bug 2's fallback, sign-matched to direction of travel in z.

Why this matters conceptually (not just numerically)

GenFit's own fit parameterizes tracks by q/p, and q/p=0 (infinite momentum / straight line) is a perfectly valid, finite, well-behaved state — position and direction have essentially zero Jacobian sensitivity to q/p when curvature is genuinely unmeasurable, so a straight track's residuals don't depend on getting the seed momentum "right". All three bugs above are artifacts of this seeder's own curvature → pT → px,y,z conversion arithmetic (singular at the exact points a straight track lives), not anything fundamental about the Kalman fit itself.

Relationship to Issues #2 and #19 — not overlapping, three different points in the same pipeline

Issue #2 (addFttHits/addFstHits/addEpdHits) found blown-up Kalman states (pT=0.001–22000 GeV/c) reaching the hit-search stage, and explicitly records that an upper-pT guard was tried there and removed — "high-pT tracks are straight lines with valid projections; only truly degenerate zero-curvature states need guarding." Bugs 2/3 above independently converge on the same principle at the seeding stage (one step earlier): the fixes give a safe finite fallback for the degenerate (near-zero-curvature / near-along-z) case, and deliberately do not add an upper-pT cap — setupTrack()'s existing Perp()>1000 → (0,0,1) reset already covers a legitimately huge pT without needing a duplicate guard here.

Issue #19 already documented that GenericFitSeeder's curvature-based charge is "numerically unstable → wrong charge ~20% of events" for near-zero-curvature tracks — a real statistical/resolution limit of a 3-point circle fit, not a bug, and not something Bugs 1–3 above fix or need to fix. Its solution routes around this for BLC/Primary/FwdVtx/BLCVtx by inheriting the Global track's already-fitted charge (externalCharge parameter through setupTrack → fitTrack) instead of re-deriving it. But the Global track itself has nothing to inherit from — it's the one seed that still runs GenericFitSeeder::makeSeed() unguarded (externalCharge=0). That's exactly where Bugs 1–3 live, and because Issue #19 propagates Global's charge to every other track type, a defect in Global's own seed (the crash, or the deterministic-charge-bias sentinel bugs) doesn't stay contained to Global tracks — it silently propagates everywhere. Fixing Bugs 1–3 closes that gap; the pre-existing ~20% mis-charge rate for genuinely near-zero-curvature tracks is unrelated and, per Issue #19's own conclusion, not worth chasing further — consistency across track types matters more than the raw geometric precision, and none of this affects position/direction residuals either way (see "Why this matters conceptually" above).

Issue #27 — DCA Target/Method Bug in refitTrack() (Track Types 0–3)

Problem

GenfitTrackResult::setDCA(TVector3 pv) (GenfitTrackResult.h) picks point- vs line-extrapolation from mTrackType, and extrapolates to whatever pv it's given. refitTrack() (FwdTracker.h) builds a fresh GenfitTrackResult via fitTrack(), which never sets mTrackType (defaults to kGlobal=0), then unconditionally called setDCA(mEventVertex) at the end — regardless of the caller's real track type or intended vertex. Since setTrackRefit(true) is on by default (fwd_afterburner_db.C), this ran for every track, every event.

  • Global (0): no effect in practice — target/method happened to match by coincidence (default type is kGlobal).
  • Beamline (1): no effect — same target (mEventVertex) used before and after refit.
  • Primary (2): silently downgraded from point-extrapolation (true 3D DCA to vertex) to line-extrapolation once refit succeeded — same target point, wrong method.
  • FwdVtx (3): two bugs stacked — mTrackType was assigned after the (pre-refit) setDCA() call, so even the initial DCA used line- not point-extrapolation; and after refit, the target silently changed from the found forward vertex to mEventVertex, a different vertex.

Fix

refitTrack() now takes an explicit dcaTarget argument and propagates the caller's mTrackType onto the refit result before calling setDCA(), so every call site passes the same target it used for its own pre-refit setDCA(). Fixed the order bug in doSecondaryTrackFitting() (mTrackType now set before setDCA()). Also extended the point-extrapolation whitelist in GenfitTrackResult::setDCA() to cover kForwardVertexConstrained and kFCSConstrained, which are constrained to a literal 3D point same as Primary/BLCVtx.

Issue #28 — FTT Geometry & Reconstruction: 7 Fixes

Started from FTT hit-position maps showing a top/bottom + north/south swapped, bowtie footprint instead of an octagon; tracing it produced 7 fixes across the FTT reconstruction/matching chain. Full writeup, plots and evidence tables: FTT geometry page.

  • maxStripLength defaulted to -999 and was never set — the swap and bowtie.
  • maxStripCenter — off-axis strip position now per-strip, was one row-averaged constant.
  • Off-axis search gate — now gates both coordinates, previously dPhi/dR only, then dx only with no dy gate.
  • Covariance unit — hit covariance left in mm² while position was cm, a 10× error in sigma.

  • StFttPointMaker dropped all of disk0/quadrant A — 0-based fill read from iRob=1, affects StFttPoint/StMuFttPoint in production MuDst.

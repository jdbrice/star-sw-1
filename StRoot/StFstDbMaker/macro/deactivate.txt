WHAT WE ARE ASKING FOR
  Set deactive != 0 on the 11 entries listed below (438 rows).
  DEACTIVATE, NOT DELETE -- we want the rows to stay in the database so the
  history remains readable and the change can be undone.

WHY
  All 11 entries are dated 2021-10-25 and every one of them is the IDENTITY
  transform: t=(0,0,0) on every row, r00=r11=r22=1 and all six off-diagonal
  elements 0, in all four tables. Verified row by row, not assumed.

  2021-10-25 falls inside Gene's "real data: any time after that" window for
  run year 2022, i.e. after the 2021-10-10 ideal slot and the 2021-10-15
  survey slot (database_timestamp.txt). St_db_Maker takes the latest entry at
  or before the requested time, so these identity rows win over the FST survey
  we are about to write at 2021-10-15, for every real-data timestamp.

  Leaving them active would force two database entries for every future FST
  alignment update -- one inside the MC survey window and one after
  2021-10-25 -- and if either is forgotten, MC and real data silently run on
  different geometry with no error and no log line. Deactivating these keeps
  it at one entry per update.

NOTHING IS LOST
  The content of these entries is identity, and identity is exactly what the
  new ideal22 entry at 2021-10-10 00:00:00 provides. Anyone reproducing a
  Run 22 production that was reconstructed without the survey asks for a
  timestamp in [2021-10-10, 2021-10-15) and gets the same numbers.

WHEN
  Only AFTER we have pushed the new entries, never before. Between the push
  and the deactivation nothing changes for anybody: real data keeps resolving
  to these identity rows exactly as it does today. If it were done first there
  would be a window with no Geometry/fst entry at all below a real-data
  timestamp.

"StFttDb pick up xyz offsets from DB by default (switch to go back using old hardcoded

    Done, but the DESIGN changed and the slide should say which, because it is the part
    people will question. DB mode does NOT add the tables to StFttDb's hardcoded
    origins. It ignores them entirely and builds

        AGML nominal (placeholder) + stgcOnTpc + stationOnStgc + pentOnStation

    The tables were written as (StFttDb origin - AGML placeholder) + alignment, so the

    Consequence worth stating out loud: the misalign tables did NOT have to be
    regenerated, and geometry and hit positions now come from one source instead of two
    kept in step by hand.


3. TWO BUGS FOUND TODAY THAT ARE NOT ON THE SLIDE, AND SHOULD BE
-----------------------------------------------------------------
Both are the kind that pass every structural check and still give wrong physics.

a. Planar FTT was on the wrong plane. Nothing ever set _genfit_plane_index on an FTT
   hit, so every sTGC hit used mFttPlanes[0] = station 1 quadrant A. A PlanarMeasurement
   keeps only the in-plane components, so hits moved silently by up to 52 cm in z. It was
   harmless while kUseSpacePoints was true and went live the day planar mode was adopted.
   Relevant to the slide's "SpacePointMode=false as default" proposal: adopting planar is
   right, but it exposed this, and the same class of thing may still be lurking.

b. StFttClusterPointMaker asked for GetDataSet("fttDbMkr") -- the MAKER's name -- and
   static_cast the result to StFttDb*, so the pointer was always wrong. Invisible for
   years because getGloablOffset_ClusterPoint only read STATIC members, which need no
   valid this. The moment it read per-quadrant instance data it returned garbage and
   destroyed the FST->sTGC matching. Worth one line as a caution: "works today" is not
   evidence when the code only ever touched statics.

5. THE ONE THING I WOULD NOT OVERSELL
--------------------------------------
The per-quadrant residual left after all of the above is RADIAL, not a set of
translations. All four quadrants sit ~1-1.9 cm closer to the beam axis than the tracks
say:

    A (x>0,y>0)  dx -1.06  dy -1.94        C (x<0,y<0)  dx +0.55  dy +1.31
    B (x>0,y<0)  dx -1.26  dy +1.02        D (x<0,y>0)  dx +0.68  dy -1.39

Sixteen per-quadrant offsets can absorb that and will drive the residual to ~0, but if
the cause is a scale -- an FST radial error, the strip pitch, something else -- the
constants will not generalise to other runs or geometries. A pure z error cannot explain
it: that would need dz ~ 10 cm at r ~ 46 cm.
    -> I would show the radial plot and say plainly that the next step is to split a
       quadrant's residual by radius. Flat = genuine offset, sloped = scale. It is one
       plot and it decides whether these numbers are alignment or a band-aid. Saying that
       first is stronger than being asked it from the floor.

Also worth one line: the FST misalign propagates into the blind residual 1:1, not with
the vertex lever arm. dy moved +3.19/+3.25/+2.93/+3.01 mm across the four stations
against an FST move of -3.197 mm -- flat, where a vertex-anchored track would have
pivoted and given a 1 mm rise. That says the TPC vertex is contributing very little to
constraining these fits, which is worth knowing before anyone leans on vertex-constrained
forward tracks. dx behaves differently (factor 3.1) and is NOT understood -- better to
say so than to leave it out.

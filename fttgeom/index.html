FTT geometry: 7 fixes, and the follow-on matching investigation

Starting point was the FTT hit-position maps on the quadrant × charge page showing a top/bottom + north/south swapped, bowtie-shaped footprint instead of the expected octagon. Tracing that down led to 4 real fixes in the FTT reconstruction/matching chain, then to a follow-on question: even past these fixes, is the FTT hit a track picks up actually the right one? That investigation turned up 2 more real bugs, in the per-VMM time calibration.

The 7 fixes

  • maxStripLength: StFttCluster::maxStripLength() defaulted to -999 and was never set -- explains the full top/bottom + north/south swap and the bowtie shape, not just a shift. Full writeup on its own page.
  • maxStripCenter: the off-axis strip position is now set per-strip. It used to default to one row-averaged constant, shared by ~92% of same-row strips.
  • Off-axis search gate, three stages:
    • Originally: gated on a wide dPhi & dR only -- dR is a 1D difference of R=sqrt(x²+y²) from the beamline, not a real 2D distance, and blind to azimuthal separation.
    • Then: gated on the precise coordinate (dx) only, with no dy gate at all -- a bug introduced earlier that left the off-axis coordinate completely unconstrained.
    • Now: gates on both -- precise coordinate within ±7.5cm, off-axis coordinate within ±3σ of the hit's own reported off-axis uncertainty, typically ±13cm.
  • Covariance unit: hit covariance stayed in mm² while position had already been converted to cm -- a 10x error in reported sigma, since fixed by rescaling by 1/100.
  • Per-VMM time calibration, 2 bugs: StFttDb::quadrant() was silently merging all 4 real quadrants sharing a (plane,feb,vmm) into one shared timing anchor (wrong sentinel bounds check); separately, the anchor-subtraction had no handling for dbcid's 12-bit rollover, splitting some channels' true peak in two. Found while building the diagnostics for the 6th fix below.
  • Afterburner time cut: AcceptAll → real cut: production's StFttClusterMaker had used kTimeCutModeAcceptAll (no time-based filtering at all) for this whole analysis; switched on a real cut (SetTimeCut(2,-40,100)) after fixing the 2 calibration bugs above. Resolves the long-standing disk0/V dip anomaly and gives a modest overall purity improvement (14.9%→15.6%), though the effect is not uniform across disks -- see the page for the honest, mixed per-disk picture.
  • StFttPointMaker drops all of disk0/quadrant A (found 2026-07-27): MakeLocalPoints() fills clusters[rob][row][orientation] using StFttDb::rob(StFttCluster*), which is 0-based (quadrant + plane*nQuadPerPlane), but the loop consuming that array started at iRob=1: 
        for ( size_t iRob = 1; iRob < StFttDb::nRob; iRob ++ ){
    So clusters[0] was never read and no point was ever made for rob==0 = disk0/quadrant A. It is silently absent from the output, not merely sparse, so it reads as a dead detector region in any QA plot built from these points.
    • Affects the standard bfc ftt chain (FttDat,FttHitCalib,FttClu,FttPoint, see BigFullChain.h), i.e. StFttPoint/StMuFttPoint in production MuDst.
    • Does not affect our afterburner (fwd_afterburner_db.C), which uses StFttClusterPointMaker instead.
    • Root cause is that StFttDb has two rob() overloads with opposite conventions -- rob(StFttRawHit*) is 1-based, rob(StFttCluster*) is 0-based, and which one you get depends on the argument type. Both are correct at every live call site today, so nothing else is broken, but the trap is invisible at the point of use: proposal_rob.txt inventories all three call sites and weighs the options for removing it.

Evidence, and three different causes of "quadrant A is missing"

Counted directly from production MuDst (500 events, script/checkDisk0QuadAPoints.C). Clusters come from StFttClusterMaker, which has no such bug, so they act as the control: if a quadrant has healthy clusters in both orientations but zero points, the point maker dropped them. StFttPointMaker pairs an H with a V cluster to triangulate, so a quadrant missing one orientation yields zero points for a physical reason instead.

quadrant A ofpointsclusters nHnVreading
disk0056,962 18,30215,413 software -- both orientations healthy and in line with neighbouring quadrants, yet zero points. Nothing physical explains this; it is the iRob=1 hole above.
disk1025,177 16,1480 real detector -- V is completely dead, so no H×V pair can form. This is the known missing-foil problem, here confirmed from production MuDst by an independent route. Unrelated to the bug.
disk32,6085,088 4,448443 real, degraded -- both orientations present but suppressed ~10x (H) and ~45x (V). A third, separate condition.
For scale, a healthy quadrant runs ~17-21k clusters per orientation and ~0.5-0.7M points over the same 500 events.

Consequence for QA: "quadrant A is missing" is not one problem. Three disks show it, for three different reasons, so a report of a missing quadrant A is only interpretable once you know which disk and whether its clusters are healthy. The macro above prints all three tables and can be pointed at any MuDst to tell them apart.

Method

  • Updated 2026-07-22 with much larger statistics: 101 real-data files (condor-parallelized, condor/submit_blinddiag_stats.txt + script/runBlindDiag), sampled evenly across the full 3846-file production (data20-23 disks), merged with hadd. ~2 billion "All candidates" entries and ~10-11 million matched entries per disk -- roughly 1000x the original 500-event single-file test. One of the 102 sampled files (run 23081004) produced no output at all and was skipped: confirmed via RunLog that this run had FST off, so zero FST-seeded tracks were ever fit and the blind-diagnostic histograms (which need an FST-only track state) never got created for it -- not a bug, just real run-to-run detector availability.
  • Same hBlindDxAll_V / hBlindDyAll_H histograms (precise coordinate) as the main page -- zoomed into ±5cm and checked for an excess right at the blind projection, before any nearest-hit selection is applied.
  • Background estimated LOCALLY: average of the two sideband windows immediately next to the peak (0.6-3cm on each side), not distant sidebands -- the background is not flat across the full ±15cm range (see disk0/H below), so a distant/symmetric average would pick up that slope instead of measuring a real peak.
  • Peak window: |x|<0.6cm. Significance uses Poisson error on the sideband-average background.
  • script/checkAllExcess.C (numbers) and script/plotAllExcess.C (these plots), both checked in.

Findings

  • With ~1000x the statistics, the excess in 7 of 8 disk×orientation combinations is now several hundred sigma (192-525σ), same ~2-5% magnitude as before -- the earlier 5-15σ single-file read was not a fluke, it's now overwhelming.
  • New at this statistics level: real peaks (and one real dip) are visible directly by eye, not just inferred from a sigma number -- see e.g. disk3/V or disk1/V below, a clean narrow spike sitting on a smooth background hump. This wasn't visually obvious in the single-file plots even though the significance was already there.
  • disk0/V is not just "flat" -- it's a real, visible narrow DIP (excess=0.99x but -127σ, a genuine statistically overwhelming deficit right at dx=0, not noise around zero). Not understood; flagged as a new open question rather than smoothed into "no effect".
  • This is not "zero correlation" -- real data does have a genuine signal in the raw candidate population, not just after selection. Argues against hits landing in a completely uncorrelated wrong place as the full explanation.
  • But it's still far below the ~20x excess seen in the 8 e-/event MC at comparable occupancy -- whatever true efficiency this implies is genuinely low.
  • H-strips also show a striking, reproducible ~15-20% left/right (+dy vs -dy) slope in their own local background, consistent across all 4 disks -- most likely the known real N-S acceptance gap below the beampipe, but not yet confirmed. Separate from the peak-excess question, visible clearly in the disk0/H plot below.

Estimating FTT matching purity

Question: of the FTT hits actually assigned to a track (the "Matched" sample), what fraction are the genuinely correct hit, versus an accidental closest-candidate-in-background match?

Method: for a given track-disk search, the real (correct) FTT hit -- if present and passing the loose off-axis-conditioned gate -- is a single physical hit encountered once in the search loop, so it contributes AT MOST one entry to the "All candidates" histogram, landing in the narrow sub-mm-wide peak at dx/dy=0. The background-subtracted integral of that peak (±1.0cm window, local sideband background) therefore counts "track-searches where the real hit was present and passed the gate" -- call this N_real. Since the real hit trivially also passes the tighter precise-coordinate gate (it's AT zero) and wins "closest" selection (nothing is closer than the true hit), N_real is a good proxy for how many Matched entries are genuinely correct: purity = N_real / N_matched. script/estimatePurity.C, checked in.

This is purity, not full efficiency. The search itself is not conditioned on an FTT hit already being assigned -- findFttStripsNearProjectedState() runs for every FST-seeded, converged track projected to the disk (the FST-only, FTT-blind projection this whole page is built on), independent of whether a hit ends up matched. So this diagnostic does see the full population of attempted track-disk searches, not just the ones that already got a hit. What's still missing for a true efficiency number: a saved count of the TOTAL number of these searches, regardless of outcome -- currently only "All candidates" (conditioned on the off-axis gate, see Method) and "Matched" are saved, not a raw per-search counter. So N_real (the background-subtracted peak) can only be divided by N_matched here, giving purity ("of what got matched, how much is real"), not by total attempts, which would give something closer to true efficiency ("of every attempt, how often is the real hit found and used"). Adding that counter would be a natural next step.

X<->Y mirror test: is the final coordinate simply mirrored?

Method: a direct global-coordinate swap (h->getX()<->h->getY()) would be physically incoherent -- StFttDb::getGloablOffset_ClusterPoint()'s per-quadrant offset/sign tables are asymmetric between X and Y (different shift values, different sign rules per quadrant), so swapping the already-transformed global values would compare each axis against the WRONG quadrant calibration. Instead: invert the known global transform back to LOCAL (mm) coordinates, swap those, then re-apply the CORRECT (still per-axis, still asymmetric) transform to the swapped local values -- this is what a genuine local x<->y mislabeling downstream of clustering would actually produce. Implemented as new, purely additive histograms filled in the same event loop as the existing ones (hBlindDxAll_V_mirror, hBlindDyAll_H_mirror in FwdTracker.h) -- does not touch found_hits/production matching at all, and gives both the normal and mirrored view from a single production pass (no separate condor batch for the "before" state needed). Run on the same 101-file statistics as the plots above.

Quadrant-split check: testing the online-QA H/V-swap hypothesis

Note: this test is DIFFERENT from the mirror test above, not a duplicate -- it perturbs raw-hit orientation classification before clustering (which can change which raw hits get merged into which cluster in the first place, since clustering happens separately per orientation stream), whereas the mirror test above perturbs only the already-correctly-clustered point's final coordinate. These are genuinely different hypotheses (raw hardware-map/online-QA labeling vs. a downstream coordinate-convention mismatch), which is part of why this test came out messier/inconclusive while the mirror test above came out clean and decisive -- not a contradiction between them.

Online monitoring (run22) reports, for plane2(=disk1)/quadrant A (positive x, positive y): FOB 1,3,5 alive, FOB 2,4,6 dead, and the alive FOBs are Vertical. A direct raw-hit tally (script/checkOrientationMap.C) confirms the same alive/dead FOB split in our data, but the original StFttDb::getOrientation() code labels those same alive FOBs Horizontal -- a direct, confirmed contradiction. A full kFttHorizontal<->kFttVertical swap (both branches of getOrientation()) was tested against the quadrant-split excess check above to see if it clarifies the picture.

Correction (2026-07-21): the quadrant-split plots (further down) show slopes and step-edges -- real geometric features of a single quadrant's acceptance -- not a symmetric bump at dx/dy=0 the way the whole-disk plots do. The quadrant-level "excess/significance" numbers are an artifact of comparing a flat local-sideband average against what is actually a monotonic gradient, and should be read qualitatively, not as signal significance.

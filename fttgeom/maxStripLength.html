FTT geometry bug: StFttCluster::maxStripLength() defaults to -999, never set

← Back to FTT geometry index (all 4 fixes, and links to the quadrant×charge / electron-gun / FST-blind-projection pages)

Found and fixed while investigating why the FTT hit-position maps on the quadrant × charge page showed a top/bottom + north/south swapped, bowtie-shaped footprint instead of the expected octagon. Full derivation of the diagnosis (including the single-electron particle-gun test that ended up motivating a separate FTT sim-hit-maker proposal) is on the electron gun @ 45° page. This page is just the bug writeup itself, split out for its own reference.

The bug

Tracing StFttClusterPointMaker::MakeLocalPoints() (StFttClusterPointMaker.cxx:184,209) found the row-position formula:

point->setY( mFttDb->YX_StripGroupEdge[clu_x->row()] + clu_x->maxStripLength()/2. );

StFttCluster::maxStripLength() reads a member that defaults to -999 (StEvent/StFttCluster.h:92, comment: "Strip center of strip with maximum ADC") and StFttClusterMaker.cxx never calls setMaxStripLength() -- confirmed by grepping the entire maker for every set*() call: setPlane, setQuadrant, setRow, setOrientation are all there in the max-ADC-hit copy block (StFttClusterMaker.cxx:461-464), setMaxStripLength is simply missing from that list. So every real cluster's row-position term evaluates to YX_StripGroupEdge[row] + (-999)/2 = YX_StripGroupEdge[row] - 499.5mm -- a large negative garbage value instead of a small positive row-center offset. The same field also poisons the covariance (maxStripLength()²/12) and the diagonal-cluster formulas (StFttClusterPointMaker.cxx:230,235,270,275).

Combined with the (correct, unmodified) per-quadrant sy/sx sign flips in StFttDb::getGloablOffset_ClusterPoint() (global.set(((x*sx)+dx)/10, ((y*sy)+dy)/10, z+dz)), this large negative local value doesn't just shift the result -- it flips which side of zero a whole quadrant lands on:

Quadrow0 y, broken (maxStripLength=-999) row0 y, fixed (real strip length)
A (south-top)-39.27 cm+18.72 cm
B (south-bottom)+57.22 cm-0.77 cm
C (north-bottom)+57.16 cm-0.83 cm
D (north-top)-39.23 cm+18.76 cm

This one bug explains the full swap, not just a shift. Every quadrant flips which side of y=0 it lands on -- quads A/D (top) land negative instead of positive, quads B/C (bottom) land positive instead of negative. This exactly matches the real bands seen on the quadrant × charge page before the fix (y≈-40,-23,-4 for quads A/D and +22,+42,+58 for quads B/C) and exactly matches what was flagged early in this investigation: "not only top 1/2 and bottom 1/2 is swapped... plus north and south is also swapped as well."

Side effect: since maxStripLength()² also feeds the covariance (StFttClusterPointMaker.cxx:186,199), every real point gets an enormous, unphysical uncertainty (σ≈29cm) in the long-strip direction. GenFit would heavily down-weight such points in the fit -- plausibly why real-data tracks still fit and matched FCS reasonably despite hit positions being this badly wrong.

Bowtie shape: also explained, by the same bug

The bug is a rigid per-row constant -- it doesn't stretch anything, so it can't directly distort a shape. But it does something just as effective: it reverses the row order. Correctly, row0 (nearest the beampipe) should land nearest y=0 and row2 (farthest) should land farthest from y=0; under the bug this is exactly backwards (row0 lands farthest, row2 lands nearest). Since each row has its own row-intrinsic x-extent (unrelated to the bug -- it's set by clu_x->x(), the real, continuous, untouched strip-index coordinate), swapping which row sits near vs. far from y=0 also swaps which x-extent shows up there. Checking the real data for disk0_x directly: row0 (appearing at the observed y=-40cm band, pre-fix) has max|x|=54.4cm (wide); row2 (observed y=-4cm band) has max|x|=30.1cm (narrow). Under the fixed mapping, row0's 54.4cm-wide data sits at y=+18.7cm (near zero) and row2's 30.1cm-narrow data sits at y=+54.8cm (far from zero) -- wide near the middle, narrow at the extremes: a proper octagon. The observed bowtie (narrow near the middle, wide at the extremes) is exactly this octagon with the row order reversed. No second bug needed -- both observed shape anomalies (the top/bottom+north/south swap, and the bowtie) come from this same single missing setMaxStripLength() call.

Checked against Daniel's dev branch (origin/dev, upstream jdbrice/star-sw-1)

Confirmed the bug is still present, unfixed, in Daniel's current dev branch (commit c7c187e00d, 2026-07-13) -- this is not a fork-local issue: setMaxStripLength() is still never called in dev's StFttClusterMaker.cxx either.

Also confirmed (per a question about the text file) commit 58c67e52fe ("StFttDb: embed strip geometry tables instead of reading Row*.txt", 2026-05-17): the FTT hardware was retired with a static geometry, so Row1.txt, Row4.txt, Row4_edge.txt, Row{1..5}_StripLength.txt are now compiled in as constexpr arrays in StFttDb.cxx instead of being read at runtime. Unrelated to the bug above, but explains why those .txt files no longer matter.

Tracing this further found the real strip-length data does exist and is wired up correctly one layer down -- it just never gets carried through to the cluster. StFttDb::hardwareMap(StFttRawHit*) (StFttDb.cxx:606-639 in dev) correctly looks up the (now-embedded) slMapRow1..5 tables and calls hit->setStripLength(stripLength) on every raw hit, so StFttRawHit::stripLength() genuinely holds the real per-strip length. The fix is one missing line in StFttClusterMaker::CalculateClusterInfo() (StFttClusterMaker.cxx:461-464 in dev, same in this repo), right next to the other max-ADC-hit field copies:

clu->setPlane       ( maxAdcHit->plane       ( ) );
clu->setQuadrant    ( maxAdcHit->quadrant    ( ) );
clu->setRow         ( maxAdcHit->row         ( ) );
clu->setOrientation ( maxAdcHit->orientation ( ) );
clu->setMaxStripLength( maxAdcHit->stripLength() );  // <-- missing

Fixed and validated on real data -- see the quadrant × charge page for the before/after comparison. Confirmation with Daniel on syncing this fix upstream is still pending. Production plots across jpsi/ still need updating with the fix before it's fully rolled out -- see that page's "Next steps".

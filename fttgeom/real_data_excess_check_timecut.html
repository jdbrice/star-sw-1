Real-data excess/purity check: with a real FTT time cut, after fixing the calibration

← Back to FST-blind projection study | ← Original (AcceptAll baseline) version of this page

Context

  • Production's StFttClusterMaker time cut had been kTimeCutModeAcceptAll (no real time-based filtering) for the entire history of this analysis. This session, switched it on: SetTimeCut(2, -40, 100) (kTimeCutModeCalibratedTime, window from Run22-Run24 online QA) in fwd_afterburner_db.C.
  • While building the diagnostics to check this, found and fixed two real bugs in the per-VMM time calibration itself -- see the per-VMM uuid-vs-time diagnostic page for the full writeup:
    • StFttDb::quadrant() was silently merging all 4 physical quadrants sharing a (plane,feb,vmm) into one shared timing anchor (wrong bounds check on a sentinel value).
    • HitCalibHelper::time() had no handling for dbcid's 12-bit (4096) rollover, splitting some channels' true peak into two disconnected sub-peaks.
  • This page repeats the main real-data checks from the original (AcceptAll) page on a fresh 101-file condor batch (same file sample, condor/submit_blinddiag_stats_timecut.txt + script/runBlindDiag, output in /gpfs01/star/pwg_tasks/FwdCalib/akio/blinddiag_stats_timecut/, merged with hadd) -- now with both bugs fixed and the time cut genuinely active, to see what changed. The online-QA H/V-labeling investigation (mirror test, quadrant-swap test) is NOT repeated here -- that's a separate, still-parked question; see the original page for that thread.

Findings

  • disk0/V's dip is resolved. The original AcceptAll baseline showed a genuine, overwhelming -127σ to -130σ DIP at disk0/V (fewer real-looking matches near dx=0 than the local background predicted) -- flagged repeatedly as an unexplained open question. With both calibration bugs fixed and the time cut active, disk0/V now shows a real, positive excess: 1.04x, +352.9σ -- same character as every other disk/orientation, not an outlier anymore. Purity flips the same way: N_real went from -384,541 (baseline, meaningless negative) to +760,204 (this run).
  • Every disk/orientation excess is stronger than the AcceptAll baseline -- 353-816σ here vs. 192-525σ in the original page, at the same 101-file statistics. Consistent with cutting away out-of-time noise before clustering, as hoped.
  • Overall purity (excluding disk0/V, for apples-to-apples with the original 14.9% figure): 14.9% → 15.6%. A real but modest improvement, not the large jump the single-file smoke test (10.3%→18.6%, done before either bug was found/fixed) suggested -- that earlier result likely didn't survive contact with the real, full-statistics, properly calibrated picture.
  • Per-disk pattern is mixed, not a uniform win: disk0 and disk1 clearly improve (disk1 V: 7.9%→11.0%, disk1 H: 8.6%→11.6%), disk2 is roughly flat, and disk3 gets slightly worse (V: 21.7%→19.5%, H: 22.4%→20.3%). Not understood yet -- worth checking whether the fixed -40,100 window is well-matched to disk3's own timing specifically, or whether something disk-dependent is going on.

Reading: a real, modest overall improvement, and disk0/V's long-standing dip anomaly is resolved -- but this is not a clean, uniform win across the detector. disk3 is measurably worse with the time cut than without it, which argues against a simple "noise is uniformly time-separable, cutting always helps" story. Worth understanding disk3's specific behavior before treating -40,100 as a settled choice for the whole detector.

  (1) EPD/FCS-pres hits had no plane and were silently dropped in planar mode
      -- about 2.1 hits/event, from Global and Primary both. They are now kept as
      spacepoints, like the PV.
        StRoot/StFwdTrackMaker/include/Tracker/TrackFitter.h:750

  (2) kFstzFilp[disk] was missing from the decode, so every wedge on the middle disk
      was mirrored, up to +-15 deg. The fix was not to add the constant back but to
      stop discarding the geometry: the node matrix carries the front/back flip, so
      the V axis is no longer normalised to counter-clockwise.
        StRoot/StFwdTrackMaker/include/Tracker/TrackFitter.h:503 (comment), :476-540

  (3) _localPosition holds raw strip indices, so the loader's phi corrections never
      reached it and there was no 1 deg outer-sensor gap term at all. The gap is now
      read from the sensor shape's Phi1/Phi2, where it actually lives.
        StRoot/StFwdTrackMaker/include/Tracker/TrackFitter.h:521-534

  (4) The sensor -> FTUS mapping used (index%3)+1, which puts inner hits on an outer
      plane and vice versa -- a 1.4 cm z error on two sensors out of three. The real
      mapping was measured from data: 0->FTUS_3, 1->FTUS_1, 2->FTUS_2.
        StRoot/StFwdTrackMaker/include/Tracker/FwdGeomUtils.h:207 (and :213 onward)
        script/fstLocalMap.C  (the measurement)

  (5) The volume path was hardcoded as /FSTM_1/FSTD_<d>/FSTW_<w>/FTUS_<s>, which fails
      on ANY misaligned geometry -- all 108 planes then fall back to the origin, with
      no error. Sensors are now found by physics: disk from z, wedge from the local +x
      bisector, sensor from the shape.
        StRoot/StFwdTrackMaker/include/Tracker/FwdGeomUtils.h:213 walkFstSensors()
        StRoot/StFwdTrackMaker/include/Tracker/FwdGeomUtils.h:248 buildFstSensorMap()

  This is the one I would check first against your version. It is silent: the code
  runs, every plane is at the origin, and nothing complains.

Two things we learned this week that will save you time:

  - StFttDb now takes the sTGC per-quadrant offsets from the survey tables rather than
    its hardcoded numbers, so an alignment iteration moves the FTT hits as well as the
    planes. It is on by default; setUseDbGeometry(false) restores the old behaviour.
    On 90 jobs / 1.17M events this took the FST->sTGC dy residual from +1.30 cm to
    +0.35 cm.

  - From the second iteration on, do NOT regenerate the misalign table from the
    residuals. Once the tables are being applied, the residual you measure is already
    relative to them, so the update is new = previous + delta. There is a helper:
        script/stgcTableAddDelta.py
    script/stgcQuadOffsets.C now refuses to write absolute tables unless you tell it
    this is iteration 1, precisely so this cannot be got wrong silently.

Short version first, details below for reference.

MY MAIN SUGGESTIONS

  (A) I think your final alignment should land as the geometry misalign tables
          $STAR/StarDb/Geometry/fst or stgc/*.C (and eventually to Offline DB)
            -> AGML -> fGeom.root
      , not as constants in code or text is other formats. That is the one place 
      both reconstruction and simulation can read it from.

  (B) I strongly recomend to work in kUseSpacePoints = false (planar) mode, with my fixes 
      and Flemming's new geometry. That gets you the correct per-sensor z, and it keeps 
      you inside the AGML transform instead of the various hardcoded geometry conventions 
      scattered outside it (See E).

  (C) While you are on iterations, you can do something of your own. But 
      rebuilding fGeom.<version>.root costs only ~30 seconds and iteration and the 
      final result then use exactly the same format and same code to apply them.
      So I'd argue that it is better if you use same geometry misalign tables 
      and rebuild fGeom.<version>.root for iterations too. Please see : 
         /star/u/akio/fcstrk11/star-sw-fwd/build_geom_misalign.C
      You can use date & time to keep different versions/iterations for records.

  (D) You can buildup for codes and test it now as is, but once we have the >1cm 
      sTGC survey offsets in the misalign tables, that should be your starting 
      point rather than ideal (all 0 translation, no rotation) geometry. Since STGC
      offsets seems to away from ideal in significant amount, we'll run MC with
      misalign on.

  (E) One caveat on (B): the fixes are not in the repo you have. I found five separate
      bugs in the planar path this week -- a wrong sensor -> FTUS plane mapping, a
      mirrored middle disk, dropped EPD hits, the 1 degree gap, and a hardcoded volume
      path that fails on ANY misaligned geometry -- and fixing them took the FST->sTGC
      match from 5.4% to 17.3%, level with the spacepoint path's 17.7%. The full list,
      with what each one did and how it was fixed, plus the before/after plot, is in
      section 5 of the FST/FTT flip page:

          https://www.star.bnl.gov/protected/spin/akio/fcs/FstFttFlipTest/index.html#spacepoints

      Since the Github/Gitea transition freeze is coming Monday, getting this into a PR

More defaills : 

1. YOUR NUMBERING IS THE SAME AS THE DB/MuDst ONE
-------------------------------------------------
We measured the stored wedge index against global phi straight out of a MuDst and got
wedge 0 -> [60.12, 89.88] deg, wedge 1 -> [30.12, 59.88], wedge 2 -> [0.12, 29.88] ...
i.e. centres at 75, 45, 15, ... 105, exactly your QA convention (clockwise from
vertical, wedge 11 back at +105). So your QA numbering and the reconstruction's
per-disk wedge index agree, and no translation is needed between them.


2. YOUR SENSOR -> FTUS MAPPING IS RIGHT, AND THE TRACKING CODE HAD IT WRONG
---------------------------------------------------------------------------
You wrote that AGML uses FTUS_3 for inner (your sensor 0), with your sensors 1 and 2
following FTUS_1 and FTUS_2. That is correct, and we confirmed it from data rather
than from documentation: for every FST hit we transformed the stored global position
into each of the three FTUS local frames of its wedge and kept the one whose shape
actually contains the hit. Result:

    hit sensor 0 (inner) -> FTUS_3, shape phi [345.0, 375.0], 128 strips, phi DECREASING
    hit sensor 1 (outer) -> FTUS_1, shape phi [344.5, 359.5],  64 strips, phi increasing
    hit sensor 2 (outer) -> FTUS_2, shape phi [  0.5,  15.5],  64 strips, phi increasing
    pitch = 0.234375 deg everywhere

Cross-check: the geometry puts inner strip 0 at 375 - 0.5*0.234375 = 374.883 deg, and
the data says 374.883.

Worth flagging: StFwdTrackMaker's own geometry helper did NOT have this. It used
FTUS_(sensor+1), which puts inner hits on an outer sensor's plane and vice versa — a
1.4 cm z error on two sensors out of three. We fixed it yesterday. If you are using
FwdGeomUtils::getFstSensorOrigin, or anything derived from it, please pick up the fix
or you will be solving for a misalignment that is partly this bug.


3. THE SENSOR SIDE-SWAP YOU NOTICED IS THE WEDGE FLIP AND YOU CAN LET GEOMETRY DO IT
---------------------------------------------------------------------------------------
You wrote that sensors 1 and 2 swap between positive and negative local phi with wedge
orientation. Yes — that is the 180 degree x-rotation with which AGML places the
front/back wedges, visible as zz = -1 in the node matrix. Half the wedges on a disk
have it, and the set flips again from disk to disk.

The useful part: in the sensor's OWN local frame the mapping is invariant — strip 0
always sits at the shape's Phi1 — and the whole swap is carried by the node matrix. So
if you build the local position from (r, phi strip) in the sensor frame and then apply
the AGML local->global transform, you never need per-wedge sign bookkeeping at all.

That is exactly what we changed in the tracker. The old code normalised the V axis to
counter-clockwise (throwing the orientation away) and then re-supplied the direction
from hardcoded per-wedge/per-disk sign tables — 36 sign bits, one of which was wrong,
mirroring every wedge on the middle disk. Letting the matrix carry it reduces that to
one rule per sensor type. I would recommend the same approach for your solver: it also
means Flemming's new tag, which changes the wedge parity, flows through with no code
change on your side.


4. THE 1 DEGREE GAP LIVES IN THE AGML SENSOR SHAPES
----------------------------------------------------
Worth knowing because the transform alone will not give it to you: the 1 degree dead gap
between the two outer sensors is in AGML, but in the sensor SHAPES (the outer phi limits
above, +-0.5 to +-15.5), not in the matrices. FTUS_1 and FTUS_2 have IDENTICAL placement
matrices — the shape is the only thing that distinguishes them. So a strip -> local
position conversion has to read Phi1/Phi2; the local->global transform cannot say which
half of the wedge a sensor covers.

Take the gap from the shape and you never need the kFstStripGapPhi constant at all. That
is what we did in the planar decode.

(If you ever work from the MuDst global positions instead, be aware they carry a known
1 degree per-half error from a sign bug in StFstHitMaker, which would be absorbed into
your constants — see proposal_spacepointmode_fix.txt. It does not apply to the planar
path.)


5. WEDGE-LEVEL SOLVING IS FINE
-------------------------------
You said the local measurements are stored at wedge level, so sensor-level tuning is out
for now. In planar mode that is fine: the per-sensor shape and placement come from AGML,
so what you are solving for really is a wedge-level deviation on top of a correct
per-sensor model.

It is still worth splitting inner vs outer in your QA. In spacepoint mode a systematic
inner-outer phi difference of 0.5-1 deg is expected from the gap bug above and is not
misalignment; in planar mode that difference should be absent, which makes the split a
useful check that you are really running the mode you think you are.


6. ITERATION: DO YOU HAVE TO REBUILD fGeom.root EACH TIME?
-----------------------------------------------------------
Yes, and it is cheap. We timed a full misaligned build (bfc with the misalign option, AgML
construction, export) at about 31 seconds — nothing against a reconstruction pass, so the
rebuild is not a reason to invent an on-the-fly scheme.

In planar mode the geometry IS the measurement, so new tables -> rebuild -> hits move,
which is exactly the loop you want: edit tables, rebuild (30 s), rerun the afterburner,
measure, repeat. The virtue is that there is one application point, and it is the same one
the final result will use, so what you converge on is what production will apply.

(In spacepoint mode rebuilding fGeom.root does essentially nothing to FST hits, which is
the other reason to work in planar.)

Two practical requirements: version the cache (fGeom.<tag>.<sdt>.root and a symlink, never
overwrite in place — a stale fGeom.root means fitting new hits to old planes, silently),
and record which table version produced each iteration's input, or pass 2 corrects on top
of an unknown baseline.


7. WHERE THE OUTPUT SHOULD LAND
--------------------------------
The DB hierarchy already defines the levels you are solving for:

    fstOnTpc -> hssOnFst -> fstWedgeOnHss -> fstSensorOnWedge

so wedge-level results belong in fstWedgeOnHss (36 rows, row = iwedgem + 12*idisk) and
half-level in hssOnFst (2 rows, row = halfid) rather than in a new flat format — that is
the indexing AGML expects, and it is what makes the misalign build work without a
translation layer. The tables are already the right size — hssOnFst has 2 rows,
fstWedgeOnHss 36 and fstSensorOnWedge 108, all filled in loops — they are simply identity
today, so you are filling in values rather than creating structure, and no geometry file
change goes with it.

Sign convention, from AgPosition.h: Misalign takes options "+xyzr", where "+ is to real,
- is to ideal". Whatever reconstruction does has to use the same sense.

Each iteration should be a new timestamped entry rather than an edited file — that is
what makes a pass reproducible and lets any past run be reprocessed with the alignment
that was current then.
